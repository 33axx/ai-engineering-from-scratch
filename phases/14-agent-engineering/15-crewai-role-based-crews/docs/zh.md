# CrewAI：基于角色的团队与流

> CrewAI 是 2026 年基于角色的多智能体框架。四个原语：智能体、任务、团队、流程。两种顶层形态：团队（自主、基于角色的协作）与流（事件驱动、确定性）。文档直言：“对于任何生产级应用，从流开始。”

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置条件：** 阶段 14 · 12（工作流模式），阶段 14 · 14（演员模型）  
**时间：** ~75 分钟

## 学习目标

- 说出 CrewAI 的四个原语（智能体、任务、团队、流程）以及每个原语负责什么。
- 区分顺序流程、层次流程和规划的共识流程；根据工作负载选择一个。
- 区分团队（自主基于角色）与流（事件驱动确定性），并解释文档中的生产推荐。
- 使用 `@tool` 装饰器和 `BaseTool` 子类连接工具；推理结构化输出与自由文本。
- 说出 CrewAI 的四种记忆类型以及每种类型何时有价值。
- 实现一个标准库三智能体团队（研究员、写手、编辑），生成一份简报。
- 指出 CrewAI 的三种失败模式：提示膨胀、管理者 LLM 税、脆弱的交接。

## 问题

采用多智能体框架的团队会遇到同样的瓶颈。“自主协作”在演示中听起来很棒。然后客户报告了一个错误，你需要确定性回放。或者财务部门询问每次运行 LLM 路由的团队的成本。或者值班人员需要知道凌晨 3 点哪个智能体卡住了。

自由的 LLM 路由团队无法清晰地回答这些问题。纯 DAG 可以回答所有问题，但失去了头脑风暴智能体所需的探索性形态。

CrewAI 的划分诚实地表达了这种权衡。团队用于协作、基于角色、探索性的工作。流用于事件驱动、代码拥有、可审计的生产环境。同一个框架，两种形态，根据表面选择。

## 概念

### 四个原语

CrewAI 的表面很小。记住这个，其余都是配置。

- **智能体（Agent）。** `role + goal + backstory + tools + (可选) llm`。背景故事承担重要职责。它塑造语气、判断以及智能体何时停止。工具是智能体可以调用的函数（更多内容见下）。
- **任务（Task）。** `description + expected_output + agent + (可选) context + (可选) output_pydantic`。一个可重用的工作单元。`expected_output` 是契约。`context` 列出上游任务，其输出会被传入。`output_pydantic` 强制结构化形态。
- **团队（Crew）。** 容器。拥有 `agents` 列表、`tasks` 列表、`process` 以及可选的 `memory`、`verbose` 和 `manager_llm` 设置。
- **流程（Process）。** 执行策略。顺序、层次、共识（已计划）。决定运行的形态。

智能体不会直接看到彼此。任务引用智能体。团队对任务进行排序。流程决定谁选择下一个任务。这就是整个心智模型。

> **已验证于** CrewAI 0.86 (2026-05)。较新版本可能重命名或合并流程类型；在依赖特定形态前，请检查 [CrewAI 流程文档](https://docs.crewai.com/concepts/processes)。

### 顺序 vs 层次 vs 共识

- **顺序（Sequential）。** 任务按声明顺序运行。任务 N 的输出作为 `context` 提供给任务 N+1。成本最低。最可预测。当顺序固定时使用。
- **层次（Hierarchical）。** 一个管理者智能体（单独的 LLM 调用）在专家之间进行路由。CrewAI 根据你的 `manager_llm` 配置或默认配置生成管理者。管理者每轮选择下一个任务，可以拒绝或重新路由。当你有四个或更多专家，并且顺序确实取决于先前输出时使用。
- **共识（Consensus）。** 已计划，目前未在公开 API 中实现。文档保留该名称用于未来基于投票的流程。今天不要依赖它。

层次流程在每次专家调用之上增加了一轮 LLM 调用（管理者）。在五步运行中，Token 成本可能翻三倍。只有在需要路由时才为此付费。

### 团队 vs 流

这是文档在 2026 年首先提出的框架。

- **团队（Crew）。** LLM 驱动的自主性。框架在运行时选择形态。适用于：研究、头脑风暴、初稿，以及任何路径本身是答案一部分的地方。难以重放。难以测试。原型成本低。
- **流（Flow）。** 你自己拥有的事件驱动图。`@start` 标记入口。`@listen(topic)` 标记一个步骤，该步骤在另一个步骤发出该主题时触发。每个步骤都是纯 Python（可以在内部调用一个团队）。适用于：生产。可观察。可测试。确定性。

文档的 2026 年生产建议：从流开始。当自主性物有所值时，将团队作为 `Crew.kickoff()` 调用折叠在流步骤内部。流提供审计追踪，团队提供探索。组合，而不是选择。

### 工具集成

三种方式为智能体提供工具。选择最适合的最简单的方式。

1. **`@tool` 装饰器。** 纯函数变成工具。签名是模式；文档字符串是 LLM 看到的描述。最适合一次性辅助工具。

   ```python
   from crewai.tools import tool

   @tool("Search the web")
   def search(query: str) -> str:
       """Return top results for the query."""
       return run_search(query)
   ```

2. **`BaseTool` 子类。** 基于类的工具，带有显式参数模式、异步支持、重试。当工具有状态（客户端、缓存）或需要结构化参数时使用。

   ```python
   from crewai.tools import BaseTool
   from pydantic import BaseModel

   class SearchArgs(BaseModel):
       query: str
       limit: int = 10

   class SearchTool(BaseTool):
       name = "web_search"
       description = "Search the web and return top results."
       args_schema = SearchArgs

       def _run(self, query: str, limit: int = 10) -> str:
           return self.client.search(query, limit=limit)
   ```

3. **内置工具包。** CrewAI 提供第一方适配器：`SerperDevTool`、`FileReadTool`、`DirectoryReadTool`、`CodeInterpreterTool`、`RagTool`、`WebsiteSearchTool`。一次导入即可连接。

结构化输出使用 Pydantic。在任务上传递 `output_pydantic=MyModel`。CrewAI 根据模型验证 LLM 响应，并强制或重试。将其与紧凑的 `expected_output` 字符串配对。自由文本输出适合草稿；结构化输出是下游流可以消费的内容。

### 内存钩子

CrewAI 开箱即用提供四种内存类型。它们可以组合：一个团队可以同时启用所有四种类型。

> **已验证于** CrewAI 0.86 (2026-05)。最近的版本将所有内容路由到一个统一的 `Memory` 系统，该系统封装了这四个存储。下面的概念模型仍然成立，但公共类表面可能在较新版本中折叠为单个 `Memory` 入口点；请检查 [CrewAI 内存文档](https://docs.crewai.com/concepts/memory) 以获取当前 API。

- **短期记忆。** 单次运行内的对话缓冲区。结束时清除。
- **长期记忆。** 跨运行持久化。存储在向量数据库（默认为 Chroma，可替换）中。通过与当前任务的相似性检索。
- **实体记忆。** 每个实体的事实。“客户 X 在企业计划中。”按实体键控，而不是按相似性。跨运行存活。
- **上下文记忆。** 组装时检索。在智能体需要时拉取相关记忆，而不是预加载。

在团队上通过 `memory=True` 或按类型配置启用。由你配置的嵌入提供程序支持（默认为 OpenAI，可替换为本地）。内存是 CrewAI 相对于较薄框架的价值所在；纯 LangGraph 要求你自己连接每一个。

### 何时适用 CrewAI

- 三到六个具有命名角色和协作工作流的智能体。草稿、审查、规划、头脑风暴。
- 路由中 LLM 关于下一步的判断是价值的一部分（层次）。
- 任何团队更喜欢阅读 `role + goal + backstory` 而不是图形定义的地方。

### 何时不适用 CrewAI

- 具有严格顺序的确定性 DAG。使用 LangGraph（第 13 课）。图形形状是合适的抽象；CrewAI 的角色框架是摩擦。
- 亚秒级延迟预算。层次增加了往返。即使是顺序序列化也包含背景故事和先前输出的提示。
- 单智能体循环。跳过框架；一个智能体循环（第 1 课）加上一个工具注册表更短。

第 17 课（智能体框架权衡）以矩阵形式阐述了这一点。简而言之：CrewAI 位于“协作基于角色”的角落。

### 依赖关系

独立于 LangChain。Python 3.10 到 3.13。使用 `uv`。星数：参见 [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI)（截至 2026-05 的快照）。AWS Bedrock 集成已文档化；供应商基准测试报告在 QA 工作负载上比 LangGraph 有显著加速，但方法论（数据集、硬件、评估指标）未发布，因此将框架供应商数字视为方向性。

### 这种模式出错的地方

- **背景故事导致的提示膨胀。** 每个智能体 2000 词的背景故事和一个五智能体团队在第一次工具调用前就消耗了上下文预算。保持背景故事不超过 200 词。跨智能体复用短语；不要重复五次家庭风格。
- **管理者 LLM Token 税。** 层次流程在每次专家调用前增加一次管理者 LLM 调用。在一个五个任务的团队中，这是六次 LLM 调用而不是五次，而且管理者调用携带完整的任务列表加上先前输出。除非路由取决于输出，否则切换到顺序。
- **脆弱的交接。** 任务 N 的 `expected_output` 是“一个大纲”。任务 N+1 将其作为 `context` 读取并尝试解析三个部分。LLM 产生了四个。下游智能体即兴发挥。通过在任务 N 上使用 `output_pydantic` 修复，这样任务 N+1 读取的是类型化对象，而不是自由文本。
- **团队作为生产。** 没有流包装器的自由形式团队放入生产。输出变异性高；重放不可能；值班人员无法比较坏运行与好运行。用流包装。

## 构建它

`code/main.py` 实现了两种形态的标准库版本以及一个三智能体团队。

形态：

- `Agent`、`Task` 数据类，匹配 CrewAI 的表面。
- `SequentialCrew.kickoff(inputs)` 按声明顺序运行任务，将输出作为 `context` 传递。
- `HierarchicalCrew.kickoff(topic)` 添加一个管理者智能体，每轮选择下一个专家，在“完成”时停止。
- `Flow` 带有 `@start` 和 `@listen(topic)` 装饰器、一个小型事件循环和一个追踪。
- `tool(name)` 装饰器，反映 CrewAI 的 `@tool` 形状。
- `Memory` 带有 `short_term`、`long_term`、`entity` 存储；模拟相似性使用 numpy。
- 模拟 LLM 响应是基于角色加上输入前缀的硬编码字符串。无网络。确定性。

具体演示：研究员、写手、编辑团队，生成关于“2026 年智能体工程”的简报。研究员获取（模拟的）来源。写手起草。编辑精简。同一团队通过流运行以显示确定性形态。

运行它：

```bash
python3 code/main.py
```

追踪涵盖：顺序团队通过 `context` 传递输出；层次团队具有管理者选择（研究员、写手、编辑，然后“完成”）；流运行相同的三个步骤，具有显式主题（`researched`、`drafted`、`edited`）；通过 `@tool` 路由的工具调用；以及在两次 kickoff 之间存活的长期记忆。

团队追踪是流动的；管理者原则上可以重新排序。流追踪是固定的。这个选择就是教训。

## 使用它

- **CrewAI 流** 用于生产。即使流只是一个调用 `Crew.kickoff()` 的步骤。流提供了审计边界。
- **CrewAI 团队（顺序）** 用于明确排序的协作工作，尤其是初稿和审查循环。
- **CrewAI 团队（层次）** 当路由取决于输出并且你有四个或更多专家时。
- **LangGraph**（第 13 课）用于显式状态机、持久恢复、严格排序。
- **AutoGen v0.4**（第 14 课）用于演员模型并发和故障隔离。
- **OpenAI Agents SDK**（第 16 课）用于具有交接和护栏的 OpenAI 优先产品。
- **Claude Agent SDK**（第 17 课）用于具有子智能体和会话存储的 Claude 优先产品。

## 交付它

`outputs/skill-crew-or-flow.md` 为一个任务选择团队 vs 流，并搭建最小实现。严格拒绝：没有背景故事的团队、没有显式主题的流、少于三个专家的层次。

## 陷阱

- **背景故事作为调味品。** 它塑造输出。每个智能体测试三个变体；差异是真实的。选择一个，冻结它。
- **跳过 `expected_output`。** 没有每个任务的契约，下游任务会拾取 LLM 产生的任何内容。团队运行；审计失败。
- **始终开启记忆。** 每次运行都写入长期记忆。向量数据库增长。检索变得嘈杂。将写入范围限定于事实持续存在的任务。
- **管理者提示漂移。** 层次流程的管理者提示是隐式的。如果路由变得奇怪，在详细模式下转储并阅读。
- **团队中的工具副作用。** 一个团队可以比预期更频繁地调用一个工具。POST、DELETE、付款属于流步骤，绝不属于团队工具。

## 练习

1. 将顺序团队转换为流。计算变异性下降的接触点。注意可读性在哪里下降了。
2. 向团队添加实体记忆：关于客户的事实跨 kickoff 持久化。验证检索拉取正确的实体。
3. 实现一个层次流程，其中管理者拒绝路由到编辑，直到写手的输出至少有三个段落。追踪重试。
4. 为（模拟的）网络搜索连接一个 `BaseTool` 子类。比较追踪形状与 `@tool` 装饰器版本。
5. 向编辑任务添加 `output_pydantic=Brief`，其中 `Brief` 有 `title`、`summary`、`sections`。使写手任务输出一次格式错误的 JSON；验证追踪中 CrewAI 的重试行为。
6. 阅读 CrewAI 的文档介绍。将玩具移植到真实的 `crewai` API。标准库版本跳过了哪些保证？
7. 将 AgentOps 或 Langfuse（第 24 课）连接到一个真实运行。在标准库版本中你错过了哪些追踪？

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| 智能体 | “角色” | 角色 + 目标 + 背景故事 + 工具 |
| 任务 | “工作单元” | 描述 + 预期输出 + 分配者 + 可选结构化输出 |
| 团队 | “智能体团队” | 智能体 + 任务 + 流程的容器 |
| 流程 | “执行策略” | 顺序 / 层次 / 共识（已计划） |
| 流 | “确定性工作流” | 事件驱动、代码拥有、可测试 |
| 背景故事 | “角色提示” | 智能体的语气和判断塑造者 |
| `@tool` | “函数工具” | 将函数转换为智能体可调用的工具的装饰器 |
| `BaseTool` | “类工具” | 基于类的工具，带有参数模式、重试、异步支持 |
| 实体记忆 | “每个实体的事实” | 限定于客户/账户/问题的记忆 |
| 长期记忆 | “跨运行记忆” | 向量备份的记忆，在 kickoff 之间存活 |
| 上下文记忆 | “即时检索” | 在智能体需要时拉取的记忆 |
| 管理者 LLM | “路由智能体” | 层次流程中额外的 LLM，用于选择下一个任务 |
| `expected_output` | “任务契约” | 告诉智能体（和审计）返回什么形状的字符串 |
