# Human-in-the-Loop: 提议-然后-提交

> 2026 年关于 HITL 的共识是具体的。它并非“智能体提问，用户点击批准”。而是提议-然后-提交：提议的操作被持久化到带有幂等键的持久化存储中；连同意图、数据溯源、所触及权限、影响范围和回滚计划一起呈现给审核人；仅在收到明确确认后提交；执行后进行验证，以确保副作用确实发生。LangGraph 的 `interrupt()` 加上 PostgreSQL 检查点，Microsoft Agent Framework 的 `RequestInfoEvent`，以及 Cloudflare 的 `waitForApproval()` 都实现了相同的模式。典型的失败模式是橡皮图章式批准：“批准？”被点击而未经过审核。已记录的缓解措施是使用带有明确检查清单的挑战与响应。

**类型：** 学习
**语言：** Python（标准库，带幂等性的提议-然后-提交状态机）
**前置条件：** Phase 15 · 12 (Durable execution), Phase 15 · 14 (Tripwires)
**时间：** 约 60 分钟

## 问题

智能体执行一个操作。用户必须决定：批准与否。如果决定是即时的，那可能并非真正的审核。如果决定是结构化的，则速度慢但可信。工程问题在于如何使结构化审核成为阻力最小的路径。

2023 年的 HITL 模式是一个同步提示：“智能体想向 X 发送邮件，内容为 Y —— 批准吗？”用户点击“批准”。人人都觉得系统很安全。但实际上这种交互被严重橡皮图章化：用户快速批准，批准几乎无法预测任何问题，而当智能体出错时，审计轨迹显示一长串用户无法回忆起的批准记录。

2026 年的模式——提议-然后-提交——将 HITL 迁移到持久化基础之上，附加结构化元数据，并要求明确的提交。每个托管的智能体 SDK 都提供了一个版本：LangGraph 的 `interrupt()`、Microsoft Agent Framework 的 `RequestInfoEvent`、Cloudflare 的 `waitForApproval()`。API 名称不同，但模式相同。

## 概念

### 提议-然后-提交状态机

1. **提议。** 智能体生成一个提议的操作。持久化到持久化存储（PostgreSQL、Redis、Durable Object）中。包括：
   - 意图（智能体为何这样做）
   - 数据溯源（导致该提议的来源是什么）
   - 所触及权限（哪些作用域/文件/端点）
   - 影响范围（最坏情况是什么）
   - 回滚计划（如果提交了，如何撤销）
   - 幂等键（每个提议唯一；重复提交返回相同记录）
2. **展示。** 审核人看到包含所有元数据的提议。审核人是真人（而非智能体自我审核）。
3. **提交。** 明确确认。操作执行。
4. **验证。** 执行后，读取并确认副作用。如果验证步骤失败，系统进入已知的不良状态，并触发告警。

### 幂等键

没有幂等键，瞬态故障后的重试可能重复执行一个已批准的操作。具体例子：用户批准“从 A 向 B 转账 100 美元”。网络波动。工作流重试。用户只批准了一次，但转账执行了两次。幂等键将批准绑定到一个唯一的副作用上；第二次执行是无操作的。

这与 Stripe 和 AWS API 使用的幂等模式相同。Microsoft Agent Framework 文档明确将其用于智能体批准。

### 持久性：为什么批准可以跨越进程存活

批准等待室是一种智能体不拥有的状态。工作流被暂停（第 12 课）。当批准到达时，工作流从该点精确恢复。这就是为什么 LangGraph 将 `interrupt()` 与 PostgreSQL 检查点配对，而非仅使用内存状态——两天后到来的批准仍然能找到完整无损的工作流。

### 橡皮图章式批准与挑战-响应缓解措施

HITL 的默认 UI（“批准”/“拒绝”按钮）会产生快速批准，没有真正的审核。有记录的缓解措施：一个挑战-响应检查清单，要求在“批准”按钮启用前对特定问题给出肯定回答。具体形式：

- “您是否理解此操作涉及什么资源？[ ]”
- “您是否已验证影响范围是可接受的？[ ]”
- “如果此操作失败，您是否有回滚计划？[ ]”

这不是为了官僚主义而官僚主义——而是一种强制机制。无法勾选这些框的审核人要请求澄清（上报）或拒绝（安全默认）。Anthropic 的智能体安全研究明确将检查清单驱动的 HITL 列为橡皮图章式批准模式的缓解措施。

### 什么算作重要操作

并非每个操作都需要提议-然后-提交。2026 年的指导原则：

- **重要操作**（始终 HITL）：不可逆写入、金融交易、对外通信、生产数据库变更、破坏性文件系统操作。
- **可逆操作**（有时 HITL）：对本地文件的编辑、暂存环境更改、具有明确回滚的可逆写入。
- **读取与检查**（从不 HITL）：读取文件、列出资源、调用只读 API。

### 操作后验证

“提交已运行”并不等同于“副作用已发生”。网络分区和竞态条件可能导致工作流认为自己成功，但后端并未持久化。验证步骤在提交后重新读取目标资源以确认。这与使用 `RETURNING` 子句的数据库事务或 AWS `PutObject` 后的 `GetObject` 是相同的模式。

### 欧盟 AI 法案第 14 条

第 14 条强制要求对欧盟高风险 AI 系统进行有效的人类监督。“有效”并非装饰性。监管语言明确排除了橡皮图章模式。在 Microsoft Agent 治理工具包合规文档中，提议-然后-提交配合挑战-响应是能够通过第 14 条审查的模式。

## 使用它

`code/main.py` 使用标准库 Python 实现了一个提议-然后-提交状态机。持久化存储为 JSON 文件。幂等键是 (thread_id, action_signature) 的哈希值。驱动程序模拟了三种情况：干净的批准流程、瞬态故障后的重试（不能重复执行），以及橡皮图章默认流程与挑战-响应流程的对比。

## 交付它

`outputs/skill-hitl-design.md` 审查了一个拟议的 HITL 工作流，检查其是否具有提议-然后-提交模式，并标记缺失的元数据、幂等性、验证或挑战-响应层。

## 练习

1. 运行 `code/main.py`。确认对已批准提议的重试会使用持久化记录且不会重新执行。然后将幂等键改为包含时间戳，并展示重试会重复执行。

2. 为提议记录添加一个 `rollback` 字段。模拟一个验证步骤失败的执行。展示回滚会自动触发。

3. 阅读 Microsoft Agent Framework 的 `RequestInfoEvent` 文档。找出该 API 包含但玩具引擎缺少的一个元数据字段。添加它并解释它防御什么。

4. 为特定操作（例如“发布到公共 Twitter 账户”）设计一个挑战-响应检查清单。审核人必须回答哪三个问题？为什么是这三个？

5. 选择一种情况，其中同步的“批准？”提示就足够了（无需持久化存储）。解释原因，并说明你在接受哪类风险。

## 关键术语

| 术语 | 人们说的是 | 实际含义 |
|---|---|---|
| 提议-然后-提交 | “两阶段批准” | 持久化提议 + 明确提交 + 验证 |
| 幂等键 | “重试安全令牌” | 每个提议唯一；第二次执行时无操作 |
| 数据溯源 | “它从哪里来” | 导致该提议的特定源内容 |
| 影响范围 | “最坏情况” | 如果操作出错，影响的范围 |
| 橡皮图章 | “快速批准” | 点击“批准”但没有真正审核 |
| 挑战-响应 | “强制检查清单” | 审核人必须对特定问题做出肯定确认 |
| RequestInfoEvent | “微软智能体框架原语” | 带有结构化元数据的持久化 HITL 请求 |
| `interrupt()` / `waitForApproval()` | “框架原语” | LangGraph / Cloudflare 的等效模式 |
