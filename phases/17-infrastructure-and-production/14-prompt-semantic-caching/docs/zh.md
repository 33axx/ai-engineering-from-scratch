# 提示缓存与语义缓存经济学

> **定价快照日期：2026年4月。** 下文中的数值声明取自本课程发布时供应商的费率卡；在引用前请对照链接文档进行核实。

> 缓存发生在两个层面。L2（提供商级别）提示/前缀缓存复用重复前缀的注意力KV——Anthropic 的提示缓存文档宣称，对于长提示可降低高达 90% 的成本和 85% 的延迟；对于 Claude 3.5 Sonnet，缓存读取价格为 $0.30/M，而新鲜读取为 $3.00/M，TTL 为 5 分钟，1 小时 TTL 选项的写入溢价为 2 倍（docs.anthropic.com，2026-04）。OpenAI 提示缓存自动应用于 ≥1024 token 的提示，缓存输入价格大约是新鲜输入的 10% 折扣（platform.openai.com，2026-04）；每个模型的具体缓存费率取决于当时生效的费率卡。L1（应用级别）语义缓存在嵌入相似度命中时完全跳过 LLM。供应商所说的“95% 准确率”指的是匹配正确性，而非命中率——生产环境中报告的命中率范围从 10%（开放式聊天）到 70%（结构化 FAQ）；两方提供商均未发布官方基线，因此请将这些视为社区遥测数据而非保证。生产陷阱：并行化会破坏缓存（N 个并行请求在第一个缓存写入完成前发出，可能使花费增加数倍），且前缀内部的动态内容会完全阻止缓存命中。ProjectDiscovery 报告通过将动态文本移出可缓存前缀，命中率从 7% 提升到 74%（2025-11）。

## 学习目标

- 区分 L2 提示/前缀缓存（在提供商处复用 KV）与 L1 语义缓存（对相似提示绕过 LLM）。
- 解释 Anthropic 的 `cache_control` 显式标记以及两种 TTL 选项（5 分钟 vs 1 小时）及其价格乘数。
- 根据命中率、提示/响应混合比例和 token 价格计算预期的月度节省。
- 指出导致费用膨胀 5-10 倍的并行化反模式以及导致命中率暴跌的动态内容反模式。

## 问题

你在 RAG 服务中添加了提示缓存。账单保持不变。你测量了命中率；只有 7%。你的提示看起来是静态的，但实际上不是——系统提示包含格式精确到分钟的当前日期、一个请求 ID 以及用于多样性的随机化示例重排。每个请求都会写入一个新的缓存条目，读取零次。

另外，你的 agent 对每个用户问题执行十个并行工具调用。这十个调用都在第一个缓存写入完成之前到达提供商。十次写入，零次读取。你的账单是“启用缓存”后预期费用的 5-10 倍。

缓存是一种协议，而不是一个开关。两个层面，两种不同的故障模式。

## 概念

### L2 —— 提供商提示/前缀缓存

提供商存储可缓存前缀的注意力 KV，并在下一个匹配该前缀的请求中复用。你支付一次写入成本，读取几乎免费。

**Anthropic（Claude 3.5 / 3.7 / 4 系列）**：请求中显式使用 `cache_control` 标记。你标记哪些 block 是可缓存的。TTL：5 分钟（写入成本为基础价的 1.25 倍）或 1 小时（写入成本为基础价的 2 倍）。缓存读取：Claude 3.5 Sonnet 上为 $0.30/M，而新鲜读取为 $3.00/M —— 便宜 10 倍（docs.anthropic.com，截至 2026-04）。不同模型（Opus/Haiku 分别发布）费率不同；请始终对照实时定价页面进行交叉核对。

**OpenAI**：对于 ≥1024 token 的提示自动启用缓存（platform.openai.com，2026-04）。无需显式标记。在当前 gpt-4o/gpt-5 费率卡上，缓存输入大约比新鲜输入便宜 10 倍。文档和发布说明均未发布官方命中率基线；社区报告显示，通过精心设计提示，命中率集中在 30–60%。监控 `usage.cached_tokens` 以自行测量。

**Google（Gemini）**：通过显式 API 进行上下文缓存；1M token 上下文意味着缓存的收益更大。

**自托管（vLLM, SGLang）**：阶段 17 · 06 涵盖了 RadixAttention —— 在你自己的计算资源上使用相同的模式。

### L1 —— 应用级语义缓存

在调用 LLM 之前，先对提示进行哈希、嵌入，并查找相似的缓存请求（余弦相似度高于阈值，通常为 0.95+）。命中时返回缓存响应。未命中时调用 LLM 并缓存结果。

开源：Redis Vector Similarity、GPTCache、Qdrant。商业：Portkey Cache、Helicone Cache。

供应商的准确率声明指的是返回的缓存响应在语义上合适的频率——而不是命中率。生产命中率：

- 开放式聊天：10-15%。
- 结构化 FAQ / 支持：40-70%。
- 代码问题：20-30%（细微变化会破坏命中）。
- 重复提示的语音 agent：50-80%（语音归一化固定集合）。

### 并行化反模式

你的 agent 并行发出 10 个工具调用。这 10 个调用使用相同的 4K token 系统提示。Anthropic 的缓存写入是按请求进行的；第一次缓存写入在提供商看到提示后约 300 毫秒完成。请求 2-10 在同一毫秒窗口内到达，每个都看到缓存未命中。你支付了 10 次写入溢价，0 次读取折扣。

解决办法：使用“顺序优先”进行批处理——先单独发送请求 1，然后在请求 1 的缓存填充完毕后，再发送请求 2-10。这会给第一个工具调用增加 300 毫秒；但能将账单降低 5-10 倍。

### 动态内容反模式

你的系统提示如下所示：

```
You are a helpful assistant. The current time is 14:32:17.
User ID: abc123. Today is Tuesday...
```

每个请求都是唯一的。每个请求都会写入。零命中。

解决办法：将所有真正静态的内容移到可缓存前缀中；将动态内容附加到缓存边界之后：

```
[cacheable]
You are a helpful assistant. [rules, examples, instructions]
[/cacheable]
[dynamic, not cached]
Current time: 14:32:17. User: abc123.
```

ProjectDiscovery 通过这种方式将缓存命中率从 7% 提升到 74%，并公布了详细分析。

### 为夜间工作负载叠加批处理与缓存

批处理 API（阶段 17 · 15）在 24 小时周转时间内提供 50% 折扣。在此基础上叠加缓存输入，可获得约 10 倍的进一步节省。夜间分类、标注和报告生成工作负载，通过叠加使用，成本可降至同步非缓存成本的约 10%。

### 你应该记住的数字

定价数据点来自 2026-04 链接的供应商文档，并且每隔几个月就会变动——在依赖它们之前请重新核对。

- Anthropic 缓存读取：Claude 3.5 Sonnet 上 $0.30/M，大约比新鲜输入便宜 10 倍（docs.anthropic.com）。
- Anthropic 缓存写入溢价：1.25 倍（5 分钟 TTL）或 2 倍（1 小时 TTL）。
- OpenAI 自动缓存：适用于 ≥1024 token 的提示；根据当前费率卡，缓存输入价格约为新鲜输入的 10%（platform.openai.com）。
- 语义缓存命中率（社区报告）：~10% 开放式聊天；最高 ~70% 结构化 FAQ。非供应商记录的基线。
- ProjectDiscovery：通过将动态内容移出前缀，命中率从 7% 提升到 74%（项目博客，2025-11）。
- 并行化反模式：当 N 个并行请求错过第一次缓存写入时，通常报告账单膨胀 5-10 倍。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|------------|----------|
| L2 提示缓存 | "前缀缓存" | 提供商存储重复前缀的 KV |
| `cache_control` | "Anthropic 缓存标记" | 用于标记可缓存 block 的显式属性 |
| 缓存写入溢价 | "写入税" | 首次未命中到缓存写入的额外成本（1.25 倍或 2 倍） |
| L1 语义缓存 | "嵌入缓存" | 在调用 LLM 之前进行应用级哈希和嵌入 |
| GPTCache | "LLM 缓存库" | 流行的开源 L1 缓存库 |
| 缓存命中率 | "命中次数 / 总次数" | 从缓存中服务的请求占比 |
| 并行化反模式 | "N 次写入陷阱" | N 个并行请求导致 N 次缓存未命中 |
| 动态内容陷阱 | "提示中时间陷阱" | 前缀中的动态字节破坏命中率 |
| RadixAttention | "副本内缓存" | SGLang 的前缀缓存实现 |
