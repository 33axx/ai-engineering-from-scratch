# 影子流量、金丝雀发布和 LLM 渐进式部署

> LLM 发布融合了软件部署中最棘手的部分：没有单元测试、故障模式分散、信号延迟。顺序是：(1) 影子模式——将生产请求复制到候选模型，记录日志，进行比较，零用户影响；能捕获明显的分布问题，但不是质量保证；(2) 金丝雀发布——渐进式流量迁移 10% → 25% → 50% → 75% → 100%，每一步设置门控；跟踪延迟百分位数、每次请求成本、错误/拒绝率、输出长度分布、用户反馈率；(3) 当稳定性确认后进行 A/B 测试以比较不同的替代方案。非确定性是不可消除的——由于 GPU FP 非结合性以及批次大小差异，相同输入下不同运行之间准确率差异高达 15%。成本是一个变量，而非常量——一个性能提升 20% 的模型每次调用的成本可能是原来的 3 倍。回滚速度至关重要：如果回滚需要重新部署，你就太慢了。策略存在于配置/标志中；模型存在于带有固定摘要的注册表中；回滚 = 翻转策略 + 恢复阈值 + 在几秒内固定旧模型。

**类型：** 学习
**语言：** Python（标准库，玩具式金丝雀进度模拟器）
**前置要求：** 阶段 17 · 13（可观测性）、阶段 17 · 21（A/B 测试）
**时长：** ~60 分钟

## 学习目标

- 区分影子模式（零影响比较）、金丝雀（现场流量渐进）和 A/B（稳定性确认后的比较）。
- 列举五个 LLM 特有的金丝雀指标（延迟、每次请求成本、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么 LLM 的非确定性（高达 15%）改变了发布中“稳定”的定义。
- 设计一个以秒为单位（策略切换）而非小时（重新部署）的回滚路径。

## 问题

你发布了一个新模型。离线评估显示准确率提升 3%。你在生产中将其切换。24 小时内，成本上升 40%，用户踩率上升 8%，三个客户工单报告“奇怪的答案”。你回滚。重新部署需要 3 小时。你的周末毁了。

这一切都是可以避免的。影子模式会在任何用户看到之前捕获 40% 的成本飙升。金丝雀会在踩率变化时在 10% 处停止。策略标志回滚只需 30 秒。这套方法论填补了“离线评估看起来不错”与“真实用户满意”之间的差距。

## 概念

### 影子模式

候选模型接收与生产相同的请求；输出被记录日志，不返回给用户。零用户影响。记录：

- 输出内容（与生产的差异）。
- Token 数量（成本差异）。
- 延迟。
- 拒绝和错误。

捕获：成本激增、长度退化、明显的拒绝变化、硬错误。不捕获：用户能感知的质量差异。影子是冒烟测试，而非质量测试。

### 金丝雀发布

渐进式流量迁移，带有门控。典型进程：1% → 10% → 25% → 50% → 75% → 100%。每一步对 5 个指标进行门控：

1. **延迟百分位数** — P50、P95、P99。触发：金丝雀的 P99 超过基线的 1.5 倍。
2. **每次请求成本** — 综合平均值。触发：高于基线 20%。
3. **错误/拒绝率** — 5xx 加上明确拒绝。触发：基线的 2 倍。
4. **输出长度分布** — 平均值 + P99。触发：分布偏移。
5. **用户反馈率** — 踩率/工单提交率。触发：基线的 1.5 倍。

### 非确定性是新的方差

相同的输入产生非相同的输出。原因：

- GPU FP 非结合性（浮点归约顺序因批次而异）。
- 批次大小差异（相同提示在 128 批次 vs 16 批次中的处理不同）。
- 采样（温度 > 0）。

测量结果：在相同评估集上，不同运行之间准确率差异高达 15%。发布中的“稳定”意味着指标在预期方差范围内，而非与基线完全相同。将门控设置在噪声基底之上。

### 成本是一个变量

一个性能提升 20% 的模型每次调用的成本可能是原来的 3 倍。每次请求成本是五个门控之一。发布一个“更好”但破坏单位经济学的模型属于需要回滚的情况。

### 回滚是武器

- **策略标志**（特性标志系统）：在配置中翻转百分比；只需数秒。
- **模型固定**（注册表摘要）：固定后的模型不会自动升级。
- **回滚 = 恢复标志 + 设置固定摘要为上一个版本。** 数秒，而非数小时。

如果你的堆栈需要重新部署来回滚，请先修复这个问题再进行发布。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进式交付控制器。与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** — 服务网格级别的流量拆分。

**KServe / Seldon Core** — 模型服务，内置金丝雀功能。

**特性标志** — LaunchDarkly、Flagsmith、Unleash。策略级别切换，无需重新部署。

### 指标节奏

金丝雀门控每 5-15 分钟检查一次，具体取决于流量量。1% 流量，假设每分钟 10 个请求，每个窗口内可得到 50-150 个数据点——对于延迟来说足够，但对用户反馈来说噪声较大。10% 流量则大约有 10 倍数据。每个步骤应暂停足够长的时间，以在每个阶段积累足够的样本。

### A/B 步骤是可选的

如果新模型有明显不同（不同的行为、不同的成本曲线、不同的语气），则在金丝雀通过后在 50% 流量下进行 A/B 测试。如果只是改进版本，当金丝雀门控通过时直接跳到 100%。

### 需要记住的数字

- 金丝雀进程：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入下不同运行之间方差高达 15%。
- 五个金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本门控：高于基线 20% 视为触发。
- 回滚：数秒，而非数小时。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| 影子模式 | "复制到新模型" | 无影响的发送到候选模型进行日志记录 |
| 金丝雀 | "渐进式流量" | 逐步暴露给用户并带有门控的发布 |
| 门控 | "发布检查" | 阻止进展的指标阈值 |
| 非确定性 | "LLM 方差" | 不可消除的运行间差异 |
| 策略标志 | "标志翻转回滚" | 配置级别的回滚，秒级而非小时级 |
| 模型固定 | "注册表摘要" | 模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进式" | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 带有金丝雀原语的模型服务 |
| Istio 加权 | "网格拆分" | 服务网格流量拆分器 |
