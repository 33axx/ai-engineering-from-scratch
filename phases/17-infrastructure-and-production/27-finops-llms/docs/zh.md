# LLM 的 FinOps —— 单位经济学与多租户归因

> 传统 FinOps 在 LLM 支出上会失效。成本是代币交易（token-transactions），而非资源在线时长（resource-uptime）。标签无法映射 —— API 调用是一笔交易，而非一项资产。工程决策（提示设计、上下文窗口、输出长度）就是财务决策。2026 年的行动手册包含三个必须在第一天就埋点的归因维度：按用户（`user_id`）用于席位定价与扩展、按任务（`task_id` + `route`）用于产品面成本与优先级排序、按租户（`tenant_id`）用于单位经济学与续费。四个代币层 —— 提示（prompt）、工具（tool）、记忆（memory）、响应（response）—— 合在一个桶里会隐藏支出。多租户产品的执行阶梯（enforcement ladder）：每租户速率限制（2-3 倍预期峰值，明确返回 429 + retry-after）；每日支出上限（1.5-3 倍合同上限，触发速率收紧 + 告警）；支出 z 分数大于 4 时的终止开关（自动暂停 + 呼叫值班人员）。归因模式：标记与聚合、遥测关联器（trace-ID → 计费，精度最高）、采样与外推、基于模型的分配、事件溯源、实时流式处理。单位指标：每解决查询成本、每生成制品成本 —— 而非 $/M 代币。追溯式标记总是遗漏，应在请求创建时就进行埋点。

**类型：** 学习  
**语言：** Python（标准库，带终止开关的玩具级成本归因模拟器）  
**前置条件：** 阶段 17 · 13（可观测性），阶段 17 · 14（缓存）  
**时长：** 约 60 分钟

## 学习目标

- 解释为什么传统 FinOps（标签 + 层级）在 LLM 支出上会失效，并说出三个新的归因维度。
- 列举四个代币层（提示、工具、记忆、响应），并说明为什么单桶计费会隐藏支出。
- 为多租户产品设计一个执行阶梯（速率 → 支出上限 → 终止开关）。
- 选择单位指标（每解决查询成本 / 每制品成本）而非 $/M 代币。

## 问题所在

你的账单显示 40,000 美元。但你不知道：
- 哪个租户花了这笔钱。
- 哪个产品功能驱动了这笔支出。
- 是否有任何单个用户存在滥用行为。
- 是提示膨胀、工具调用还是记忆放大导致了问题。

供应商侧的标记与聚合方法适用于云资源（EC2、S3），因为标签会传播到账单条目。但 LLM API 调用不会自动打标签 —— 你必须在调用点手动添加 user/task/tenant 信息并传递下去。追溯式归因总是会遗漏边界情况。

## 概念

### 三个归因维度

**按用户**（`user_id`）：谁花了多少钱。驱动席位定价、扩展沟通、识别超级用户。

**按任务**（`task_id` + `route`）：哪个产品面花了多少钱。驱动功能优先级排序、决定关闭高成本功能。

**按租户**（`tenant_id`）：哪个客户有盈利。驱动单位经济学、续费定价、层级阈值。

从第一天起就在调用点埋入这三个维度。追溯式总是更差。

### 四个代币层

| 层 | 示例 | 占总量的典型百分比 |
|-----|---------|---------------------|
| 提示 | 系统提示 + 用户输入 | 40-60% |
| 工具 | 工具调用结果回传 | 20-40%（智能体工作负载）|
| 记忆 | 先前对话 / 检索的文档 | 10-30% |
| 响应 | 模型输出 | 10-30% |

将所有四个层合并为一个桶会使优化失去方向。在归因模式中要分开它们。

### 执行阶梯

1. **每租户速率限制**。2-3 倍预期峰值。返回 429 并附带 `Retry-After`。租户感到摩擦，账单不会意外。

2. **每租户每日支出上限**。1.5-3 倍合同上限。触发：收紧速率限制 + 通知客户成功团队。

3. **终止开关**：支出 z 分数大于 4（相对于租户基线）。自动暂停租户；呼叫值班人员；升级到运维 + 客户成功。

### 归因模式

- **标记与聚合**：在元数据头中打上标记；后续聚合。简单但粗略。
- **遥测关联器**：通过 trace ID 将追踪与计费关联。精度最高。成熟团队的做法。
- **采样 + 外推**：采样 5-10%，乘以系数。成本有效但粗略估算支出，会遗漏尾部。
- **基于模型的分配**：用回归推断成本驱动因素。适用于缺乏标记的历史数据。
- **事件溯源**：将成本作为事件放在流中（Kafka / Kinesis）。实时。
- **实时流式处理**：仪表盘亚秒级更新。

### 单位指标应该是“每 X 成本”

$/M 代币是供应商的行话。产品指标：

- 每解决支持工单的成本。
- 每生成文章的成本。
- 每成功智能体任务的成本。
- 每用户会话分钟的成本。

将成本与产品结果挂钩。否则优化就会失去锚点。

### 成本归因追踪结构

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都发送。存入数据湖。按维度聚合。阶段 17 · 13 的可观测性栈是存放这些数据的地方。

### 复合节约栈

栈：缓存 + 批处理 + 路由 + 网关。全部四个都启用时：
- 缓存 L2（阶段 17 · 14）：输入成本约降低 10 倍。
- 批处理（阶段 17 · 15）：节省 50%。
- 路由到廉价模型（阶段 17 · 16）：成本降低 60%。
- 网关效率（阶段 17 · 19）：冗余 + 重试。

最佳情况叠加：约为原始基线的 5-10%。大多数团队只启用了 2-3 个杠杆，很少有团队全部四个都用上。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个代币层：提示、工具、记忆、响应。
- 终止开关：支出 z 分数大于 4。
- 单位指标：每解决查询成本，而非 $/M 代币。
- 叠加优化：可实现基线的约 5-10%。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| 按用户归因 | "用户级成本" | 每次调用都带上 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品面 |
| 按租户归因 | "客户成本" | `tenant_id`；驱动单位经济学 |
| 四个代币层 | "成本层" | 提示 + 工具 + 记忆 + 响应 |
| 速率限制 | "429 防护" | 在网关上执行的每租户上限 |
| 每日支出上限 | "每日天花板" | 租户级别的预算与告警 |
| 终止开关 | "自动暂停" | 支出 z 分数 > 4 触发自动挂起 |
| 每解决成本 | "产品单位指标" | 成本与产品结果挂钩，而非代币 |
| 遥测关联器 | "追踪到计费" | 精度最高的归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复合节省至约 5-10% 基线 |
