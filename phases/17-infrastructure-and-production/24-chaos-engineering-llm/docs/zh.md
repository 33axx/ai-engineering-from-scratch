# 面向LLM生产环境的混沌工程

> LLM的混沌工程在2026年已自成一门学科。在生产环境运行实验前的前置条件：定义好的SLI/SLO、追踪+指标+日志可观测性、自动化回滚、运行手册、值班人员。架构包含四个平面：控制（实验调度器）、目标（服务、基础设施、数据存储）、安全（防护+中止+流量过滤）、可观测性（指标+追踪+日志）、反馈（反馈至SLO调整）。护栏是强制性的：燃烧率告警在每日错误预算消耗超过预期2倍时暂停实验；抑制窗口+追踪ID关联去重告警噪音。节奏：每周小型金丝雀+SLO评审；每月演练日+事后复盘；每季度跨团队韧性审计+依赖映射。LLM特定实验：内存过载、网络故障、供应商故障、畸形提示词、KV缓存驱逐风暴。工具：Harness混沌工程（LLM派生建议、爆炸半径缩减、MCP工具集成）；LitmusChaos（CNCF）；Chaos Mesh（CNCF Kubernetes原生）。

**类型：** 学习
**语言：** Python (stdlib, toy chaos experiment runner)
**前置要求：** 阶段 17 · 23（面向AI的SRE），阶段 17 · 13（可观测性）
**时长：** ~60分钟

## 学习目标

- 说出五个混沌工程前置条件（SLI/SLO、可观测性、回滚、运行手册、值班人员）并解释为何跳过任何一条都会导致实践失效。
- 绘制四个平面（控制、目标、安全、可观测性）及反馈到SLO的回路图。
- 列举五个LLM特定实验（内存过载、网络故障、供应商故障、畸形提示词、KV驱逐风暴）。
- 根据技术栈选择工具——Harness、LitmusChaos或Chaos Mesh。

## 问题

传统技术栈中的混沌测试已经成熟。LLM技术栈带来了新的故障模式。一个包含恶意字符的4K token提示词会导致分词器停滞12秒。上游供应商返回429；你的网关重试；你的服务因重试放大的并发而OOM。在突发负载下，KV缓存驱逐风暴导致重新预填充的级联效应，使计算资源饱和。

这些都不会出现在单元测试中。混沌工程让你在用户发现问题之前发现它们。

## 概念

### 前置条件

不要在生成环境中运行混沌测试，除非具备以下条件：

1. **SLI/SLO** ——已定义的服务等级指标和目标。
2. **可观测性** ——追踪、指标、日志，并连接到仪表盘。
3. **自动化回滚** ——阶段17·20的策略标记回滚。
4. **运行手册** ——结构化的，阶段17·23。
5. **值班人员** ——有人响应。

缺少任何一项，混沌实验就会变成真实的事故。

### 四个平面 + 反馈

**控制平面** ——实验调度器（Litmus工作流、Chaos Mesh调度、Harness UI）。

**目标平面** ——服务、Pod、节点、负载均衡器、数据存储。

**安全平面** ——紧急开关、抑制窗口、爆炸半径限制、错误预算门限。

**可观测性平面** ——常规指标 + 追踪ID关联，用于区分混沌引发与自然故障。

**反馈回路** ——发现结果反馈到SLO调整、运行手册更新、代码修复。

### 护栏是强制性的

- **燃烧率告警**：如果每日错误预算消耗超过预期的2倍，暂停实验。
- **抑制窗口**：实验期间，在爆炸半径内静默非实验告警。
- **追踪ID关联**：所有实验引发的错误携带标记，以便值班人员去重。

### 五个LLM特定实验

1. **内存过载** ——通过高并发发送长上下文请求，强制引发KV缓存抢占风暴。观察：服务是优雅地降级还是崩溃？

2. **网络故障** ——切断推理网关与供应商之间的连接。观察：故障转移是否在SLA内启动？（阶段17·19）

3. **供应商故障模拟** ——OpenAI 100%返回429。观察：路由是否切换到Anthropic？（阶段17·16，19）

4. **畸形提示词** ——注入导致分词器阻塞的负载（例如深层嵌套的Unicode、巨大的UTF-8码点）。观察：单个请求是否会导致工作进程卡死？

5. **KV驱逐风暴** ——通过饱和vLLM的块预算强制驱逐。观察：LMCache能否恢复，或者服务是否降级？

### 节奏

- **每周** ——在预发布环境执行小型金丝雀实验，可能5%的生产流量。
- **每月** ——针对特定场景安排演练日，跨团队参与，事后复盘。
- **每季度** ——跨团队韧性审计，更新依赖映射图。

### 工具

- **Harness Chaos Engineering** ——商业软件；基于AI的实验建议；爆炸半径缩减；MCP工具集成。
- **LitmusChaos** ——CNCF毕业项目；基于Kubernetes工作流。
- **Chaos Mesh** ——CNCF孵化项目；Kubernetes原生CRD风格。
- **Gremlin** ——商业软件；支持广泛。
- **AWS FIS** / **Azure Chaos Studio** ——托管的云服务。

### 从小处着手

第一个实验：在稳定流量下杀死一个解码副本的Pod。观察重新路由和恢复。如果一切正常且安全，再推进到网络混沌。

第一个LLM特定实验：向一个供应商注入持续5分钟的429错误。观察故障转移。大多数团队发现他们的故障转移并未经过充分测试。

### 应记住的数字

- 四个平面：控制、目标、安全、可观测性。
- 燃烧率暂停：每日预算消耗的2倍。
- 节奏：每周金丝雀，每月演练日，每季度审计。
- 五个LLM实验：内存、网络、供应商、畸形提示词、KV风暴。

## 关键术语

| 术语 | 通常称为 | 实际含义 |
|------|----------|----------|
| SLI / SLO | "服务目标" | 指标+目标；必要前置条件 |
| 爆炸半径 (Blast radius) | "范围" | 受实验影响的服务/用户集合 |

| 演练日 (Game day) | "月度演习" | 按计划进行的跨团队混沌演练 |
| LitmusChaos | "CNCF工作流" | CNCF毕业的Kubernetes混沌工具 |
| Chaos Mesh | "CNCF CRD" | CNCF孵化的Kubernetes原生混沌工具 |
| Harness CE | "商业AI辅助" | 具备AI建议的Harness混沌工程 |
