# 层次架构及其失效模式

> 层次结构即监督者嵌套。管理者智能体管辖子管理者，子管理者管辖工人。CrewAI 的 `Process.hierarchical` 是教科书式的实现：一个 `manager_llm` 动态分配任务并验证输出。LangGraph 的等价实现是 `create_supervisor(create_supervisor(...))`。当任务本身就是一个真实的组织架构图时，这是最自然的模式。但它也是最容易陷入管理者循环的模式——管理者智能体分配工作不当、误解子输出，或无法达成共识。顺序架构通常能胜出。

**类型：** 学习 + 构建  
**语言：** Python (stdlib)  
**前置条件：** 阶段 16 · 05（监督者模式）  
**时长：** ~60 分钟

## 问题

一旦理解了监督者模式，下一步自然就是“如果工人本身也是监督者会怎样？”团队下有子团队；公司下有部门的部门。层次架构正是这种结构的映射。

问题在于：LLM 管理者与人类管理者不同。人类管理者对其下属所知的内容有稳定的先验知识。LLM 管理者每一轮都会根据其上下文中的内容重新推理整个组织架构。上下文中微小的漂移，就会导致整个树形结构错误分配工作。

## 概念

### 结构形状

```
                 Manager
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       Sub-Mgr A         Sub-Mgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点负责规划、分配和综合。只有叶子节点执行实际工作。

### 优势所在

- **清晰的组织映射。** 如果实际任务是部门级的（“法务审核文档、财务审核文档、工程审核文档，然后为高管层总结”），那么层级结构是显式的。
- **局部摘要。** 每个子管理者在顶级管理者看到其团队输出之前，先进行摘要综合。顶级管理者看到的是三个子管理者的摘要，而不是十五个工人的输出。

### 失效之处

在 2026 年的复盘报告中反复发现的三种失效模式：

1.  **任务分配错误。** 管理者读取目标，虚构出一个分解方案，并将任务分配给错误的子管理者。由于子管理者会尽职尽责地处理被分配的任务，错误直到顶层综合时才暴露——比人类能够发现错误的位置晚了一个层级。
2.  **输出误解。** 子管理者返回“无法验证声明 X”。顶级管理者将其总结为“声明 X 未确认”。每个层级的意义都会发生漂移。
3.  **共识循环。** 两个子管理者意见不一致；顶级管理者要求他们协调；他们再次向下分配；工人重新运行；子管理者返回略有不同的答案；循环。CrewAI 的 `Process.hierarchical` 通过步骤限制来防止这种情况，但这个限制本身现在成了一个超参数。

### 决定性问题

顺序架构（线性流水线）与层次架构：你的任务是真的有独立的子团队，还是只是一个假装成树形结构的线性流程？如果是后者，使用顺序架构。如果是前者，使用层次架构，但要预先设定明确的协调规则。

### CrewAI 的实现

`Process.hierarchical` 将一个管理者 LLM 置于专业团队之上。管理者：

- 接收顶级任务，
- 将子任务分配给团队，
- 评估团队输出，
- 决定是接受、重新分配还是迭代。

文档：https://docs.crewai.com/en/introduction（在“核心概念”下查找“Hierarchical Process”）。

### LangGraph 的实现

LangGraph 使用嵌套的 `create_supervisor` 调用。内部监督者有自己的图；外部监督者将内部图视为一个不透明节点。这在调试方面比 CrewAI 更清晰（你可以分别逐步执行每个图），但难以表达树形结构的动态重塑。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 构建它

`code/main.py` 运行一个三级层次结构：

- 顶级管理者：将任务拆分为“工程”和“法务”分支，
- 工程子管理者：拆分为“前端”和“后端”工人，
- 法务子管理者：一个工人。

演示对比了顺利路径（所有人意见一致）与一个**扰动路径**，其中顶级管理者的分解错误地将“法务”标记为“财务”，并观察错误级联——子管理者尽职地做财务工作，顶层综合器报告财务发现，原始的法务问题未得到回答。

运行：

```
python3 code/main.py
```

输出会展示两个路径，并清晰对比“用户问的是什么”与“实际交付的是什么”。

## 使用它

`outputs/skill-hierarchy-fitness.md` 评估给定任务应使用层次架构、顺序架构还是扁平监督者模式。输入：任务描述、组织架构、协调预算。输出：模式推荐，以及需要防范的具体失效模式。

## 交付它

如果你交付层次架构：

- **将树深度限制为 2 层。** 三层已经会使大多数错误隐藏在可观测性之外。
- **明确的协调预算。** 设置顶级管理者必须提交前的最大轮数。通常为 2。
- **每次综合都要有来源追溯。** 每个节点的摘要必须引用生成它的是哪些叶子输出。
- **对分解漂移发出告警。** 记录每一步管理者的分解结果；与用户查询进行比对。如果分解结果不再覆盖用户查询，则发出告警。

## 练习

1. 运行 `code/main.py`，比较顺利路径与扰动路径。需要经过多少层管理者传递，顶级输出才会完全偏离用户的问题？
2. 添加第三层（顶级 → 子级 → 子-子级 → 工人）。测量随着深度增加，扰动路径自我纠正的频率与完全偏离的频率。
3. 在每个子管理者处实现一个“金丝雀”工人，它始终被问询原始用户问题（不变）。使用金丝雀的答案检测分解漂移。金丝雀与综合答案不一致时，管理者应如何反应？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。找出 CrewAI 应用的一个具体防护栏（步骤限制、manager_llm 约束），并描述它针对的是哪种失效模式。
5. 比较嵌套的 LangGraph 监督者与 CrewAI 层次架构。哪个更容易检测协调循环？

## 关键术语

| 术语 | 人们常说的意思 | 实际含义 |
|------|----------------|------------------------|
| 层次架构 | “组织架构图模式” | 监督者之上还有监督者；只有叶子节点执行工作。 |
| 管理者 LLM | “老板” | 在内部节点负责分解、分配和验证的 LLM。 |
| 分解漂移 | “老板搞丢了主线” | 顶级管理者的分解不再覆盖原始问题。 |
| 协调循环 | “无尽的会议” | 子管理者意见不一致；顶级重新分配；工人重新运行；循环直至预算耗尽。 |
| 深度-2 上限 | “不要超过 2 层深度” | 经验性防护栏：3 层及以上的深度会使可观测性崩溃。 |
| 金丝雀问题 | “每层都有地面真相” | 一个始终被问询原始查询（不变）的工人，用于检测漂移。 |
| 来源链 | “谁说了什么” | 从每次综合回溯到生成它的叶子输出的追踪。 |
