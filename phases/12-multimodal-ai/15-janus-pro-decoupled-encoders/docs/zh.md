# Janus-Pro：用于统一多模态模型的解耦编码器

> 统一多模态模型存在一个无法回避的矛盾。理解任务需要语义特征——SigLIP或DINOv2输出的向量富含概念级信息。生成任务需要易于重建的编码——能够干净地组合回清晰像素的VQ标记。这两个目标在单个编码器中无法兼容。Janus（DeepSeek，2024年10月）和Janus-Pro（DeepSeek，2025年1月）认为解决办法是停止尝试：将两个编码器解耦。在Transformer主体之间共享，但通过SigLIP路由理解任务，通过VQ分词器路由生成任务。在7B规模下，Janus-Pro在GenEval上超越了DALL-E 3，同时在MMMU上匹配LLaVA。本课将解读为什么两个编码器能在单个编码器失败的情况下奏效。

**类型：** 构建
**语言：** Python（标准库，双编码器路由 + 共享主体信号）
**前置课程：** 阶段12·13（Transfusion）、阶段12·14（Show-o）
**时长：** 约120分钟

## 学习目标

- 解释为什么单个共享编码器会损害理解或生成质量。
- 描述Janus-Pro的路由：输入侧使用SigLIP特征用于理解，输入和输出侧使用VQ标记用于生成。
- 追溯使Janus-Pro成功的（Janus未做到的）数据混合扩展。
- 比较解耦（Janus-Pro）、耦合连续（Transfusion）和耦合离散（Show-o）架构。

## 问题所在

统一模型在理解和生成任务之间共享一个Transformer主体。之前的尝试（Chameleon、Show-o、Transfusion）都使用一个视觉分词器处理两个方向。这个分词器是一种折衷：

- 针对重建（生成）优化：VQ-VAE捕捉精细的像素细节，但产生的标记语义连贯性弱。
- 针对语义（理解）优化：SigLIP嵌入将“猫”图像靠近“猫”标记群集，但不允许良好的重建。

Show-o和Transfusion为此付出了代价，在一个方向上出现了明显的质量损失。Janus-Pro问：当任务需求不同时，为什么要求使用同一个分词器？

## 概念

### 解耦视觉编码

Janus-Pro的架构将两个编码器分离：

- **理解路径。** 输入图像 → SigLIP-SO400m → 2层MLP → Transformer主体。
- **生成路径。** 输入图像（如果以现有图像为条件） → VQ分词器 → 标记ID → Transformer主体。
- **输出生成。** Transformer预测的图像标记 → VQ解码器 → 像素。

Transformer主体是共享的。主体上游和下游的所有部分都是任务特定的。

输入通过提示格式消除歧义：`<understand>`标签路由至SigLIP；`<generate>`路由至VQ。或者路由由任务隐含决定。

### 为何有效

理解损失获得SigLIP特征，这些特征经过CLIP式预训练调优以获得语义相似性。模型的感知基准测试优于Show-o / Transfusion，因为输入特征更适合任务。

生成损失获得VQ标记，分词器已针对重建进行了调优。图像质量优于Show-o，因为VQ码能干净地组合回像素。

共享的Transformer主体看到两种输入分布（SigLIP和VQ），并学会同时处理两者。主张是：足够的数据 + 足够的参数，主体能够吸收切换。

### 数据扩展——Janus vs Janus-Pro

Janus（原始版，arXiv 2410.13848）引入了解耦，但规模较小（1.3B参数，有限数据）。Janus-Pro（arXiv 2501.17811）进行了扩展：

- 7B参数（vs 1.3B）。
- 第一阶段（对齐）使用9000万图像-文本对，高于7200万。
- 第二阶段（统一）使用7200万对，高于2600万。
- 第三阶段增加了20万个图像生成指令样本。

结果：Janus-Pro-7B在MMMU上匹配LLaVA（60.3 vs ~58），在GenEval上击败DALL-E 3（0.80 vs 0.67）。一个开放模型，在统一频谱的两侧都具有竞争力。

### JanusFlow——整流流变体

JanusFlow（arXiv 2411.07975）将VQ生成路径替换为整流流生成路径（连续）。拆分变为 SigLIP用于理解 + 整流流用于生成。质量上限进一步提高。架构仍然是解耦编码器-共享主体。

### 共享主体的工作

Transformer主体处理统一序列，但有两个输入分布。其工作是：

- 对于理解：消耗SigLIP特征 + 文本标记 → 自回归生成文本。
- 对于生成：消耗文本标记 +（可选的图像VQ标记）→ 自回归生成图像VQ标记。

主体没有每个块的模态特定权重。它是你在Qwen或Llama中会找到的文本样式Transformer，再加上两个输入适配器。

有趣的是，这意味着Janus-Pro的主体可以从预训练的LLM初始化。Janus-Pro确实从DeepSeek-MoE-7B初始化。这个选择很重要：LLM贡献了从零开始的统一模型难以达到的推理能力。

### 与InternVL-U的比较

InternVL-U（课程12.10）是2026年的后续版本。它结合了：

- 原生多模态预训练（InternVL3骨干）。
- 解耦编码器路由（输入SigLIP，输出VQ + 扩散头）。
- 统一的理解 + 生成 + 编辑。

InternVL-U将Janus-Pro的架构选择吸收到一个更大的框架中。解耦编码器思想现已成为大规模统一模型的默认方案。

### 局限性

解耦编码器增加了架构复杂性。需要训练两个分词器，维护两条输入路径，存在两组故障模式。对于不需要生成功能的产品，Janus-Pro过于工程化——可以选择LLaVA系列的理解模型。

对于不需要理解功能的产品，Janus-Pro大材小用——可以选择Stable Diffusion 3 / Flux模型。

对于两者都需要的产品，Janus-Pro现在是参考的开放架构。

## 使用它

`code/main.py`模拟了Janus-Pro路由：

- 两个模拟编码器：类似SigLIP（产生256维语义向量）和类似VQ（产生整数编码）。
- 一个根据任务标签选择编码器的提示路由器。
- 一个共享主体（占位），处理来自任何编码器产生的标记序列。
- 从第一阶段（对齐）到第三阶段（指令微调）的加权采样计划切换。

为3个示例打印路由路径：图像问答、文生图、图像编辑。

## 练习

1. Janus-Pro-7B在GenEval上击败了DALL-E 3。解释为什么一个7B的开放模型在生成上可以匹敌前沿专有模型，但在理解上却不能。

2. 实现一个路由器函数：给定提示文本，分类为`understand`或`generate`。如何处理像“描述然后画出来”这样的模糊提示？

3. JanusFlow用整流流替换了VQ路径。现在Transformer主体输出什么？损失函数有什么变化？

4. 设想Janus-Pro架构可以通过增加一个解耦编码器来处理第四种任务。例如：图像分割（DINO风格）、深度估计（MiDaS风格）。

5. 阅读Janus-Pro第4.2节关于数据扩展的内容。与Janus相比，哪个数据阶段对文生图质量的提升贡献最大？

## 关键术语

| 术语 | 人们常说 | 实际含义 |
|------|----------|----------|
| 解耦编码 | “两个视觉编码器” | 每个方向使用独立的分词器或编码器：语义用于理解，重建用于生成 |
| 共享主体 | “一个Transformer” | 单个Transformer处理任一编码器的输出；没有模态特定权重 |
| SigLIP用于理解 | “语义特征” | CLIP家族视觉塔，提供丰富的概念特征但重建能力差 |
| VQ用于生成 | “重建编码” | 向量量化标记，能干净地解码回像素 |
| JanusFlow | “整流流变体” | Janus-Pro将VQ替换为连续流匹配生成头 |
| 路由标签 | “任务标签” | 提示标记（`<understand>` / `<generate>`），用于选择输入编码器 |
