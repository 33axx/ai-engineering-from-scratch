# vLLM 服务内部原理：PagedAttention、连续批处理、分块预填充

> vLLM 在 2026 年的主导地位并非依靠单个技巧，而是三个默认机制协同作用。PagedAttention 始终开启。连续批处理在解码迭代之间将新请求注入活跃批次。分块预填充将长提示词切分，使解码令牌永远不会因等待而停滞。同时开启这三个机制后，在一张 H100 SXM5 上运行 Llama 3.3 70B FP8，当并发数为 128 时，吞吐量可达 2,200-2,400 tok/s——比 vLLM 自身的默认值高出约 25%，是朴素 PyTorch 循环的 3-4 倍。本节课将从可绘制图表的深度讲解调度器和注意力内核，最后在 `code/main.py` 中实现一个玩具级连续批处理器，按照 vLLM 的方式调度预填充和解码。

## 问题

一个朴素的 PyTorch 服务循环一次只运行一个请求：分词、预填充、解码直到 EOS，返回。对于一个用户，这没问题。但对于一百个用户，这就是一个排队的耐心队列。常用的修复方案——静态批处理——将每个请求填充到窗口中最长提示词的长度，每个解码填充到期望的最长输出长度，并且整个批次会因为最慢的序列而停滞。你为从未使用的填充付出了代价，快速请求等待慢速请求。

vLLM 一次性解决了三个问题。PagedAttention 阻止了 KV 缓存碎片化，这种碎片化在经典连续分配方式下会吃掉 60-80% 的 GPU 内存。连续批处理允许请求在每次解码迭代之间加入和离开批次，因此批次始终满载着实际工作。分块预填充将一个 32k 令牌的提示词分解成约 512 令牌的片段，与解码交错执行，因此长提示词不会让 GPU 上的所有解码令牌陷入冻结。

2026 年的生产默认设置是三者全部开启。你需要理解每个机制的作用，因为失败模式都出在调度器上，而不是模型上。

## 概念

### PagedAttention 作为虚拟内存系统

KV 缓存的大小为 `num_layers × 2 × num_heads × head_dim × seq_len × bytes_per_element` 每个序列。对于 Llama 3.3 70B 在 8192 令牌长度下，BF16 格式大约为每个序列 1.25 GB。如果为每个请求预保留 8192 个槽位，但平均请求只使用 1500 个令牌，那么你浪费了约 82% 的 HBM。经典批处理要承担这种浪费。

PagedAttention 借用了操作系统虚拟内存的思想。KV 缓存并非按序列连续存储。它被分配为固定大小的块（默认 16 个令牌）。每个序列有一个块表，将其逻辑令牌位置映射到物理块 ID。当一个序列增长超过已分配的块时，会添加一个块。当序列结束时，其块返还给池。

碎片率从 60-80%（经典方式）降至 4% 以下（PagedAttention）。你无需通过标志启用 PagedAttention——它是 vLLM 唯一自带的分配器。可调节参数是 `--gpu-memory-utilization`（默认值 0.9），它告诉 vLLM 在加载权重和激活后，有多少 HBM 可以保留给 KV 块。

### 迭代级别的连续批处理

旧的“动态批处理”会等待一个窗口（例如 10 毫秒）来填满一个批次，然后运行预填充 + 解码 + 解码 + 解码直到所有序列结束。快速序列提前离开，然后在 GPU 完成慢速序列时空闲。

连续批处理在每次解码步骤之间进行操作。将正在运行的序列集合称为 `RUNNING` 列表。在每次迭代中：

1. 从 `RUNNING` 中移除任何刚达到 EOS 或 max_tokens 的序列。
2. 调度器查看等待队列。如果有空闲的 KV 块，它接纳新序列（预填充或恢复）。
3. 前向传播在当前的 `RUNNING` 集合上执行，每个序列生成一个新令牌。

批次大小永远不会填充到固定数量。处于不同输出位置的序列共享一个融合的前向传播。在 2026 年的 vLLM 中，这被称为 `V1 调度器`。关键不变量：调度器每次解码迭代运行一次，而不是每次请求一次。

### 分块预填充保护 TTFT 尾部延迟

预填充是计算密集型的。Llama 3.3 70B 在一个 H100 上处理 32k 令牌的提示词大约需要 800 毫秒的纯预填充。当预填充运行时，批次中其他每个序列的解码令牌都在等待。在服务循环中，一个长提示词的首令牌延迟（TTFT）变成了其他数十个用户的令牌间延迟（ITL）波动。

分块预填充将预填充拆分成固定大小的块（默认 512 个令牌），并将每个块作为一个单元调度。块之间，调度器可以为解码序列前进一个令牌。这用每块几个毫秒的绝对预填充延迟增加，换来了更低的解码时间抖动。在已发表的基准测试中，混合负载下的 P99 ITL 从约 50 毫秒降至约 15 毫秒。

### 三个默认机制相互依赖

这三个功能彼此假设。PagedAttention 为调度器提供了一个细粒度的 KV 资源用于交易。连续批处理需要这种细粒度资源，以便接纳新序列不会导致全局重排。分块预填充是调度器在同一个 `RUNNING` 列表上做出的决策——它只是一个额外的调度策略，而非独立系统。

你不需要记住每个标志。你需要知道调度器优化的目标：在 KV 块预算约束下，结合分块预填充，最大化有效吞吐量。

### 2026 v0.18.0 的陷阱

在 vLLM v0.18.0 中，你不能将 `--enable-chunked-prefill` 与草稿模型推测解码（`--speculative-model`）结合使用。文档记录的例外是 V1 调度器中的 N-gram GPU 推测解码。团队如果未阅读发布说明就开启所有标志，会在启动时遇到运行时错误，而非软性性能下降。如果你认为推测解码带来的收益值得启用分块预填充，则需要重新评估——2026 年的正确答案通常是 EAGLE-3 搭配无分块预填充，而不是一个无法编译的“草稿模型加分块预填充”。

### 你应该记住的数据

- Llama 3.3 70B FP8, H100 SXM5, 128 并发，三个机制全部开启：2,200-2,400 tok/s。
- 相同模型，默认 vLLM（无分块预填充）：约 1,800 tok/s。
- 相同模型，朴素 PyTorch 前向循环：约 600 tok/s。
- 生产负载下 PagedAttention 的 KV 碎片浪费：<4%。
- 混合负载下的 P99 ITL：有分块预填充约 15 ms，无分块预填充约 50 ms。

### 调度器长什么样

```python
# 伪代码：迭代级别调度
while True:
    # 1. 从 RUNNING 中移除已完成序列
    for seq in RUNNING:
        if seq.finished:
            free_blocks(seq.block_table)
            RUNNING.remove(seq)

    # 2. 从等待队列中接纳新序列（如果 KV 块足够）
    while WAITING and free_blocks_available():
        seq = WAITING.pop(0)
        allocate_blocks(seq, for_prefill=True)
        RUNNING.append(seq)

    # 3. 执行一个前向步骤
    # 如果启用了分块预填充，预填充序列只处理一个块的大小
    # 解码序列总是生成一个令牌
    for seq in RUNNING:
        if seq.is_prefill:
            tokens = seq.next_chunk() if chunked_prefill else seq.all_tokens()
        else:
            tokens = seq.last_token()
        logits = model(tokens, seq.block_table)
        next_tokens = sample(logits)
        seq.append(next_tokens)

    # 4. 更新块表（如果需要扩展）
    for seq in RUNNING:
        if seq.needs_new_block():
            allocate_new_block(seq)
```

`code/main.py` 正是使用标准库 Python 实现的这个循环，包含虚拟令牌计数和虚拟前向延迟。运行它可以看到在长预填充过程中分块预填充如何保持解码序列的活跃。

## 使用它

`code/main.py` 模拟了一个 vLLM 风格的调度器，支持可选功能。运行以观察：

- `NAIVE` 模式：一次只处理一个请求，无批处理。
- `STATIC` 模式：填充并等待，经典批处理。
- `CONTINUOUS` 模式：迭代级别的接纳和释放。
- `CONTINUOUS + CHUNKED` 模式：预填充片段与解码交错。

输出显示总吞吐量（虚拟秒内令牌数）、TTFT 均值、P99 ITL。`CONTINUOUS + CHUNKED` 行应在混合流量中占据主导。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|------------|----------|
| PagedAttention | “那个 KV 技巧” | KV 缓存的固定大小块分配器；碎片率 <4% |
| 块表 | “页表” | 每个序列从逻辑令牌位置到物理 KV 块的映射 |
| 连续批处理 | “动态批处理，但更正确” | 每次解码迭代做出接纳/释放决策 |
| 分块预填充 | “预填充拆分” | 将长预填充拆分为 512 令牌片段，与解码交错 |
| TTFT | “首令牌时间” | 预填充 + 队列 + 网络；长提示词下主要受预填充影响 |
| ITL | “令牌间延迟” | 连续解码令牌之间的时间；主要受批大小影响 |
| 有效吞吐量 | “满足 SLO 的吞吐量” | 每秒令牌数，且所有请求仍满足 TTFT 和 ITL 目标 |
| V1 调度器 | “新调度器” | vLLM 的 2026 调度器；N-gram 推测解码是与分块预填充兼容的路径 |
| `--gpu-memory-utilization` | “内存旋钮” | HBM 中用于 KV 块（加载权重和激活之后）的比例 |
