# 工具使用与函数调用

> Toolformer（Schick 等人，2023）开创了自监督工具标注方法。伯克利函数调用排行榜 V4（Patil 等人，2025）设定了 2026 年的标准：40% 智能体、30% 多轮、10% 实时、10% 非实时、10% 幻觉检测。单轮问题已解决。记忆、动态决策和长链工具使用尚未解决。

**类型：** 构建
**语言：** Python（标准库）
**前置知识：** 第 14 阶段 · 01（智能体循环），第 13 阶段 · 01（函数调用深入探讨）
**时长：** 约 60 分钟

## 学习目标

- 解释 Toolformer 自监督训练信号：仅在工具执行能降低下一个 token 损失时保留工具标注。
- 列举 BFCL V4 的五个评估类别及各类别衡量的内容。
- 实现一个带有模式验证、参数强制类型转换和执行沙箱的标准库工具注册表。
- 诊断 2026 年的三大未解决问题：长链工具调用、动态决策和记忆。

## 问题背景

早期的工具使用问题在于：模型能否预测出正确的函数调用？现代工具使用问题则变为：模型能否在 40 个步骤内串联工具，具备记忆、部分可观测性、从工具故障中恢复的能力，并且不幻觉出不存在的工具？

Toolformer 建立了基线：模型可以通过自监督学习在何时调用工具。BFCL V4 定义了 2026 年的评估目标。两者之间的差距正是生产级智能体所处的空间。

## 概念

### Toolformer（Schick 等人，NeurIPS 2023）

核心思想：让模型用自己的预训练语料库来标注候选 API 调用。对于每个候选，执行它。仅当包含工具结果能降低下一个 token 的损失时，才保留该标注。在过滤后的语料库上进行微调。

涵盖的工具：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号纯粹取决于工具是否有助于预测文本——无需人工标注。

规模效应：工具使用随着模型规模扩大而出现。较小模型从工具标注中受损；较大模型则从中获益。这就是为什么 2026 年的前沿模型内置了强大的工具使用能力，而大多数 7B 模型需要显式的工具使用微调才能变得可靠。

### 伯克利函数调用排行榜 V4（Patil 等人，ICML 2025）

BFCL 是 2026 年事实上的评估标准。V4 的组成如下：

- **智能体（40%）**——完整的智能体轨迹：记忆、多轮、动态决策。
- **多轮（30%）**——带有工具链的交互式对话。
- **实时（10%）**——用户提交的真实提示（分布更困难）。
- **非实时（10%）**——合成测试用例。
- **幻觉检测（10%）**——检测何时不应调用任何工具。

V3 引入了基于状态的评估：执行一系列工具后，检查 API 的实际状态（例如“文件是否已创建？”），而不是匹配工具调用的抽象语法树。V4 增加了网络搜索、记忆和格式敏感性类别。

2026 年的关键发现：单轮函数调用已基本解决。失败主要集中在记忆（跨轮次传递上下文）、动态决策（根据先前结果选择工具）、长链（超过 20 步后出现漂移）以及幻觉检测（当没有合适的工具时拒绝调用）。

### 工具模式

每个提供商都有自己的模式。它们在细节上有所不同，但具有相同的形状：

```json
{
  "name": "get_weather",
  "description": "获取指定城市当前的天气",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string"}
    },
    "required": ["city"]
  }
}
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。两者都接受 JSON Schema。描述性文字至关重要——模型通过它们来选择正确的工具。糟糕的工具描述是导致“选错工具”失败的首要原因。

### 参数验证

不要信任任何工具调用。进行以下验证：

1. **类型强制转换。** 模型可能返回字符串 `"5"`，而模式规定为整数。如果转换明确则进行强制转换；否则拒绝。
2. **枚举验证。** 如果模式规定 `status in {"open", "closed"}`，但模型输出了 `"in_progress"`，则应拒绝并提供描述性错误。
3. **必填字段。** 缺失必填字段 → 立即向模型返回带描述的错误观察，而不是崩溃。
4. **格式验证。** 日期、电子邮件、URL——使用具体解析器进行验证，而不是正则表达式。

每次验证失败都应返回结构化的观察结果，以便模型能够以正确的格式重试。

### 并行工具调用

现代提供商支持在一次助手轮次中进行并行工具调用。循环如下：

1. 模型发出 3 个带有不同 `tool_use_id` 的工具调用。
2. 运行时执行它们（如果互相独立则并行执行）。
3. 每个结果通过 `tool_use_id` 关联，作为 `tool_result` 块返回。

工程原则：将关联 ID 视为关键。交换它们会导致工具与结果匹配错误。

### 沙箱化

工具执行是沙箱的边界。详见第 09 课。简而言之：每个工具应指定读/写范围、网络访问权限、超时时间和内存上限。通用的 `run_shell(cmd)` 是一个危险信号；具体的 `git_status()` 更安全。

## 动手构建

`code/main.py` 实现了一个生产级工具注册表：

- JSON Schema 子集验证器（仅使用标准库）。
- 工具注册，包含描述、输入模式、超时和执行器。
- 参数强制类型转换和枚举验证。
- 带有关联 ID 的并行工具调度。
- 将错误观察作为结构化的字符串返回。

运行它：

```bash
python code/main.py
```

追踪输出显示一个迷你智能体在一次轮次中调用了三个工具，其中一个故意格式错误，被拒绝并返回了描述性错误，模型可据此采取行动。

## 如何使用

每个提供商都有自己的工具模式——Anthropic、OpenAI、Gemini、Bedrock。如果需要支持多提供商，请使用一个转换层（OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器）。BFCL 是参考基准——如果工具使用是产品的核心，那么在发布之前用 BFCL 测试你的智能体。

## 交付内容

`outputs/skill-tool-registry.md` 为给定的任务领域生成一个工具目录、模式和注册表。包含描述质量检查（每个工具的描述是否告诉模型何时使用它？）。

## 练习

1. 添加一个“无操作”工具，让模型明确拒绝使用任何其他工具。在类似 BFCL 的幻觉测试上进行评估。
2. 实现整数作为字符串和浮点数作为字符串的参数强制类型转换。强制转换在什么时候开始掩盖真正的 bug？
3. 为每个工具添加超时和断路器（连续失败 3 次后，60 秒内拒绝该工具）。这会对模型的恢复方式产生什么影响？
4. 阅读 BFCL V4 描述。选择一个类别（例如“多轮”），并通过你的智能体运行 10 个示例提示。报告通过率。
5. 将标准库验证器移植到 Pydantic 或 Zod。Pydantic/Zod 发现了哪些被这个简易实现遗漏的问题？

## 关键术语

| 术语 | 人们常说的含义 | 实际含义 |
|------|----------------|------------------------|
| 函数调用（Function calling） | “工具使用” | 带有验证模式的结构化输出工具调用 |
| Toolformer | “自监督工具标注” | Schick 2023 —— 保留那些结果能降低下一个 token 损失的工具调用 |
| BFCL | “伯克利函数调用排行榜” | 2026 基准：40% 智能体、30% 多轮、10% 实时、10% 非实时、10% 幻觉检测 |
| 工具模式（Tool schema） | “模型的函数签名” | 名称、描述、参数的 JSON Schema |
| tool_use_id | “关联 ID” | 将工具调用与其结果关联；对于并行调度至关重要 |
| 幻觉检测（Hallucination detection） | “知道何时不调用” | V4 类别：当没有合适的工具时拒绝调用 |
| 参数强制类型转换（Argument coercion） | “字符串到整数的修复” | 对可预测的模式不匹配进行窄修复；不明确时拒绝 |
| 沙箱化（Sandboxing） | “工具执行边界” | 每个工具的读/写范围、网络、超时、内存上限 |
