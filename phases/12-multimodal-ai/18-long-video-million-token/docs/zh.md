# 百万Token上下文中的长视频理解

> 一个1小时的4K视频，以24 FPS抽取帧、分块并嵌入后，会产生大约6000万个Token。一个2小时的播客节目转录文本是30,000个Token。一部完整的蓝光故事片，即使经过激进池化压缩，也有数十万个Token。Google的Gemini 1.5（2024年3月）以1000万Token的上下文开创了新时代，能够对长达1小时的视频实现可靠的大海捞针召回。LWM（Liu等人，2024年2月）展示了环形注意力的扩展路径。LongVILA和Video-XL进一步扩展了输入规模。VideoAgent则将原始上下文替换为智能体检索。每种方法在计算量、召回率和工程复杂度上做出了不同的权衡。本课程将逐一解读。

**类型：** 构建  
**语言：** Python（标准库，大海捞针模拟器 + 智能体检索路由器）  
**先决条件：** 阶段12 · 17（视频时间Token）  
**时间：** 约180分钟

## 学习目标

- 计算长视频在不同FPS和池化下的总视觉Token数量。
- 解释三种扩展路径：暴力上下文（Gemini 1.5）、环形注意力（LWM）、Token压缩（LongVILA / Video-XL）。
- 比较原始上下文视频VLM与智能体检索视频VLM（VideoAgent）在准确性和延迟上的差异。
- 设计一个针对30分钟视频的大海捞针测试，并测量特定分钟处的召回率。

## 问题

Qwen2.5-VL尺寸的块在384原生分辨率下，每帧约729个Token。经过3x3池化后，每帧81个Token。一个30分钟的片段以1 FPS抽取 = 1800帧 = 145,800个Token。到2025年，开放的VLM可以做到，但空间紧张。如果以2 FPS抽取，则为291,600个Token——只有最大的上下文能够容纳。

一部2小时的电影以1 FPS抽取是583k Token。超出大多数2026年开放模型的能力；需要Gemini 2.5 Pro或更激进的池化。

出现了三种扩展路径。

## 概念

### 路径1：暴力上下文（Gemini 1.5, Claude Opus）

用硬件解决问题。将上下文扩展到数百万个Token，在一次前向传播中处理所有内容。

Gemini 1.5 Pro推出时有1M Token；Gemini 1.5 Ultra达到10M；2026年的Gemini 2.5 Pro可以可靠地处理数小时的视频。论文（arXiv:2403.05530）记录了在约950万Token内达到99.7%的大海捞针召回率。

工程实现：定制的注意力机制，采用内存层次结构（局部 + 全局 + 稀疏）以及MoE专家路由，以提升长上下文效率。未公开全部细节。非开源。

### 路径2：环形注意力（LWM, LongVILA）

环形注意力将长序列分布在一个“环”中的多个设备上，每个设备持有一个块。跨全序列的注意力通过每个设备将其块发送给环中的下一个设备来实现，计算部分注意力并聚合。

LWM（Liu等人，2024）以这种方式训练了一个1M上下文模型。训练计算量随上下文线性增长，而非二次增长——注意力的二次开销被环中设备分摊。

LongVILA（arXiv:2408.10188）将此模式适配到VLM。1400帧视频，每帧192个Token = 268k上下文，使用环形注意力在8路并行下训练。

### 路径3：Token压缩（Video-XL, LongVA）

比暴力上下文更便宜：在LLM看到序列之前进行激进压缩。

Video-XL（arXiv:2409.14485）使用视觉摘要Token：每个N帧的剪辑产生一个“摘要”Token，该Token关注这N帧。在推理时，LLM每个剪辑只看到一个摘要Token，大幅缩小上下文。

LongVA通过“长上下文迁移”技术将LLM上下文从200k扩展到2M。在长上下文文本上训练，通过共享表示迁移到长上下文视频。

Token压缩在特定时间戳的召回率与可扩展性之间进行权衡。模型大致知道发生了什么，但有时会错过精确帧。

### 路径4：智能体检索（VideoAgent）

不将完整视频喂给LLM。而是将视频视为一个数据库，让LLM来查询它。

VideoAgent（arXiv:2403.10517）：
1. LLM读取问题。
2. LLM向检索工具请求相关剪辑（“显示包含猫的片段”）。
3. 工具返回匹配的剪辑时间戳。
4. LLM通过VLM读取这些剪辑。
5. LLM组织答案或提出后续查询。

这是将LLM作为智能体的模式应用于长视频。推理成本更低（只编码相关剪辑），但工程难度更大（检索质量成为瓶颈）。

### 大海捞针基准测试

标准的长上下文测试：在视频中随机位置插入一个独特的视觉或文本标记，然后提出一个需要回忆该标记的问题。

指标：在不同视频长度和标记位置上的Recall@k。

Gemini 2.5 Pro在长达90分钟的视频上召回率>99%。开放的72B模型（Qwen2.5-VL-72B, InternVL3-78B）在30分钟时得分约85-90%，超过60分钟后下降。

VideoAgent在2小时以上的视频中可以匹配或超越原始上下文模型，因为如果检索工具足够好，它能够找到“针”。

### 如何选择路径

对于15分钟的片段且追求前沿精度：开放的72B + 原生上下文通常可行。选择Qwen2.5-VL-72B。

对于30分钟到1小时的内容：开源方面使用LongVILA或Video-XL；闭源方面使用Gemini 2.5 Pro。质量要求高时选择闭源前沿模型。

对于2小时以上的内容：采用VideoAgent或类似的检索模式。或者，将视频摘要为较小的片段，然后输入分层摘要。

### 2026年生产模式

在实践中，生产级长视频处理流水线是混合式的：
1. 对整段视频应用动态FPS采样 + 激进池化（得到一个约100k Token的全局表示）。
2. 将全局表示输入一个72B VLM，生成全局摘要。
3. 如果用户提出细节问题，则使用该摘要作为索引运行智能体检索。

这种做法结合了暴力上下文用于全局理解，以及检索用于局部细节。

## 使用它

`code/main.py`：
- 计算从1分钟到3小时的视频在不同FPS + 池化下的Token预算。
- 模拟一次大海捞针运行：在随机时间戳注入标记，提出问题，评分召回率。
- 包含一个智能体检索路由器模拟器，该路由器选择特定剪辑提供给下游VLM。

运行预算表，感受规模差距。

## 交付

本课程生成了`outputs/skill-long-video-strategy-planner.md`。给定视频时长和查询复杂度，该文件会在暴力上下文、压缩和智能体检索之间进行选择，并计算延迟和质量预期。

## 练习

1. 一个45分钟的讲座，以1 FPS抽取，每帧81个Token。总Token数是多少？能适用于哪些模型的上文？
2. 设计一个大海捞针测试：你在哪一分钟注入标记？确切的查询格式是什么？
3. 比较暴力上下文Qwen2.5-VL-72B（80k上下文）与VideoAgent（Claude 3.5 + 检索）在1小时视频上的表现。哪个在召回率上胜出？哪个在延迟上胜出？
4. 环形注意力的内存成本在序列长度上线性增长，在设备数量上也线性增长。解释原因，以及如果跳过环旋转阶段会发生什么失败。
5. 阅读Gemini 1.5论文第5节关于大海捞针的内容。论文发现了在1M与10M Token边界上召回率的什么情况？

## 关键术语

| 术语 | 人们常说的意思 | 实际含义 |
|------|----------------|----------|
| 暴力上下文 | “就多加些Token” | 将LLM上下文扩展到数百万个Token；一次处理所有内容 |
| 环形注意力 | “LWM风格并行” | 分布式注意力模式，每个设备持有一个块并旋转 |
| Token压缩 | “摘要Token” | 在送入LLM之前，通过学习的压缩器减少每剪辑Token数 |
| 大海捞针 | “NIH测试” | 在随机点插入唯一标记，测试时要求模型回忆它 |
| 智能体检索 | “LLM作为查询规划器” | LLM向检索工具请求相关剪辑，通过VLM读取，组织答案 |
| VideoAgent | “视频的检索模式” | 经典的智能体检索设计：问题 -> 工具 -> 剪辑 -> 答案 |
