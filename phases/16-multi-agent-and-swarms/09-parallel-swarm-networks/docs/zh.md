# 并行 / 群集 / 网络化架构

> 与监督者的对比：没有中央决策者。智能体读取共享事件总线，异步领取任务，将结果写回。LangGraph 明确支持“群集架构 (Swarm Architecture)”，适用于去中心化、动态的环境。Matrix（arXiv:2511.21686）将控制流和数据流都表示为由分布式队列传递的序列化消息，从而消除编排器的瓶颈。这里的取舍是明确的：以确定性和可追溯性换取可扩展性。群集模式适用于包含大量独立子问题的任务；不适用于需要单一连贯计划的任务。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`，`queue`）
**前置知识：** 阶段 16 · 05（监督者模式），阶段 16 · 04（原始模型）
**时长：** ~75 分钟

## 问题

监督者模式可以扩展到几个工作节点。但数百个呢？监督者本身会成为瓶颈：每个关于谁做什么的决策都通过一个智能体汇聚。一个缓慢的计划步骤会导致整个系统停滞。

群集架构反转了设计。工作节点不是由中央规划器分配任务，而是从共享队列中拉取任务。“协调”内嵌在事件总线的语义中。没有编排器；系统会一直扩展，直到队列成为瓶颈。

## 概念

### 形态

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

没有编排器。每个工作节点重复：拉取任务、处理、写入结果（并可选择将后续任务入队）。

### 群集适用的场景

- **大量独立任务。** 抓取、转换、分类。任务之间不依赖。
- **时长可变的工作。** 如果某些任务耗时 100 毫秒，另一些耗时 10 秒，群集可以自动平衡负载——快速的工作节点会拉取下一个任务。而监督者需要预先估计时长。
- **吞吐量优先于确定性。** 你关心的是总完成时间，而不是严格的顺序。

### 群集不适用的情况

- **有序的工作流。** 如果步骤 3 需要步骤 2 的输出，群集可能会在步骤 2 完成之前就触发步骤 3。
- **需要全局计划的任务。** 复杂的研究问题需要一个规划器。一群研究者会产生独立的事实，而不是一份连贯的报告。
- **调试困难。** 由于没有中央日志且工作异步进行，重现一个 bug 的成本很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年的一篇论文，它将群集模式推向了自然结论：控制流和数据流都是分布式队列上的序列化消息。没有中央协调器。容错依赖于消息的持久性。可扩展性成为消息代理的问题，而非系统本身的问题。

贡献：一种编程模型，其中多智能体协调变成了“这个智能体订阅哪个消息主题？”，而不是“监督者下一步选哪个智能体？”。这使得系统看起来像一个发布/订阅事件网格。

### LangGraph 的群集架构

LangGraph 2025 文档明确将“群集架构 (Swarm Architecture)”描述为多智能体模式之一：智能体是节点，但边形成一个有向图，包含循环，并且任何节点都可以从池中被激活。工作节点根据条件从可用工作中选取，而不是由监督者分配。

### 失败模式：饥饿与热点

如果所有工作节点都拉取最快可完成的任务，那么长时间运行的任务永远不会被选中，直到它们成为仅剩的任务。经典的队列饥饿问题。

缓解措施：
- 带有显式老化机制的优先级队列（根据等待时间增加优先级）。
- 工作节点专业化：某些工作节点只处理“长”任务。
- 背压：限制进入队列的快速任务数量。

### 基于内容的路由的关联

群集模式与基于内容的路由（第 22 课）自然搭配。不用单一的通用队列，而是为每种消息类型设置一个队列。专业工作节点只订阅其对应类型的队列。这是支持数千智能体的消息总线架构的基础。

## 构建它

`code/main.py` 实现了一个由 4 个工作线程组成的群集，它们从共享的 `queue.Queue` 中拉取任务。任务的持续时间可变（有的快，有的慢）。该演示对比了：

- **顺序基线：** 一个工作节点串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定的工作节点（监督者风格）。
- **群集：** 工作节点从共享队列中拉取任务。

群集自动平衡负载；而固定分配会导致当分配的任务较慢时，空闲的工作节点无事可做。

运行：

```
python3 code/main.py
```

输出显示每个工作节点的任务计数（群集分布不均但最优）以及挂钟时间。

## 使用它

`outputs/skill-swarm-fit.md` 评估一个任务应该使用群集还是监督者模式。输入包括：任务独立性、时长方差、排序要求、可调试性需求。

## 交付它

检查清单：

- **带老化的优先级队列。** 防止长任务饥饿。
- **工作节点幂等性。** 如果工作节点在运行过程中崩溃，一个任务可能被拉取多次。工作节点必须是幂等的。
- **持久化队列。** 生产环境中使用 Kafka、Redis Streams 或数据库支持的队列。`queue.Queue` 仅存在于内存中。
- **每个任务的可观测性。** 每个任务有一个追踪 ID；每个工作节点记录开始和结束时间，并带上该 ID。
- **背压。** 如果队列增长速度快于工作节点消耗速度，则减缓生产者。

## 练习

1. 运行 `code/main.py`。在可变时长工作负载下，群集比顺序快多少？比固定分配快多少？
2. 添加一个优先级队列变体（使用 `queue.PriorityQueue`）。按任务的“重要性”字段分配优先级。观察在持续负载下，低优先级任务是否会永远得不到执行。
3. 实现一个热点检测器：当某个工作节点处理的任务数是最慢工作节点的 3 倍以上时记录日志。这说明了任务时长分布方面的什么问题？
4. 阅读 Matrix 论文（arXiv:2511.21686）的摘要和第 3 节。找出 Matrix 接受的一个具体取舍（可扩展性增益）以及放弃的一个方面（可追溯性、确定性）。
5. 将群集演示改为使用 `(task_type, payload)` 元组的 `queue.Queue`，工作节点只订阅特定类型。当任务异构时，什么样的路由规则是合理的？

## 关键术语

| 术语 | 人们所说的 | 实际含义 |
|------|------------|----------|
| Swarm architecture | “去中心化智能体” | 工作节点从共享队列中拉取任务；没有中央协调器。 |
| Event bus | “智能体订阅主题” | 将任务按类型或内容路由到工作节点的消息代理。 |
| Starvation | “任务从不运行” | 低优先级任务因为持续有更高优先级的工作到达而从未被选中。 |
| Hot-spotting | “一个工作节点被淹没” | 负载不平衡，其中一个工作节点处理了大部分任务。 |
| Back-pressure | “减慢生产者” | 当队列填满时，向上游发出信号停止生产的机制。 |
| Idempotent worker | “可以安全地重跑” | 一个任务被处理两次产生相同的结果。因为工作节点可能在运行中途崩溃，所以需要这种特性。 |
| Durable queue | “崩溃后依然存在” | 由磁盘或复制存储支持的队列；工作节点崩溃时任务不会丢失。 |
| Matrix framework | “全消息传递群集” | 数据和控制流都是分布式队列上的序列化消息。 |
