# SGLang 与 RadixAttention：应对前缀密集型负载

> SGLang 将 KV 缓存视为一种存储于基数树（radix tree）中的、可复用的头等资源。vLLM 采用 FCFS（先到先服务）调度请求，而 SGLang 的缓存感知调度器则优先处理具有更长共享前缀的请求——这实质上是一种深度优先的基数遍历，使得热分支能常驻于 HBM。在 Llama 3.1 8B 模型上，使用类似 ShareGPT 的 1K 提示词，SGLang 达到约 16,200 tok/s，vLLM 约 12,500 tok/s，优势约 29%。在前缀密集的 RAG 工作负载上，优势可达 6.4 倍。在语音克隆类工作负载上，缓存命中率超过 86%。2026 年已在 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 等机构部署超过 400,000 GPU。但需要注意的是，当前缀顺序不一致时，6.4 倍的提升会消失——顺序是工程师手中的杠杆。

## 学习目标

- 图示 RadixAttention：前缀如何存储在基数树中，以及 KV 块如何在同一分支的多个序列间共享。
- 解释缓存感知调度，以及为什么 FCFS 不适合前缀密集型负载。
- 给定前缀缓存命中率和提示词长度分布，计算工作负载的预期加速比。
- 指出使 6.4 倍加速成为现实而非潜力损失所需的提示词顺序规则。

## 问题

经典服务将每个请求的提示词视为黑盒。即使 5,000 个 RAG 请求都以相同的 2,000 token 系统提示词和相同的检索前言开头，vLLM 仍会对该 2,000 token 前缀进行 5,000 次预填充。GPU 反复做着相同的工作。

观察发现：在智能体和 RAG 工作负载中，提示词几乎总是共享长前缀。系统提示词、工具模式、少样本示例、检索头部、对话历史——这些都在请求间重复出现。如果只存储该前缀的 KV 缓存一次并复用，就无需再次预填充。

RadixAttention 正是这样做的。Token 被索引在一棵基数树中；每个节点拥有从其根路径开始的 token 序列的 KV 块。新请求沿树行走：任何 token 匹配的节点将复用该节点的 KV 块。预填充成本变得与“新”后缀成正比，而非整个提示词。

挑战在于调度。如果两个请求共享一个 2,000 token 前缀，而第三个请求只共享相同前缀的 200 token，那么你希望同时处理那两个长共享请求，以使长前缀留在 HBM 中。FCFS 则相反——它服务于最先到达的请求，可能在下一個长前缀请求到来之前就驱逐了热分支。

## 概念

### 作为 KV 索引的基数树

基数树（紧凑 trie）存储 token 序列。每个节点拥有一个 token 范围以及为该范围计算的 KV 块。子节点扩展序列一个或多个 token。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

新请求携带系统提示词 + "Context: <doc A>" + "Question: Carol"。调度器遍历：系统前缀匹配（复用 124 个块），doc-A 分支匹配（复用 31 个块），然后仅为 "Question: Carol" 分配新块（4 个块）。预填充成本：4 个新 token 块。没有树则为 160 个块。预填充节省约 40 倍。

### 缓存感知调度

如果缓存不断抖动，基于基数树的复用例毫无意义。两个关键策略：

1. **深度优先分发**。选择队列中下一个请求时，优先选择与当前运行集合处于同一分支的请求。这使热分支保持常驻。
2. **分支级 LRU，而非块级**。驱逐整个分支（从最短使用的叶子开始），而非单个块，使缓存形状与基数形状匹配。

FCFS 违背了这两点。一个共享 2,000 token 的请求排在一个仅共享 50 token 的请求后面，然后 2,000 token 的分支被驱逐以腾出空间给 50 token 的请求。

### 你应该记住的基准数字

- Llama 3.1 8B, H100, ShareGPT 1K 提示词：SGLang ~16,200 tok/s vs vLLM ~12,500（约 29% 优势）。
- 前缀密集的 RAG（相同系统提示词 + 相同文档，不同问题）：SGLang 可达 6.4 倍。
- 语音克隆工作负载：前缀缓存命中率 86.4%。
- SGLang 客户生产环境命中率：50-99%，取决于提示词顺序规则。
- 2026 年部署在 400,000+ GPU 上。

### 顺序陷阱

6.4 倍的数字依赖于一致的提示模板顺序。如果你的客户端在某些请求中构造提示词为 `[system, tools, context, history, question]`，而在其他请求中为 `[system, context, tools, history, question]`，树就无法找到共享前缀。对人类来说看似共享的前缀，对基数树而言是两个不同的序列。

工程师的杠杆：你的提示模板就是缓存键。固定顺序。将不可变部分（系统提示词、工具、模式）放在最前面。检索上下文紧随其后。用户问题放在最后。不要将动态内容穿插到前缀中。

研究中的真实案例：将动态内容移出可缓存前缀，仅一次修改就将部署的缓存命中率从 7% 提升到 74%。

### RadixAttention 的胜场与败场

胜场：
- RAG（相同检索前言，不同问题）。
- 智能体（相同工具模式，不同查询）。
- 带有长系统提示词的聊天。
- 带有重复前言的语音/视觉工作负载。

败场（回落到 vLLM 级别的吞吐量）：
- 具有唯一提示词的单次生成（代码补全、无系统提示词的开放式聊天）。
- 动态提示词，每个请求都将独特内容穿插到前缀中。

### 为什么这是调度问题，而不仅仅是内核问题

你可以将 KV 复用实现为一种内核技巧。SGLang 的洞察在于：只有在调度器保持热分支常驻时，复用才有意义。在混合负载下，一个朴素的“如果可用就复用”策略会使缓存抖个不停。正是基数树索引的调度器将内核技巧变成了 29% 的生产环境优势。

### 与 vLLM 的互动

两者并非严格的竞争对手。2026 年，vLLM 添加了前缀缓存（`--enable-prefix-caching`）和一个缓存感知路由器（vLLM Router in Rust）。差距缩小但没有完全消失——SGLang 的整个栈是以基数为先的；vLLM 则是移植的。对于以前缀复用为主的工作负载，SGLang 仍是默认选择。对于没有强前缀模式的通用服务，vLLM 仍然持平或更好。

## 使用它

`code/main.py` 实现了一个玩具 radix-tree KV 缓存以及一个具有两种策略（FCFS 和缓存感知）的调度器。对同一工作负载运行两种策略，报告前缀缓存命中率和吞吐量差异。然后运行一个“乱序”工作负载，展示 6.4 倍提升的消失。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| RadixAttention | "SGLang 那东西" | KV 缓存以基数树索引，共享前缀复用块 |
| 基数树（Radix tree） | "紧凑 trie" | 每个节点拥有一个 token 范围及其 KV 块的树 |
| 缓存感知调度器（Cache-aware scheduler） | "热分支优先" | 优先选择与常驻分支共享的请求的调度器 |
| 前缀缓存命中率（Prefix-cache hit rate） | "你的提示词有多少是免费的" | 从复用 KV 块服务的提示 token 比例 |
| FCFS | "先来先服务" | 破坏前缀局部性的默认调度 |
| 分支级 LRU（Branch-level LRU） | "驱逐叶子" | 与基数形状匹配的驱逐策略 |
| 提示模板顺序（Prompt template ordering） | "缓存键" | 提示词的组件顺序决定了树能共享什么 |
| 系统提示词固定（System prompt pinning） | "常驻前缀" | 固定不可变的系统部分以避免驱逐抖动 |
