# SRE for AI — 多智能体事件响应、Runbook 与预测性检测

> AI SRE 利用基于基础设施数据（日志、runbook、服务拓扑）的 LLM 通过 RAG 来自动化调查、记录和协调阶段。2026 年的架构模式是多智能体编排——由主管协调的专门智能体（日志、指标、runbook）；AI 提出假设与查询，人类批准判断决策。Datadog Bits AI 和 Azure SRE Agent 将其作为托管产品交付。Runbook 正在演进：NeuBird Hawkeye 使用对抗性评估（两个模型分析同一事件；一致 = 置信，不一致 = 不确定性）；操作记忆跨越团队变动持续保留。自动修复保持谨慎：AI 建议，人类批准。完全自主行动范围狭窄（重启 Pod、回滚特定部署）且具有严格护栏——任何兜售“设置后不用管”的都是过度承诺。新兴前沿：事件前预测。MIT 研究报告了一个基于历史日志 + GPU 温度 + API 错误模式训练的 LLM，能提前 10-15 分钟预测 89% 的中断。预测：到 2026 年底，95% 的企业 LLM 将拥有自动故障转移能力。

**类型：** 学习
**语言：** Python（stdlib，玩具级多智能体事件分诊模拟器）
**前置知识：** 阶段 17 · 13（可观测性），阶段 17 · 24（混沌工程）
**时间：** 约 60 分钟

## 学习目标

- 绘制多智能体 AI SRE 架构图：主管 + 专门智能体（日志、指标、runbook）+ 人类批准关卡。
- 解释为什么自动修复是狭窄的（重启 Pod、回滚部署）而非广泛的（重新设计服务）。
- 说出对抗性评估模式（NeuBird Hawkeye）：两个模型一致 = 置信；不一致 = 升级。
- 引用 MIT 89% 早期检测结果以及操作约束：没有执行力的预测只是仪表盘。

## 问题

一位值班工程师在凌晨 3 点被寻呼。“结账错误率很高”。他们检查 Datadog、Loki、三个 runbook、部署日志。30 分钟后他们意识到根本原因是 vLLM 因 KV 缓存峰值导致 OOM。他们重启 Pod；错误清除。

到 2026 年，调查过程中的前 20 分钟是可以自动化的。按服务分组日志、关联最近的部署、匹配 runbook——这些都是 RAG + 工具使用。一个受监督的智能体可以在人类打开 Datadog 之前完成初步分诊并给出假设。

完全自主修复是另一个问题。重启 Pod：安全。扩展 GPU 池：如果策略允许则安全。重新设计服务：绝对不行。这门学科就是划定这条狭窄的界限。

## 概念

### 多智能体架构

```
          Incident
             │
             ▼
        Supervisor
        /    |    \
       ▼     ▼     ▼
  Log agent  Metric agent  Runbook agent
       │     │     │
       └─────┴─────┘
             │
             ▼
        Hypothesis + evidence
             │
             ▼
        Human approval
             │
             ▼
        Action (narrow set)
```

主管将事件分解为子查询。专门智能体拥有工具访问权限（日志搜索、PromQL、文档检索）。主管进行综合，将假设 + 证据呈现给人类。人类批准或改变方向。

### 自动修复范围

**安全（狭窄）**：重启 Pod、回滚特定部署、在预先批准的范围内扩展池、启用预先批准的功能开关。

**不安全（广泛）**：更改服务拓扑、修改资源限制、部署新代码、更改 IAM、修改数据库。

任何兜售“设置后不用管”的都是过度承诺。随着 AI SRE 的成熟，安全集将增长，但边界是真实存在的。

### 对抗性评估（NeuBird Hawkeye）

两个模型独立分析同一事件。如果它们在根本原因上一致，则置信度高。如果不一致，则将事件升级给人类，同时展示两种假设。简单的模式，有效的过滤器，可防止虚假的根本原因。

### 操作记忆

团队人员变动是传统 SRE 的无声杀手——隐性知识会流失。AI SRE 将 runbook + 事后分析存储在向量数据库中；每次新事件时智能体会进行检索。当新工程师加入时，AI 拥有完整的历史记录。

### 事件前预测

MIT 2025 年研究：基于历史日志、GPU 温度、API 错误模式训练的 LLM 在测试集上提前 10-15 分钟预测了 89% 的中断。

现实检查：没有执行力的预测只是仪表盘。操作问题是“当我们预测到时，我们该做什么？”主动排空？寻呼？自动扩缩？答案是策略特定的。

### 2026 年的产品

- **Datadog Bits AI** — 托管在 Datadog 内部的 SRE 副驾驶。
- **Azure SRE Agent** — Azure 原生。
- **NeuBird Hawkeye** — 对抗性评估 + 操作记忆。
- **PagerDuty AIOps** — 分诊 + 去重。
- **Incident.io Autopilot** — 事件指挥 + 协调。

### 作为代码的 Runbook

Runbook 从 Confluence 页面演变为带有结构化章节（症状、假设、验证、行动）的版本化 Markdown。结构化的 runbook 有助于更好的 RAG 检索。任何 AI-SRE 部署都应将非结构化的 runbook 转换为结构化。

### 你应该记住的数字

- MIT 早期检测：89% 的中断，10-15 分钟提前量。
- 多智能体分诊：主管 +（日志、指标、runbook）+ 人类。
- 安全自动修复集：重启 Pod、回滚部署、在规定范围内扩展。
- 对抗性评估：两个模型独立；一致 = 置信。

## 使用它

`code/main.py` 模拟了多智能体分诊：日志智能体发现错误，指标智能体发现 CPU 峰值，runbook 智能体匹配已知问题。主管对假设进行排序。

## 交付它

本课程生成 `outputs/skill-ai-sre-plan.md`。根据当前的 on-call 状况、事件量、团队成熟度，设计一个 AI SRE 部署方案。

## 练习

1. 运行 `code/main.py`。如果日志和指标智能体意见不一致怎么办？主管如何解决？
2. 为你的服务定义三个“安全”的自动修复操作。证明每个操作的合理性。
3. 编写一个结构化的 runbook 模板：章节、必填字段、验证命令。
4. 预测性检测在 12 分钟提前量时触发。你的策略是什么——寻呼、预排空、还是两者都做？
5. 辩论一支 3 人团队是否应该在 2026 年采用 AI SRE 还是再等等。考虑成熟度、事件量、风险。
