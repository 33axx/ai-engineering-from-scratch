# Claude Code 作为自主智能体：权限模式与 Auto 模式

> Claude Code 暴露出七种权限模式。"plan" 模式在每次操作前询问，"default" 模式仅对危险操作询问，"acceptEdits" 模式自动批准文件写入但仍确认命令执行，"bypassPermissions" 模式批准所有操作。Auto 模式（2026 年 3 月 24 日）将逐操作审批替换为一个两阶段并行安全分类器：每个操作运行一个单 token 快速检查；被标记的操作触发思维链深度审查。操作预算通过 `max_turns` 和 `max_budget_usd` 强制执行。Auto 模式以研究预览形式发布——Anthropic 已明确说明分类器本身并不足够。

**类型:** 学习
**语言:** Python（标准库，两阶段分类器模拟）
**前置知识:** 阶段 15 · 01（长周期智能体），阶段 15 · 09（编码智能体格局）
**时长:** ~45 分钟

## 问题

你机器上的自主编码智能体是一个独特的安全类别。攻击面是智能体能触及的一切——文件系统、网络、凭据、剪贴板、任何浏览器标签页、任何打开的终端。Bruce Schneier 等人已公开指出这一问题：计算机使用智能体并非聊天机器人的“功能更新”，而是一种具有新型风险特征的新型工具。

Claude Code 的权限系统是 Anthropic 的解决方案。它并非一个“自主/非自主”开关，而是七种模式，横跨一个能力阶梯：plan → default → acceptEdits → … → bypassPermissions。每种模式在速度与逐操作审查之间做出不同权衡。Auto 模式（2026 年 3 月）增加了一个两阶段分类器，将用户从分类器判定为安全的操作的审批关键路径中移除，同时为分类器标记的操作保留审查层。

工程问题在于：该系统能捕获什么，遗漏什么，以及给定任务实际上需要哪种模式？

## 概念

### 七种权限模式

| 模式 | 行为 | 何时使用 |
|---|---|---|
| `plan` | 智能体提出计划；用户批准整个计划；每个操作执行前都经过审查 | 不熟悉的任务；靠近生产的代码；首次在仓库上使用智能体 |
| `default` | 智能体执行操作；对任何“危险”操作（命令执行、破坏性操作、网络调用）提示用户 | 大多数交互式编码会话 |
| `acceptEdits` | 文件写入自动批准；命令执行和网络调用仍提示 | 跨多个文件的代码重构 |
| `acceptExec` | 命令在精心制定的允许列表中自动批准；写入自动批准 | 紧密内循环，其中每个命令都是 `npm test` 或类似操作 |
| `autoMode` | 两阶段安全分类器；被标记的操作升级为审查 | 在受限工作区内进行长周期无人值守运行 |
| `yolo` | 跳过大多数提示；仍运行工具允许列表/拒绝列表 | 临时沙箱、CI 任务、研究脚本 |
| `bypassPermissions` | 批准所有操作 | 记录为“仅在你愿意丢弃的临时容器内” |

（以上名称与公开的 Claude Code 文档一致；“yolo”是宽松中间地带的非正式简称。）

### Auto 模式一页纸

Auto 模式（2026 年 3 月 24 日发布）是首个将逐操作审批委托给模型的权限模式。结构如下：

1. **第一阶段——单 token 分类器。** 对每个提议的操作运行。成本低廉。返回“安全”或“标记”。设计为主智能体循环并行运行，以便已批准的操作不会排队等待。
2. **第二阶段——二级策略/安全审查。** 仅对标记的操作运行。对操作、会话当前状态以及声明的任务进行有针对性的策略和安全评估。如果置信度较低，则升级到用户介入。

预算控制与分类器并存：

- `max_turns` —— 会话中的总迭代次数。
- `max_budget_usd` —— 美元上限，达到后终止会话。
- 每个工具的操作次数限制（例如，`WebFetch` 调用不超过 N 次等）。

### 系统能捕获什么

- 直接的提示注入，注入的指令映射到已知危险的操作形态。
- 重复的工具循环——分类器可以看到操作 N+1 与操作 N 几乎相同，连续五次。
- 在仅进行文件编辑的会话中，明显超出范围的命令执行。

### 系统可能遗漏什么

- **微妙的提示注入**，在不产生单个标记操作的情况下改变行为。间接提示注入并非完全可修补的漏洞（OpenAI 准备部门主管，2025，关于浏览器智能体——见第 11 课）。
- **语义层面的不当行为。** 每个单独操作看起来安全，但组合轨迹可能有害。分类器判断操作；它不会重新推导用户的意图。
- **通过合法渠道的数据外泄。** 将数据写入你拥有的文件，然后 `git push` 到公共仓库，是一系列已允许的操作，其组合才是问题所在。

### 研究预览框架

Anthropic 将 Auto 模式作为研究预览发布。文档明确指出分类器是一层，而非解决方案：用户应将 Auto 模式与预算、允许列表、隔离工作区和轨迹审计（第 12-16 课）结合使用。预览框架也反映了已记录的评价-部署差距（第 1 课）——在离线评价中通过的分类器在实际会话中可能表现不同，因为用户上下文可能存在歧义。

### 该阶梯在你工作流程中的位置

- 不熟悉的任务：从 `plan` 模式开始。阅读计划比回滚失败的运行成本更低。
- 已知的重构：`acceptEdits` 可节省大量确认点击。
- 无人值守后台运行：`autoMode` 仅在你已测量过爆炸半径的工作区内使用（无凭据、无生产挂载、未选择退出的出口）。
- 临时容器：`yolo` / `bypassPermissions` 仅在容器及其凭据可丢弃时才可接受。

## 使用它

`code/main.py` 模拟了两阶段分类器。第一阶段是对提议的操作进行的廉价关键词规则；第二阶段是较慢的多规则审查器。驱动程序输入一段简短的合成轨迹（安全操作、一次提示注入尝试、一个重复循环），并展示分类器在哪里捕获、在哪里遗漏。

## 交付它

`outputs/skill-permission-mode-picker.md` 将任务描述与正确的权限模式、预算上限和所需的隔离级别匹配起来。

## 练习

1. 运行 `code/main.py`。哪种合成操作类型从未被第一阶段标记，但总是被第二阶段捕获？哪种类型两个阶段都未捕获？

2. 扩展第一阶段规则集以捕获一个特定的已知危险形态（例如 `curl $ATTACKER/exfil`）。在良性操作样本上衡量误报率。

3. 阅读 Anthropic 的“智能体循环如何工作”文档。列出在 `default` 模式下智能体默认接触的所有外部状态。哪些状态需要在无人值守运行 `autoMode` 之前单独进行门控？

4. 设计一个 24 小时无人值守运行的预算：`max_turns`、`max_budget_usd`、每个工具的上限、允许列表。证明每个数字的合理性。

5. 描述一个轨迹，其中每个单独操作都被第一阶段和第二阶段批准，但组合行为却是不对齐的。（第 14 课介绍了终止开关和金丝雀令牌如何解决这一问题。）

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|---|---|---|
| 权限模式 | "智能体能做什么的程度" | 控制逐操作审批的七种命名策略之一 |
| plan 模式 | "做什么都先问" | 智能体编写计划；用户执行前批准 |
| acceptEdits | "让它写文件" | 文件写入自动批准；命令执行仍提示 |
| autoMode | "自动批准" | 两阶段安全分类器；标记的操作升级 |
| bypassPermissions | "完全 YOLO" | 批准所有操作；适用于临时容器 |
| 第一阶段分类器 | "快速 token 检查" | 对提议操作的单 token 规则；并行运行 |
| 第二阶段分类器 | "深度审查" | 对标记操作进行思维链推理 |
| 研究预览 | "非 GA" | Anthropic 对故障模式仍在绘制中的功能的框架 |
