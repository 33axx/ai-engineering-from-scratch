# 长时间运行的后台代理：持久化执行

> 生产环境中的长周期代理并非在 `while True` 中运行。每次 LLM 调用都会成为一个带有检查点、重试和重放的活动。Temporal 的 OpenAI Agents SDK 集成于 2026 年 3 月正式可用。Claude Code Routines（Anthropic）无需持久的本地进程即可运行定时调度的 Claude Code 调用。会话会在等待人工输入时暂停，在部署后依然存活，并能根据 `thread_id` 对应的最新检查点恢复执行。在这些新的易用性背后，是一个老模式——工作流编排——加上一个新输入：将 LLM 调用视为非确定性活动，这些活动在恢复时必须能够被确定性地重放。

**类型：** 学习
**语言：** Python（标准库，最小持久化执行状态机）
**前置要求：** 第15阶段·10（权限模式），第15阶段·01（长周期代理）
**时间：** 约60分钟

## 问题

设想一个运行四个小时的代理。它调用了三个工具，两次提示用户，并进行了四十次 LLM 调用。运行到一半时，宿主机重启了。会发生什么？

- 在简单的 `while True` 循环中：一切丢失。运行从头开始重新执行。那三个工具调用（带有真实的副作用）会再次执行。用户会被再次提示那些他们已经批准过的事情。四十次 LLM 调用会被重新计费。
- 使用持久化执行：运行从最近的检查点恢复。已经完成的活动不会重新执行；它们的结果会从持久化日志中重放。用户不会重新批准他们已经批准过的事情。已经完成的 LLM 调用不会重新计费。

这与工作流引擎已提供十年的模式相同（Temporal、Cadence、Uber 的 Cherami）。不同之处在于，LLM 调用现在成为一种活动——非确定性、昂贵、带有副作用——并且它们能很好地适应这个模式。

本课的核心主题：长周期可靠性会衰减（METR 观察到“35 分钟退化”——成功率大致随周期平方下降）。持久化执行使得运行时间可以超过可靠性特性所能支持的范围，如果设计正确，这是一种新的安全失败方式；如果设计错误，则是一种不安全的失败方式。

## 概念

### 活动、工作流与重放

- **工作流**：确定性编排代码。定义活动序列、分支、等待。必须是确定性的，以便能够从事件日志中重放而不会出现意外的偏差。
- **活动**：一个非确定性的、可能失败的单元工作。LLM 调用、工具调用、文件写入、HTTP 请求。每个活动都会记录其输入和（完成后）输出。
- **事件日志**：持久化的后端存储。每个活动的开始、完成、失败、重试以及每个工作流决策都会被记录。
- **重放**：恢复时，工作流代码从头开始重新运行；每个已经完成的活动直接返回其记录的结果，而不重新执行。只有尚未完成的活动才会真正运行。

这与 React 根据虚拟 DOM 重新渲染，或 Git 根据提交重建工作树是相同的模式。编排器中的确定性使得持久化变得廉价。

### 为什么 LLM 调用适合这种模式

LLM 调用是：
- 非确定性的（温度 > 0；即使温度为 0，也会随模型版本漂移）。
- 昂贵的（金钱和延迟）。
- 可能失败的（速率限制、超时）。
- 带有副作用的（如果调用了工具）。

这正是活动的特性。将每次 LLM 调用包装为一个活动，可以获得指数退避的重试、跨重启的检查点以及可供调试的可重放跟踪。

### 基于 `thread_id` 的检查点

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects 和 Claude Code Routines 都收敛到了相同的 API 形态：使用 `thread_id`（或等价物）标识会话；每次状态转换都持久化到后端（默认 PostgreSQL，开发用 SQLite，缓存用 Redis）；恢复时读取最新的检查点。

后端的选择很重要：

- **PostgreSQL**：持久化、可查询、可跨越部署。LangGraph 的默认选择。
- **SQLite**：仅限本地开发；跨主机会丢失数据。
- **Redis**：快速但临时，除非配置了 AOF/快照。
- **Cloudflare Durable Objects**：透明分布式；通过唯一键限定作用域；可持续数小时到数周。

### 人工输入作为一等状态

提议-然后提交（课程 15）需要持久的“等待人工输入”状态。工作流暂停，外部队列持有待处理请求，批准从该确切点恢复。没有持久化，这只能尽力而为；有了持久化，隔夜的批准到达后，工作流会在早上继续执行。

### 35 分钟退化

METR 观察到，所有测量的代理类在连续运行约 35 分钟后都会出现可靠性下降。任务持续时间加倍，故障率大致翻两番。持久化执行并不能解决这个问题；它只是让你能够运行超过可靠性特性支持的时间。安全的模式是将持久化与检查点结合使用，这些检查点在重新进入时需要新的人工参与循环（HITL），并与预算终止开关（课程 13）结合，以限制总计算量，而不论挂钟时间多长。

### 持久化执行何时不是正确的答案

- 运行时间短于几分钟且无需人工输入的情况。开销大于收益。
- 严格只读的信息检索。
- 那些正确性要求端到端在一个上下文窗口内完成的任务（某些推理任务；某些一次性生成）。

## 使用它

`code/main.py` 使用标准库 Python 实现了一个最小的持久化执行引擎。它支持：

- `@activity` 装饰器，将输入和输出记录到 JSON 事件日志中。
- 一个工作流函数，用于编排活动序列。
- 一个 `run_or_replay(workflow, event_log)` 函数，可以重放已完成的活动而不重新执行它们。

驱动程序模拟了一个包含三个活动的工作流，在中间模拟崩溃，并展示 (a) 简单重试会重新执行所有内容，而 (b) 重放只运行缺失的活动。

`outputs/skill-durable-execution-review.md` 审查了一个拟议的长时间运行代理部署的正确持久化执行形态：活动、确定性、检查点后端、人工输入状态以及恢复时的人工参与循环（HITL）策略。

## 练习

1. 运行 `code/main.py`。观察简单重试与重放在活动执行次数上的差异。更改崩溃点，并展示重放计数相应变化。

2. 将玩具引擎改为显式使用 `thread_id`。模拟两个并发会话共享同一个引擎，并确认它们的事件日志不会冲突。

3. 在玩具引擎中选取一个活动。引入一个非确定性因素（工作流决策中的挂钟时间戳）。展示重放时的偏差。解释真实引擎如何处理这个问题（副作用注册、`Workflow.now()` API）。

4. 阅读 LangChain 的“生产环境深度代理背后的运行时”文章。列出运行时持久化的每个状态，并指出每个状态覆盖了哪种故障模式。

5. 为一个 6 小时的自主编码任务设计一个检查点策略。你在哪里设置检查点？崩溃后恢复是什么样的？哪些部分需要新的人工参与循环（HITL）？

## 关键术语

| 术语 | 人们说的意思 | 实际含义 |
|---|---|---|
| 工作流 | “代理的脚本” | 确定性编排代码；可从事件日志重放 |
| 活动 | “一个步骤” | 非确定性单元（LLM 调用、工具调用）；执行前后均记录 |
| 事件日志 | “后端存储” | 每次状态转换的持久化记录 |
| 重放 | “恢复” | 重新运行工作流；已完成的活动直接返回记录的结果而不重新执行 |
| 检查点 | “保存点” | 基于 thread_id 持久化的状态；恢复时取最新的 |
| thread_id | “会话键” | 用于限定持久化状态作用域的标识符 |
| 35 分钟退化 | “可靠性衰减” | METR：成功率大致随周期平方下降 |
| 非确定性 | “重放时的偏差” | 挂钟时间、随机数、LLM 输出；必须注册为副作用 |
