# 角色专业化 — 规划者、批评者、执行者、验证者

> 2026年最常见的多智能体分解方式：一个智能体规划，一个执行，一个批评或验证。MetaGPT（arXiv:2303.00352）将其形式化为编码到角色提示中的标准操作程序——产品经理、架构师、项目经理、工程师、测试工程师——遵循`Code = SOP(Team)`范式。ChatDev（arXiv:2307.07924）通过"聊天链"与"沟通式去幻觉"（智能体主动请求缺失的细节）将设计师、程序员、评审员、测试员串联起来。验证者承担关键作用：Cemri等人（MAST，arXiv:2503.13657）表明，每个多智能体系统的失败都可追溯到缺失或损坏的验证环节。普华永道报告称，在CrewAI中使用结构化验证循环可使准确率提升7倍（从10%提升至70%）。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置要求：** 阶段16 · 04（基础模型），阶段16 · 05（监督者）
**时间：** 约60分钟

## 问题

通用的多智能体系统产生通用的输出。三个程序员在群聊中写出三个版本同样平庸的代码。你可以增加更多智能体、增加更多轮次，但仍然无法跨越质量门槛。

解决方案不是增加智能体数量，而是增加*不同类型*的智能体。分配不同的角色。赋予批评者规划者没有的工具。赋予验证者客观的测试套件。这样系统就具有了基于有依据修正的内部异议能力，而不仅仅是并行猜测。

## 概念

### 四种典型角色

**规划者。** 读取目标，生成步骤列表或规格说明。工具：知识检索、文档。输出：结构化计划。

**执行者。** 每次读取一个计划步骤，生成制品。工具：实际工作工具（代码编译器、Shell、API客户端）。输出：制品。

**批评者。** 对照规划者的意图评估执行者的输出。工具：对制品的只读访问、静态分析。输出：接受/拒绝并附上理由。

**验证者。** 读取制品并运行确定性检查。工具：测试运行器、类型检查器、模式验证器。输出：通过/失败并提供证据。

批评者是主观的、基于观点的，通常基于LLM。验证者是客观的、确定性的，通常基于代码。它们不是同一个角色。

### MetaGPT的SOP模式

MetaGPT（arXiv:2308.00352）将软件工程标准操作程序编码为角色提示：

- **产品经理**编写产品需求文档。
- **架构师**生成系统设计。
- **项目经理**拆分任务。
- **工程师**实现代码。
- **测试工程师**运行测试。

每个角色都有严格的输入/输出模式。角色提示说明了该角色*是什么*以及它*必须产出什么*。`Code = SOP(Team)`的表述——确定性的标准操作程序将一组LLM转化为可预测的流水线。

### ChatDev的沟通式去幻觉

ChatDev增加了一个关键举措：当执行者需要一个在计划中没有的具体细节时，它会在继续之前明确向设计师提问。这防止了经典的LLM错误——看似合理但实际虚构细节。

实现方式：角色提示中包含"当你需要未获得的具体信息时，在产生输出之前通过名称向相关角色提问。"

### 为什么验证者最重要

Cemri等人（MAST）追踪了1642次多智能体执行失败。其中21.3%是验证缺口——系统交付了没有人检查过的答案。其余79%通常可追溯到"存在一个静默失败或从未运行的检查"。验证者是承担关键作用的角色。

普华永道报告（CrewAI部署，2025年）指出，添加结构化验证循环使准确率从10%提升至70%。一个角色带来7倍增益。

### 批评者与验证者的区别

- 批评者是一个LLM，审查制品的质量。主观的。可能被看似合理的表述迷惑。
- 验证者是一个确定性的程序，在制品上运行。客观的。给出通过/失败并附上证据。

两者并用。批评者捕捉验证者无法表达的风格问题。验证者捕捉批评者无法看到、仅在运行时才显现的错误。

### 反模式

系统中每个角色都是LLM，每个角色的输出都是"我看挺好"。经典的MAST失败模式。至少添加一个通过代码而非LLM决定通过/失败的验证者。

### 框架映射

- **CrewAI** — `Agent(role, goal, backstory)` 是教科书式的专业化接口。
- **LangGraph** — 节点可以拥有专业化提示；边强制执行流水线。
- **AutoGen** — 角色特定的ConversableAgents，在GroupChat中使用一个词命名。
- **OpenAI Agents SDK** — 角色专业化的Agent之间的转交工具。

## 动手构建

`code/main.py`实现了一个构建简单Python函数的4角色流水线：

- **规划者**生成一个规格说明。
- **执行者**生成代码字符串。
- **批评者**（模拟LLM）标记明显的问题。
- **验证者**在沙箱中运行生成的代码（使用`exec`）并针对测试用例进行测试。

演示运行两次：一次执行者生成正确代码（批评者和验证者均通过），一次执行者生成不符合规格的代码（批评者因代码看似合理而错过了错误，验证者因测试失败而捕获了错误）。

运行：

```
python3 code/main.py
```

## 使用指南

`outputs/skill-role-designer.md`接收一个任务，生成角色名册（3-5个角色）、每个角色的输入/输出模式以及验证者检查。在将智能体接入框架之前使用此工具。

## 交付清单

- **至少一个确定性验证者。** 绝不要全是LLM。
- **每个角色有明确的输入/输出模式。** 规划者返回规格说明，而非散文；执行者读取该模式。
- **沟通式去幻觉。** 信息缺失时执行者必须向规划者提问；绝不虚构。
- **批评者/验证者排序。** 先运行批评者（成本低，捕获设计问题），再运行验证者（速度慢，捕获错误）。
- **循环预算。** 在升级到人类处理之前，最多进行2轮批评者-执行者修订循环。

## 练习

1. 运行`code/main.py`并观察验证者如何捕获批评者遗漏的错误。添加一个静态分析检查（统计`return`出现次数）作为额外的验证者。它捕获了运行时测试遗漏的什么问题？
2. 添加第5个角色："需求分析师"，将用户愿望转化为规划者可读的规格说明。哪些沟通式去幻觉请求应向上传递给它？
3. 阅读MetaGPT第3节（"智能体"）。列出MetaGPT的5个角色各自的输入/输出模式。
4. 阅读ChatDev的聊天链图（arXiv:2307.07924图3）。找出沟通式去幻觉在何处打破了本会无限循环的循环。
5. 普华永道的7倍准确率提升来自验证循环。假设三个添加验证者没有帮助的任务——即无法或成本过高地对正确性进行确定性检查的任务。

## 关键术语

| 术语 | 人们通常的说法 | 实际含义 |
|------|----------------|----------|
| 角色专业化 | "不同的智能体，不同的工作" | 为规划者/执行者/批评者/验证者角色调优的不同系统提示。 |
| SOP模式 | "编码的标准操作程序" | MetaGPT的框架：每个角色严格的输入/输出模式将团队转变为流水线。 |
| 沟通式去幻觉 | "先问再编" | ChatDev模式：当细节缺失时，执行者向规划者提问而不是自行编造。 |
| 批评者 | "LLM评审员" | 主观的、基于观点的评审员。捕捉风格问题。可能被看似合理的表述迷惑。 |
| 验证者 | "确定性检查" | 基于代码的通过/失败。测试运行器、类型检查器、模式验证器。不会被迷惑。 |
| 验证缺口 | "没有人检查" | 21.3%的MAST失败。交付的答案没有经过本可捕获错误的检查。 |
| 修订循环 | "批评者退回重做" | 批评者拒绝触发执行者带着反馈重新运行。需要预算控制。 |
| 全LLM反模式 | "我看挺好" | 每个角色都是LLM，没有确定性检查。经典的MAST失败模式。 |
