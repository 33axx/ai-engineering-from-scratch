# 生产环境扩展——队列、检查点、持久性

> 将多智能体系统扩展到数千个并发运行需要**持久执行**。LangGraph 的运行时在每个超级步骤后写入检查点（默认使用 Postgres），键值为 `thread_id`；工作进程崩溃后释放租约，另一个工作进程恢复。智能体可以无限期休眠等待人工输入。**MegaAgent**（arXiv:2408.09955）运行了一个每智能体的生产者-消费者队列，具有三种状态（空闲 / 处理 / 响应）和两层协调（组内聊天 + 组间管理聊天）。**Fiber/async** 在 LLM 流式传输方面优于每任务线程：线程在 99% 的时间里等待令牌而空闲，fiber 在 I/O 上协作式让出。反方观点：Ashpreet Bedi 的“Scaling Agentic Software”主张使用 **FastAPI + Postgres + 别的东西**，直到负载证明需要更多——简单架构往往超出预期。本课程构建一个持久检查点日志、一个带有状态转换的每智能体工作队列、一个 async 与线程的演示，并落实“从简单开始”的实用规则。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`asyncio`，`sqlite3`）  
**前置条件：** 阶段 16 · 09（并行群体网络），阶段 16 · 13（共享内存）  
**时间：** 约 75 分钟

## 问题

一个原型多智能体系统在一台笔记本电脑上使用内存事件循环运行三个智能体，运行良好。但当你将其投入生产时：

- 智能体有时会运行数小时（长期研究，人工在环等待）。
- 工作进程崩溃。重启会丢失状态。
- 峰值负载是平均值的 10 倍；你需要水平扩展。
- 用户按智能体运行付费；你需要为计费提供恰好一次语义。

内存事件循环无法满足这些需求。你需要在底层建立持久执行层。2026 年的典型方案有：

1. 带有检查点的工作流引擎（Temporal、LangGraph 运行时）。
2. 带有状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor 模型框架（MegaAgent 的每智能体生产者-消费者模型）。
4. 自建 FastAPI + Postgres（Bedi 的观点）。

本课程将构建每种方案的微型实现。

## 概念

### 持久执行，模式

持久执行引擎在每个“步骤”（LangGraph 中称为超级步骤）之后持久化完整的程序状态。崩溃时：

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

为了实现这一点，需要满足：

- **可序列化的状态。** 所有智能体状态必须可持久化。带有实时数据库连接的函数闭包无法存活。
- **确定性的恢复。** 在相同状态和相同输入下，智能体产生相同的动作（或将 LLM 调用委托给外部确定性预言机）。
- **幂等的外部影响。** 外部调用（工具调用、支付）必须是幂等的，或者使用去重键。

LangGraph 在每个超级步骤后写入检查点；Temporal 在每个活动后写入；Restate 使用事件溯源的日志。它们都实现了相同的模式。

### LangGraph 的运行时

每个智能体有一个 `thread_id`；状态是一个类型化的字典；每个超级步骤向检查点表写入一行。恢复时，运行时从最后一个检查点重放，而不是从头开始。智能体可以 `interrupt()` 等待人工输入；运行时持久化状态并释放工作进程。当输入到达时，任何工作进程都可以恢复。

这是 2026 年 4 月的参考生产设计。

### MegaAgent 的每智能体队列

arXiv:2408.09955 描述了一个规模实验：一个集群中运行数千个并发智能体。架构如下：

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

两层协调使得组内对话密集，而组间对话稀疏——这是用于在数千个智能体下保持成本线性的模式。

### 异步与每任务线程

LLM 调用是 I/O 密集型的。等待下一个令牌的线程有 99% 的时间处于空闲状态。每个线程约消耗 1MB RAM；在 10,000 个并发调用下，仅栈内存就需要 10GB。

Fiber（Python 的 `asyncio`，Go 的 goroutine，Rust 的 `tokio`）在 I/O 上协作式让出。同样的 10,000 个调用可以舒适地存在于一个进程中。在 LLM 智能体规模下，异步不是优化——而是架构本身。

例外：CPU 密集型后处理（嵌入、分词器技巧）仍然需要线程或进程。将 I/O 层与 CPU 层分开。

### Bedi 的反方观点

《Scaling Agentic Software》（Ashpreet Bedi，2026）认为，大多数团队在测量负载之前就过度设计了。务实的默认方案：

- FastAPI + Postgres。
- 每个智能体运行是一行；状态原地更新，使用乐观并发控制。
- 后台任务通过 `pg_notify` 或简单的 Celery 工作进程实现。
- 应用程序代码中的重试策略。

对于大约 100 个并发智能体运行且任务可管理的负载，这通常就足够了。在测量到失败时才升级。

规则：只有在遇到简单架构无法解决的具体问题时，才采用持久执行框架。过早采用会耗费时间在无回报的仪式上。

### 恰好一次语义

对于付费的智能体运行，你需要“恰好一次有效”（至少一次交付 + 幂等消费者）。工程要点：

- **每次运行的去重键。** 包含在每一个外部影响调用中。
- **发件箱模式。** 外部影响首先写入表，然后由单独的进程执行。两个步骤都是幂等的。
- **补偿事务。** 当外部影响成功但其跟踪写入失败时，调度补偿。

这些是数据库工程模式，而非 LLM 特有。LLM 带来的额外开销仅仅是 LLM 调用缓慢；其他都是标准的分布式系统问题。

### 彩虹部署

Anthropic 的多智能体研究系统使用“彩虹部署”：多个版本的智能体运行时同时运行，这样长时间运行的智能体在每次代码部署时不必被杀死。在新版本上对部分流量进行金丝雀测试；当旧版本的智能体完成后将其退役。

这是长时间运行的有状态系统的标准做法；2026 年的调整是，智能体可能存活数小时，因此部署周期必须适应。

### 典型生产环境检查清单

- 持久状态（检查点、快照，或发件箱 + 可重放日志）。
- 幂等的外部影响。
- 用于 LLM 调用的异步 I/O 层。
- 至少一次交付 + 去重。
- 有状态工作负载的彩虹/金丝雀部署。
- 可观测性：每智能体追踪、超级步骤审计、重试计数器。

## 构建

`code/main.py` 实现了：

- `CheckpointStore` — 基于 SQLite 的检查点日志，使用线程 ID 作为键。每个超级步骤追加一行。
- `run_with_checkpoint(agent, thread_id)` — 模拟运行中途崩溃；第二个工作进程从最后一个检查点恢复。
- `AgentQueue` — 每智能体空闲/处理/响应状态机，带有一个小型工作队列。
- `demo_async_vs_threads()` — 通过 asyncio 和线程运行 500 个并发模拟“LLM 调用”；报告 wall-clock 时间和峰值内存（近似）。

运行：

```
python3 code/main.py
```

预期输出：检查点恢复在模拟崩溃后成功；异步版本在不到 1 秒内处理 500 个并发调用；线程版本耗时数秒，并且每个并发单元消耗的内存数量级更高。

## 交付

典型的生产环境强化：

- **从简单开始（Bedi 规则）。** 使用 FastAPI + Postgres，直到你测量到它失败。
- **在优化之前先做好一切度量。** 每次运行的延迟直方图、每步时间、重试次数、失败分类。
- **外部影响的发件箱模式。** 特别是支付和外部 API 调用。
- **彩虹部署。** 绝不在部署过程中杀死正在进行的智能体运行。
- **当遇到特定问题时采用持久执行引擎（Temporal / LangGraph / Restate）**，例如：长达一小时的人工在环等待、跨区域协调、复杂的重试/补偿策略。
- **I/O 层使用异步。** 仅 CPU 密集型后处理才使用线程。

## 练习

1. 运行 `code/main.py`。确认检查点恢复正常工作；测量异步与线程并发性的差异。
2. 实现一个**发件箱**表：每个工具调用首先写入发件箱，然后由单独的 goroutine/任务执行。通过运行两次工具调用来验证幂等性。
3. 模拟**彩虹部署**：两个并发运行时版本；将一半新 thread_id 路由到每个版本；确认旧版本上的正在进行的线程不会被中断。
4. 阅读 LangGraph 的运行时文档（下方链接）。确定运行时的哪些功能在自建 FastAPI + Postgres 版本中需要最长时间来复制。这是否构成采用的理由，或者你可以推迟？
5. 阅读 MegaAgent（arXiv:2408.09955）第 3 节。明确的两层协调（组内 + 组间管理聊天）。画出如何将其映射到具有两个队列族的消息队列。

## 关键术语

| 术语 | 人们所说的含义 | 实际含义 |
|------|----------------|------------------------|
| 持久执行 | "持久化程序状态" | 引擎在每个超级步骤后写入状态；崩溃恢复是确定性的。 |
| 超级步骤 | "事务边界" | 检查点之间的工作单元。LangGraph 术语。 |
| thread_id | "智能体运行标识符" | 绑定检查点和恢复逻辑的键。 |
| 幂等性 | "安全重试" | 重复执行外部影响产生与一次尝试相同的结果。 |
| 发件箱模式 | "解耦外部影响" | 将意图写入表；单独的执行器执行并标记完成。 |
| 至少一次交付 | "可能重复" | 消息队列语义；去重键使消费者变成有效一次。 |
| 彩虹部署 | "重叠版本" | 长时间运行的工作负载期间，多个运行时版本并发存在。 |
| 异步 fiber | "协作式让出" | 用户态并发；对于 I/O 密集型负载，比线程更廉价。 |
| 检查点 | "状态快照" | 在超级步骤边界处的序列化状态；恢复的关键。 |
