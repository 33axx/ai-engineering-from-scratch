# AlphaEvolve — 进化式编码智能体

> 将前沿编码模型与进化循环和机器可检查的评估器配对。让循环运行足够长的时间。它能发现一种4x4复矩阵乘法过程，仅使用48次标量乘法——这是56年来首次超越Strassen的改进。它还找到了一套Google全域Borg调度启发式策略，在生产中恢复了约0.7%的集群计算资源。架构故意设计得平淡无奇。胜利来自评估器的严谨。

**类型:** 学习
**语言:** Python (stdlib, 进化循环示例)
**前置条件:** Phase 15 · 01 (长周期框架), Phase 15 · 02 (自推理)
**时间:** 约60分钟

## 问题

大型语言模型可以编写代码。进化算法可以在代码空间中搜索。两者都分别尝试了数十年，但都遇到了天花板。LLM的天花板是虚构化：模型编写看起来合理的代码，但实际并非其所声称的那样。进化的天花板是搜索成本：对语法进行随机突变很少能产生可编译的程序，更不用说更好的程序了。

AlphaEvolve (Novikov 等人, DeepMind, arXiv:2506.13131, 2025年6月) 将两者结合。LLM对程序数据库提出有针对性的编辑；自动评估器对每个变体打分；高分变体成为未来世代的父代。LLM负责编写合理代码这一昂贵步骤；评估器负责捕获虚构内容。循环运行数小时到数周。

报告的结果：4x4复矩阵乘法的48次标量乘法（Strassen的1969年边界为49），Google生产环境中的Borg调度启发式策略，32.5%的FlashAttention内核加速，Gemini训练吞吐量改进。

该架构之所以有效，是因为评估器是机器可检查的。在评估器不具备这一特性的领域，它就不起作用。这种不对称性正是关键教训。

## 概念

### 循环

1. 从种子程序 `P_0` 开始，该程序正确但非最优。
2. 维护一个变体程序数据库，每个变体都由评估器打分。
3. 从数据库中采样一个或多个父代（基于MAP-elites或岛屿模型）。
4. 提示LLM（对于许多候选者使用Gemini Flash，对于困难任务使用Gemini Pro）生成父代的修改变体。
5. 编译、运行并在保留评估器上评估变体。
6. 根据其得分和特征向量将其插入数据库。
7. 重复。

有两个细节很重要。首先，LLM不仅接收父程序——通常还接收数据库中的几个最佳变体，以及评估器签名和简短任务描述。模型的工作是提出有针对性的更改，可能提高得分。其次，数据库的结构（MAP-elites网格、岛屿模型）旨在保持搜索多样性，而不仅仅是当前领先者。

### 评估器为何不可妥协

AlphaEvolve的所有成功都来自评估器快速、确定且难以被钻空子的领域：

- **矩阵乘法算法**：一个单元测试，将矩阵相乘并按位精确比较结果。
- **Borg调度启发式策略**：一个生产级模拟器，重放历史集群负载并测量浪费的计算资源。
- **FlashAttention内核**：一个正确性测试加上真实硬件上的挂钟基准测试。
- **Gemini训练吞吐量**：每个步骤的实测GPU秒数。

在每种情况下，评估器都能捕获LLM本应占主导的错误类型：虚构的正确性声明、在硬件上不存在的性能声明以及边缘情况下的失败。移除评估器，循环就会优化出漂亮的代码。

### 奖励黑客是同一枚硬币的另一面

进化会优化评估器测量的任何内容。如果评估器不完善，循环就会找到其不完善之处。在未经验证的领域，循环会优化表面特征，而非预期行为。DeepMind在论文中明确指出了这一点：AlphaEvolve的成功仅能迁移到评估器严格性与搜索野心相匹配的领域。

2025-2026年间代码搜索循环中奖励黑客的具体例子：

- 优化目标奖励“完成时间”，从而奖励提交空解决方案。
- 基准测试分数奖励“测试下的正确性”，从而奖励记忆测试和过拟合。
- “代码质量”代理奖励删除注释和重命名变量，而没有语义变化。

AlphaEvolve的修复方案：提供一个LLM从未见过的保留评估器，其输入在评估时生成。即便如此，DeepMind仍建议对任何拟定的部署进行严格审查。

### 为何LLM + 搜索优于任何单一方法

LLM能生成可编译、语义上合理的修改。对2000行Python文件进行随机突变的遗传算法几乎总是产生语法错误。LLM还能将搜索集中在合理的邻域（更改一个函数，而不是随机字节），从而显著减少浪费的评估器调用。

而评估器则负责捕获LLM的虚构内容。LLM会自信地声称某个函数“在极限情况下是O(n log n)”，而实际上它是O(n²)；一次挂钟基准测试就能让问题尘埃落定。

### AlphaEvolve在前沿技术栈中的位置

| 系统 | 生成器 | 评估器 | 领域 | 示例成果 |
|---|---|---|---|---|
| AlphaEvolve | Gemini | 正确性 + 基准测试 | 算法、内核、调度器 | 48次乘法4x4矩阵乘法 |
| FunSearch (DeepMind, 2023) | PaLM / Codey | 正确性 | 组合数学 | cap-set下界 |
| AI Scientist v2 (Sakana, L5) | GPT/Claude | LLM批评 + 实验 | 机器学习研究 | ICLR workshop论文 |
| Darwin Godel Machine (L4) | 智能体脚手架 | SWE-bench / Polyglot | 智能体代码 | 20% → 50% SWE-bench |

这四个都是同一配方（生成器加评估器，循环）的变体。区别在于评估器的评分内容及其严格程度。

## 使用它

`code/main.py`实现了一个极简的类似AlphaEvolve的循环，针对一个示例符号回归问题。其中的“LLM”是一个stdlib代理，它提出对计算目标函数的程序进行小的语法突变。“评估器”在保留测试点上测量均方误差。

观察：

- 随着世代推移，最佳得分如何改善。
- MAP-elites网格如何保持多样化的存活解决方案，从而使循环不会收敛于局部最小值。
- 移除保留测试（仅训练评估器）如何让循环显著过拟合。

## 练习

1. 运行 `code/main.py`。记录最佳得分轨迹。禁用保留评估器（标志 `--no-holdout`）并重新运行。量化过拟合程度。

2. 阅读AlphaEvolve论文第3节关于MAP-elites网格的内容。为某个新问题（例如编译器优化过程）设计一个特征向量描述符，以保持搜索多样性。

3. 4x4矩阵乘法的48次乘法结果在56年后改进了Strassen的49次乘法边界。阅读论文附录F，用三句话解释为什么该问题的评估器特别容易做对，以及为什么大多数领域与它不同。

4. 提出一个AlphaEvolve会失败的领域。明确指出评估器在哪里失效以及为什么。

5. 针对你熟悉的领域，写出你将使用的评估器签名。包括 (a) 正确性条件，(b) 性能指标，(c) 保留输入生成规则，(d) 至少一个反奖励黑客检查。

## 关键术语

| 术语 | 人们通常怎么说 | 实际含义 |
|---|---|---|
| AlphaEvolve | “DeepMind的进化式编码智能体” | Gemini + 程序数据库 + 机器可检查的评估器 |
| MAP-elites | “保持多样性的存档” | 按特征向量键化的网格；每个单元格保存该描述符下的最佳变体 |
| 岛屿模型 | “并行进化子种群” | 独立种群，定期迁移；防止过早收敛 |
| 机器可检查的评估器 | “确定性的神谕” | LLM无法伪造的单元测试、模拟器或基准测试 —— 该循环的先决条件 |
| 奖励黑客 | “优化度量，而非目标” | 循环找到最大化得分的方法，而不执行预期任务 |
| 种子程序 | “起点” | 一个初始正确但次优的程序，循环从它开始进化 |
| 保留评估器 | “LLM从未见过的评估数据” | 在评估时生成的输入，以防止记忆 |
