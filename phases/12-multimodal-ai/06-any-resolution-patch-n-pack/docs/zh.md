# 任意分辨率视觉：补丁打包与 NaFlex

> 真实图像并非 224x224 的方形。一张收据可能是 9:16，一张图表可能是 16:9，一张医学扫描可能是 4096x4096，一张手机截图可能是 9:19.5。2024 年之前的 VLM 做法——将所有图像缩放至固定方形——丢弃了使 OCR、文档理解和高级场景解析能够工作的信号。NaViT（Google, 2023）展示了你可以将可变分辨率的补丁打包到单个 Transformer batch 中，并配合块对角掩码。Qwen2-VL 的 M-RoPE（2024）完全抛弃了绝对位置表。LLaVA-NeXT 的 AnyRes 将高分辨率图像分割为基础图像 + 子图像。SigLIP 2 的 NaFlex 变体（2025）如今已成为开放 VLM 的默认编码器，旨在用一个检查点服务所有宽高比。本课程将端到端实现补丁打包。

**类型：** 构建
**语言：** Python（标准库，补丁打包器 + 块对角掩码）
**先修知识：** 阶段 12 · 01（ViT 补丁），阶段 12 · 05（LLaVA）
**时间：** 约 120 分钟

## 学习目标

- 将一批可变分辨率图像的补丁打包成一个序列，并构建块对角注意力掩码。
- 为给定任务选择 AnyRes 分块（LLaVA-NeXT）、NaFlex（SigLIP 2）或 M-RoPE（Qwen2-VL）。
- 在不调整大小的情况下，计算 OCR、图表和摄影的 token 预算。
- 列举方形缩放的三种失败模式：文本压扁、内容裁剪、填充导致的 token 浪费。

## 问题

Transformer 期望一个序列。一个 batch 是长度相同的序列堆叠。如果你的图像是 224x224，每次你会得到 196 个补丁 token，无需填充，任务完成。用 224 训练，用 224 推理，再也不考虑分辨率。

但现实世界并不配合。文档是竖屏的（8.5x11 英寸，约 2:3）。图表截图是横屏的（16:9）。收据又高又窄（1:3）。医学图像则以 2048x2048 或更大的尺寸传输。移动设备截图是 1170x2532（0.46:1）。

三种 2024 年之前的方案及其失败原因：

1. 缩放至固定方形（224x224 或 336x336）。压扁会扭曲文本和人脸。缩小会破坏图表标签和 OCR 内容。这是 LLaVA-1.5 之前的标准做法。
2. 裁剪至固定宽高比。你丢掉了大部分图像，而选择裁剪位置本身就是一个视觉问题。
3. 填充至最长边。解决了变形问题，但对于竖屏图像会浪费 50% 以上的 token 在填充上。所有填充 token 的二次注意力成本。

2024-2025 的答案：让 Transformer 以图像原始分辨率消费补丁，并弄清楚如何将异构 batch 打包成一个序列而不浪费计算。

## 概念

### NaViT 与补丁打包

NaViT（Dehghani 等人，2023）是证明该方法可在大规模下工作的论文。思路很机械：

1. 对于 batch 中的每张图像，以选定的补丁大小（例如 14）计算其原始补丁网格。
2. 将每张图像的补丁展平为其自身变长序列。
3. 将所有图像的补丁连接成一个长序列作为 batch。
4. 构建一个块对角注意力掩码，使得图像 A 的补丁仅能在图像 A 内部相互关注。
5. 为每个补丁携带位置信息（2D RoPE 或分数位置嵌入）。

三个图像分别为 336x336（576 token）、224x224（256 token）、448x336（768 token）的 batch 将变成一个 1600 token 的序列，带有一个 1600x1600 的块对角掩码。无需填充，无浪费计算。Transformer 处理任意宽高比。

NaViT 还引入了训练时的分数补丁丢弃 —— 在整个 batch 中随机丢弃 50% 的补丁 —— 既可以正则化又能加速训练。SigLIP 2 继承了这一点。

### AnyRes（LLaVA-NeXT）

LLaVA-NeXT 的 AnyRes 是实用替代方案。给定一张高分辨率图像和一个固定编码器（CLIP 或 SigLIP 在 336 分辨率），对图像进行分块：

1. 从预定义集合中选取一个网格布局 —— (1x1), (1x2), (2x1), (1x3), (3x1), (2x2) 等 —— 以最佳匹配图像的宽高比。
2. 将完整图像分割到网格中；每个子块成为一个 336x336 的裁剪。
3. 同时生成一个缩略图：将整张图像缩放到 336x336 作为全局上下文 token。
4. 通过冻结的 336 编码器编码每个子块。将子块 token 与缩略图 token 连接。

对于 672x672 的图像，使用 2x2 网格加缩略图：4 * 576 + 576 = 2880 个视觉 token。代价高昂但有效 —— LLM 同时看到了局部细节和全局上下文。

当你的编码器是冻结的且只支持一种分辨率时，AnyRes 是首选。对于大图像（1344x1344 在 4x4 网格下为 9216 + 576 ≈ 9800 token，几乎填满 8k LLM 上下文），token 数量爆炸式增长。

### M-RoPE（Qwen2-VL）

Qwen2-VL 引入了多模态旋转位置编码。不是 NaViT 的分数位置或 AnyRes 的分块加缩略图，每个补丁携带一个 3D 位置（时间、高度、宽度）。查询/键旋转处理任意 H、W 和时间长度。

M-RoPE 无需重新训练即可实现原生动态分辨率。在推理时，你输入任意 HxW 图像，补丁嵌入器产生 H/14 x W/14 个 token，每个 token 获得其 (t=0, r=行, c=列) 位置，RoPE 以正确频率旋转注意力，完成。Qwen2.5-VL 和 Qwen3-VL 延续了这一点。InternVL3 的 V2PE 是同样的思想，但按模态进行可变编码。

与 AnyRes 不同，M-RoPE 在原生分辨率下 token 数为 O(H x W / P^2) —— 没有乘性分块开销。与 NaViT 不同，它仍期望每次前向传播只有一张图像。跨分辨率批处理仍需在其之上进行补丁打包。

### NaFlex（SigLIP 2）

NaFlex 是 SigLIP 2 检查点的原生灵活模式。单个模型在推理时支持多个序列长度（256、729、1024 token）。内部使用 NaViT 风格的补丁打包进行训练，并为每个补丁使用绝对分数位置。卖点：一个检查点，根据任务在推理时选择你的 token 预算。

对于语义任务（分类、检索），256 token。对于 OCR 或图表理解，1024 token。无需重新训练。

### 打包掩码

块对角掩码是大多数实现卡住的地方。对于总长度为 `N_total`、包含图像 `i=0..B-1` 且长度分别为 `n_i` 的打包序列，形状为 `(N_total, N_total)` 的掩码 `M` 为 1（如果两个索引落在同一图像的块内），否则为 0。你可以从累积长度列表构建它：

```
offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 iff there exists b where offsets[b] <= i < offsets[b+1] and offsets[b] <= j < offsets[b+1]
```

在 PyTorch 中，这可以用一行 `torch.block_diag` 或显式 gather 实现。FlashAttention 的变长路径（`cu_seqlens`）完全跳过掩码，直接使用累积长度张量在序列内部进行注意力 —— 对于典型 batch，比密集掩码快 ~10 倍。

### Token 预算

根据任务选择策略：

- OCR / 文档：1024-4096 token。SigLIP 2 NaFlex 在 1024，或 AnyRes 3x3 + 缩略图。
- 图表和 UI：729-1024 token，在 384-448 原生分辨率下。Qwen2.5-VL 动态分辨率，带有最大像素数上限。
- 自然照片：256-576 token 就够了。下游 LLM 能看够。在高内容密度区域为 token 付费。
- 视频：每帧空间池化后 64-128 token，2-8 FPS。课程 12.17 涵盖此内容。

2026 年的生产规则：为每个任务选择一个最大像素数上限，以原生宽高比编码至该上限，打包 batch，跳过填充。Qwen2.5-VL 暴露了 `min_pixels` 和 `max_pixels` 作为此旋钮。

## 使用它

`code/main.py` 实现了对一批具有整数像素坐标的异构图像的补丁打包。它：

- 接收一个 (H, W) 图像尺寸列表。
- 计算每张图像在补丁大小为 14 时的补丁序列长度。
- 将它们打包成一个总长度为 `sum(n_i)` 的序列。
- 构建块对角注意力掩码（为清晰起见使用密集掩码）。
- 比较打包成本与方形缩放和 AnyRes 分块的成本。
- 打印混合 batch（收据、图表、截图、照片）的 token 预算表。

运行它。得出的数字解释了为什么每个 2026 年的开放 VLM 都使用补丁打包。

## 交付

本课程产生 `outputs/skill-resolution-budget-planner.md`。给定一个混合宽高比的工作负载（OCR、图表、照片、视频帧）和一个总 token 预算，它选择正确的策略（NaFlex、AnyRes、M-RoPE 或固定方形），并输出每个请求的配置。当你为产品确定 VLM 规模时使用此技能 —— 它能防止静默的 10 倍 token 激增，从而避免破坏延迟预算。

## 练习

1. 一张收据为 600x1500（1:2.5）。补丁大小为 14 时，原生分辨率 token 数是多少？缩放至 336 方形后呢？在实践中哪种做法会丢失更多 OCR 精度？

2. 为四个长度分别为 256、576、729、1024 的图像构建块对角掩码。验证注意力矩阵为 2585x2585，且恰好有 `256^2 + 576^2 + 729^2 + 1024^2` 个非零元素。

3. 对于 1792x896 的图像，补丁大小为 14，比较：(a) 缩放至 336 方形后编码，(b) AnyRes 2x1 加缩略图，(c) M-RoPE 在原生分辨率下。哪种使用的 token 最少？哪种保留的细节最多？

4. 实现分数补丁丢弃：给定一个打包序列，均匀随机丢弃 50% 的 token，并相应更新块对角掩码。测量掩码稀疏度的变化。

5. 阅读 Qwen2-VL 论文（arXiv:2409.12191）第 3.2 节。用两句话描述 `min_pixels` 和 `max_pixels` 控制什么，以及为什么这两个界限都很重要。

## 关键术语

| 术语 | 通常说法 | 实际含义 |
|------|----------|----------|
| 补丁打包 | "NaViT 风格的打包" | 将不同图像的变长补丁序列连接成一个 batch 维度 |
| 块对角掩码 | "打包掩码" | 注意力掩码，将每张图像的补丁限制为仅自我关注，而不是打包中的邻居 |
| AnyRes | "LLaVA-NeXT 分块" | 将高分辨率图像分割成固定大小的子块网格加上全局缩略图；用固定编码器编码每个子块 |
| NaFlex | "SigLIP 2 原生灵活" | 单个 SigLIP 2 检查点，推理时可服务于 256/729/1024 token 预算，无需重新训练 |
| M-RoPE | "多模态 RoPE" | 3D 旋转位置编码（时间、行、列），无需位置表即可处理任意 H、W、T |
| cu_seqlens | "FlashAttention 打包" | FlashAttention 变长路径使用的累积长度张量，替代密集的块对角掩码 |
| min_pixels / max_pixels | "分辨率边界" | Qwen2.5-VL 的每请求旋钮，用于限制非常小或非常大的输入上的 token 数量 |
| 视觉 token 预算 | "每张图像多少个 token" | 每张图像发出的补丁 token 的大致数量；决定了 LLM 的 prompt 预算和注意力成本 |
