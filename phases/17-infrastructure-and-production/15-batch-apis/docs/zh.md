# 批量 API——50% 折扣已成为行业标准

> 每家主流提供商都提供异步批量 API，享受 50% 折扣和约 24 小时周转。OpenAI、Anthropic、Google 以及大多数推理平台（Fireworks batch tier、Together batch）都实现了相同的模式。如果将批处理与提示缓存结合，过夜管道的成本可降至同步非缓存成本的约 10%。规则非常简单：如果不是交互式的，就应该走批处理。内容生成管道、文档分类、数据提取、报告生成、批量标注、目录标签——任何能容忍 24 小时延迟的工作负载，如果不迁移到批处理，就是在浪费钱。2026 年的生产模式是将每个新的 LLM 工作负载分为三类：交互式（同步+缓存）、半交互式（异步队列+回退）、批处理（过夜、缓存输入叠加）。那些假装是交互式但实际能容忍几分钟延迟的工作负载，浪费最为严重。

**类型：** 学习
**语言：** Python (stdlib, toy batch-vs-sync cost simulator)
**前置知识：** Phase 17 · 14 (Prompt & Semantic Caching)
**时间：** ~45 分钟

## 学习目标

- 说出三家提供商的批量 API（OpenAI、Anthropic、Google）以及通用的 50% 折扣 + 24小时周转保证。
- 计算在过夜分类工作负载上叠加批处理+缓存输入的成本，并与同步非缓存基线进行比较。
- 将工作负载分为交互式/半交互式/批处理三类，并说明分类理由。
- 说出两个陷阱：部分交互性（用户期望快于 24 小时）和输出模式漂移（不同提供商的批处理文件格式不同）。

## 问题

你的团队负责一个夜间报告生成管道。50,000 份文档，每份进行摘要、聚类摘要、起草执行简报。同步运行需要 4 小时，每晚花费 2,000 美元。你听说了批量 API。

批处理给你 50% 折扣。你还在系统提示（所有 50k 次调用共享）上启用了提示缓存。叠加后，账单降至每晚 180 美元——约为基线的 9%。同一管道，只需三个配置变更。

批量是 LLM 成本工具包中最便宜但没人去用的杠杆。原因主要是组织层面的：团队在 SLA 实际上是“早晨之前”时，却想着“实时”。本课就是关于不要把 90% 的账单白白浪费。

## 概念

### 三大批量 API

**OpenAI Batch API**：JSONL 文件上传，包含请求列表。承诺 24 小时周转（实际通常 ~2-8 小时）。输入和输出令牌享受 50% 折扣。端点 `/v1/batches`。符合缓存条件的输入还可额外享受缓存输入定价。

**Anthropic Message Batches**：JSONL 上传。24 小时周转。50% 折扣。支持 `cache_control`——缓存写入是显式的，读取在批处理中自动发生。

**Google Vertex AI Batch Prediction**：BigQuery 或 GCS 输入。Gemini 同样享受 50% 折扣。与 Vertex 管道集成。

### 语义：异步，而非慢速

批处理是“我承诺在 24 小时内返回”——而不是“这需要 24 小时”。典型的 P50 是 2-6 小时。提供商会将你的批处理安排在非高峰时段，此时 GPU 库存利用率较低。

### 与缓存叠加

一个 50k 文档摘要任务，使用相同的 4K 令牌系统提示：

- 同步非缓存：50000 × ($input × 4000 + $output × 200) 按全价计算。
- 同步缓存：系统提示在第一次写入后缓存；剩余 49999 次输入的输入成本降低 10 倍。
- 批处理缓存：上述所有优惠，再加上读写均享受 50% 折扣。

叠加结果：批处理 + 缓存 ≈ 同步非缓存账单的 10%。任何在夜间运行且具有共享系统提示的工作负载都应使用此方式。

### 工作负载分类

**交互式**——用户等待响应。TTFT（首令牌时间）重要。同步调用并使用提示缓存。不能走批处理。

**半交互式**——用户提交任务，几分钟后回来查看。异步队列，如果批处理不可用则回退到同步。例如中等规模的 RAG 索引。

**批处理**——用户期望“早晨之前”或“下一个小时”得到结果。内容管道、大规模分类、离线分析。总是走批处理，总是叠加缓存。

常见错误：因为管道是生产环境就把所有东西都归类为交互式。生产环境不是延迟规格——SLA 才是。

### 部分交互性陷阱

某些功能看起来是交互式的，但实际上能容忍 5-10 分钟。例如：一份夜间客户健康报告，带有一个“刷新”按钮。用户点击刷新，等待 10 分钟也没关系。团队却用同步方式实现。50 个并发刷新，成本是批处理并通过邮件发送的 10 倍。

要问的问题是：“对于这个用户来说，24 小时意味着什么？”如果答案是“他们不会注意到”，那就用批处理。

### 输出模式陷阱

不同提供商的批处理文件格式不同：

- OpenAI：JSONL，每行一个请求。
- Anthropic：JSONL，每行一条消息；响应格式嵌入其中。
- Vertex：BigQuery 表或 GCS 前缀加 TFRecord。

编写“一个批处理客户端”来适配所有提供商，意味着每个提供商需要适配代码。那些宣称支持多提供商批处理的网关（Portkey、LiteLLM 的部分层级）仍然只是对原始格式的薄封装。

### 你应该记住的数字

- 各提供商的批处理折扣：输入+输出统一 50%。
- 周转 SLA：保证 24 小时，典型 P50 为 2-6 小时。
- 批处理+缓存输入叠加：约为同步非缓存成本的 10%。
- 工作负载分类规则：如果可接受 24 小时延迟，则始终走批处理。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|------------|----------|
| Batch API | "异步折扣" | 50% 折扣，24 小时周转 |
| JSONL | "批量格式" | 每行一个 JSON 请求；OpenAI/Anthropic 标准格式 |
| Message Batches | "Anthropic 批量" | Anthropic 的批量 API 产品名称 |
| Batch prediction | "Vertex 批量" | Vertex AI 的批量 API 产品 |
| Turnaround SLA | "24 小时承诺" | 保证，并非典型值；典型值为 2-6 小时 |
| Workload triage | "交互性决策" | 交互式/半交互式/批处理的路由决策 |
| Output schema | "响应格式" | 每个提供商的 JSONL 布局；不可移植 |
| Stacked discount | "批处理+缓存" | 两者同时应用时，约为非缓存同步账单的 10% |
