# 无服务器 LLM 的冷启动缓解

> 一个 20GB 的模型镜像从冷状态到提供服务需要 5-10 分钟（7B 模型）到 20 分钟以上（70B 模型）。在真正的无服务器世界中，这不是预热——而是宕机。缓解措施在五个层面运作：预植入节点镜像（AWS 上的 Bottlerocket，双卷架构）、模型流式加载（NVIDIA Run:ai Model Streamer，vLLM 原生支持）、GPU 内存快照（Modal 检查点，重启速度提升 10 倍）、热池（`min_workers=1`）、分层加载（ServerlessLLM 的 NVMe→DRAM→HBM 流水线，延迟降低 10-200 倍），以及传输输入 token（KB）而非 KV 缓存（GB）的实时迁移。Modal 公布的最低冷启动时间为 2-4 秒；Baseten 默认 5-10 秒，通过预热可实现亚秒级。本课程教你如何测量、预算并叠加这五个层面。

**类型：** 学习
**语言：** Python（标准库，玩具冷启动路径模拟器）
**前置知识：** 阶段 17 · 02（推理平台经济学）、阶段 17 · 03（GPU 自动扩缩）
**时间：** 约 60 分钟

## 学习目标

- 列举冷启动缓解的五个层面，并说明每个层面的一种工具或模式。
- 计算 70B 模型的总冷启动时间，作为（节点供应）+（权重下载）+（权重加载到 HBM）+（引擎初始化）之和。
- 解释为什么实时迁移传输的是输入 token（KB）而不是 KV 缓存（GB），以及代价是什么（重计算）。
- 说明热池的权衡（为空闲 GPU 付费或接受冷启动尾部延迟），以及 `min_workers > 0` 成为强制要求的 SLA 阈值。

## 问题

你的无服务器 LLM 端点会在夜间缩减到零。早上 8 点流量激增。第一个请求需要等待：

1. Karpenter 供应一个 GPU 节点：45-60 秒。
2. 容器拉取一个 30GB 的镜像（包含权重）：120-300 秒。
3. 引擎将权重加载到 HBM：45-120 秒，取决于模型大小和存储速度。
4. vLLM 或 TRT-LLM 初始化 CUDA 图、KV 缓存池、分词器：10-30 秒。

总计：220-510 秒（大约 3-8 分钟）才能返回一个 token。你的 SLA 是 2 秒。你部署了一个热池（`min_workers=1`），问题似乎消失了——但现在你需 24x7 为一台空闲 GPU 付费。如果你的服务有 5 个产品，每个都有一个热副本，那就是每月 5 × 24 × 30 = 3600 GPU 小时，无论是否有用户调用。

冷启动缓解的关键在于保持无服务器的经济性，同时逼近始终在线的延迟。

## 概念

### 第一层——预植入节点镜像（Bottlerocket）

在 AWS 上，Bottlerocket 的双卷架构将操作系统与数据分离。用预拉取容器镜像的数据卷创建快照；在 `EC2NodeClass` 中引用快照 ID。新节点启动时权重已在本地 NVMe 上——第 2 步和第 3 步的一部分消失。与 Karpenter 原生配合。典型收益：大型模型每次冷启动节省 2-4 分钟。

在 GCP 上的等效方法：自定义 VM 镜像并预烘焙容器层。在 Azure 上：使用相同模式的托管磁盘快照。

### 第二层——模型流式加载（Run:ai Model Streamer）

无需在回答第一个请求之前加载完整文件，而是逐层将权重流式加载到 GPU 内存，并在第一个 Transformer 块驻留后立即开始处理。NVIDIA Run:ai Model Streamer 在 vLLM 2026 中原生提供。适用于 S3、GCS 和本地 NVMe。通过将 I/O 与计算设置重叠，大型模型的权重加载时间大约减半。

### 第三层——GPU 内存快照（Modal）

Modal 在首次加载后获取 GPU 状态（权重、CUDA 图、KV 缓存区域）的检查点。后续重启直接反序列化到 HBM——比重新初始化快 10 倍。这是最接近“在 2 秒内启动热 GPU”的方法。权衡：快照是特定于 GPU 拓扑的，因此如果 Karpenter 将你迁移到不同的 SKU，你需要重新创建检查点。

### 第四层——热池（min_workers=1）

最简单的缓解措施：始终保持一个副本就绪。成本是一台 GPU 的 24x7 小时费率。对于小型模型来说计算很残酷（你支付 $0.85-$1.50/小时来避免 30 秒的冷启动），对于大型模型则相对温和（支付 $4/小时来避免 5 分钟的冷启动）。热池成为强制要求的 SLA 阈值通常是：70B+ 模型上 TTFT P99 < 60 秒。

### 第五层——分层加载（ServerlessLLM）

ServerlessLLM 将存储视为一个层次结构：NVMe（快速但容量大）、DRAM（中等但分层）、HBM（极小但零延迟）。权重预加载到 DRAM；按需加载到 HBM。论文报告相比天真的磁盘到 HBM 加载，冷加载延迟降低 10-200 倍。生产采用仍处于早期，但已存在与 vLLM 的集成。

### 第六层——实时迁移（额外模式）

当节点不可用时（Spot 实例被回收、节点排空），传统模式是冷启动另一个副本并排空请求队列。实时迁移将输入 token（千字节）传输到已加载模型的目标节点，并在目标节点上重新计算 KV 缓存。重计算比通过网络传输数 GB 的 KV 缓存更便宜。适用于分离式部署。

### 热池的计算

对于一个 P99 TTFT SLA 为 2 秒的服务，问题不是“是否使用热池”，而是“多少个热副本，以及哪些路径需要它们”。

- 高价值交互路径（实时聊天、语音助手）：`min_workers=1-2`。
- 后台批处理路径（夜间分类）：接受缩到零，容忍 5-10 分钟的冷启动。
- 高级层：按租户配备 `min_workers`，具有专用容量。

### 先测量再优化

70B 模型在全新节点上的冷启动剖析（示意）：

| 阶段 | 时间 | 缓解措施 |
|------|------|----------|
| 节点供应 | 50 秒 | Bottlerocket + 预植入镜像、热池 |
| 镜像拉取 | 180 秒 | 预植入数据卷（消除） |
| 权重加载到 HBM | 75 秒 | 模型流式加载（减半）；GPU 快照（消除） |
| 引擎初始化 | 20 秒 | 持久化 CUDA 图缓存 |
| 首次前向传播 | 3 秒 | 最小固有延迟 |
| **冷启动总计** | **328 秒** | |
| **采用缓解措施后总计** | **约 15 秒** | 22 倍降低 |

### 你应该记住的数字

- Modal 冷启动：2-4 秒（使用 GPU 快照）。
- Baseten 默认冷启动：5-10 秒；通过预热可达亚秒。
- 原始 70B 冷启动：3-8 分钟。
- Run:ai Model Streamer：权重加载速度提升约 2 倍。
- ServerlessLLM 分层加载：延迟降低 10-200 倍（论文数据）。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| Cold start | “大停顿” | 从请求到新副本返回第一个 token 的时间 |
| Warm pool | “始终在线最小值” | `min_workers >= 1`，以保持至少一个副本就绪 |
| Pre-seeded image | “烘焙 AMI” | 容器权重预驻留的节点镜像 |
| Bottlerocket | “AWS 节点 OS” | AWS 容器优化操作系统，支持双卷快照 |
| Model streamer | “流式加载” | 将权重 I/O 与计算设置重叠 |
| GPU snapshot | “检查点到 HBM” | 序列化加载后的 GPU 状态；重启时反序列化 |
| Tiered loading | “NVMe + DRAM + HBM” | 存储层级体系；按需加载 |
| Live migration | “移动 token” | 传输输入（KB），在目标端重新计算 KV |
| `min_workers` | “热副本” | 无服务器最小保持活跃的副本数 |
| Scale-to-zero | “完全无服务器” | 空闲时零成本；接受完整的冷启动代价 |
