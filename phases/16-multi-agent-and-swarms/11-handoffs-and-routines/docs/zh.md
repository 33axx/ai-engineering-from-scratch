# 交接与例程——无状态编排

> OpenAI的Swarm（2024年10月）将多智能体编排提炼为两个原语：**例程**（作为系统提示的指令+工具）和**交接**（返回另一个Agent的工具）。没有状态机，没有分支DSL——LLM通过调用正确的交接工具来路由。OpenAI Agents SDK（2025年3月）是生产级后继版本。Swarm本身仍然是最清晰的概念参考——其全部源码仅几百行。这种模式之所以流行，是因为API表面大致是“agent = 提示 + 工具；交接 = 返回agent的函数”。局限性：无状态，因此内存是调用方的问题。

**类型：** 学习+构建
**语言：** Python（标准库）
**前置条件：** 阶段16·04（基础模型）
**时间：** 约60分钟

## 问题

每个多智能体框架都想让你学习它的DSL：LangGraph的节点和边、CrewAI的团队和任务、AutoGen的GroupChat和管理器。这些DSL是真正的抽象，但它们让事情显得比实际更复杂。

Swarm朝着相反的方向推进：利用模型已有的工具调用能力。交接变成工具调用。编排器是当前持有对话的智能体。状态机隐式地存在于智能体的系统提示中。

## 概念

### 两个原语

**例程。** 定义智能体角色和可用工具的系统提示。可以把它想象成一小组限定范围的指令：“你是一个分流智能体；如果用户询问退款，则移交给退款智能体。”

**交接。** 智能体可以调用的一个工具，它返回一个新的Agent对象。Swarm运行时会检测到Agent返回值，并在下一轮切换活跃智能体。

这就是整个抽象。

```
def transfer_to_refunds():
    return refund_agent  # Swarm sees Agent return → switch active agent

triage_agent = Agent(
    name="triage",
    instructions="Route the user to the right specialist.",
    functions=[transfer_to_refunds, transfer_to_sales, transfer_to_support],
)
```

分流智能体的系统提示使其根据用户消息选择合适的交接。LLM的工具调用完成路由。

### 为什么流行

- **小型API。** 只需学习两个概念。
- **利用模型已有的能力。** 工具调用在各个提供商中已经是生产级特性。
- **无状态机负担。** 你不需要描述图；智能体的提示描述了它们要移交给谁。

### 无状态的取舍

Swarm在运行之间明确是无状态的。框架在运行期间会保留消息历史，但不持久化任何内容。内存、连续性、长任务——全部是调用方的问题。

在生产中（OpenAI Agents SDK，2025年3月），这是主要变化之一：SDK在保留交接原语的同时，增加了内置的会话管理、护栏和追踪。

### Swarm/交接适用场景

- **分流模式。** 一线智能体将用户路由到专家。
- **基于技能的移交。** “如果任务需要代码，调用编码器；如果需要研究，调用研究员。”
- **简短、有边界的对话。** 客户支持、FAQ到工单、简单工作流。

### Swarm困难场景

- **带有共享内存的长会话。** 交接会将对话状态重置为新智能体的提示加历史记录。如果没有调用方管理的内存，跨智能体没有持久状态。
- **并行执行。** 交接是逐个进行的——活跃智能体切换。并行性需要调用方编排多个Swarm运行。
- **审计与重放。** 无状态运行难以精确重放；LLM的交接选择不是确定性的。

### OpenAI Agents SDK（2025年3月）

生产级后继版本增加了：

- **会话状态。** 跨运行持久化线程。
- **护栏。** 输入/输出验证钩子。
- **追踪。** 每次工具调用和交接都会被记录。
- **交接过滤器。** 控制在交接时传递哪些上下文。

交接原语保留下来；围绕它增加了生产级的人体工程学。

### Swarm vs GroupChat

两者都使用LLM驱动的路由，但在**谁选择下一个**上存在差异：

- GroupChat：一个选择器（函数或LLM）从外部选择下一个发言者。
- Swarm：当前智能体通过调用交接工具选择自己的后继者。

Swarm是“智能体决定下一步”；GroupChat是“管理器决定下一步”。Swarm的决策存在于活跃智能体的工具调用中；GroupChat的决策存在于`GroupChatManager`中。

## 构建它

`code/main.py` 从头实现Swarm：一个Agent数据类、一个交接机制（工具返回Agent）以及一个检测智能体切换的运行循环。

演示：一个分流智能体路由到退款、销售或支持专家。每个专家都有自己的工具。运行循环打印每次交接。

运行：

```
python3 code/main.py
```

## 使用它

`outputs/skill-handoff-designer.md` 为给定任务设计一个交接拓扑：存在哪些智能体，它们可以调用哪些交接，以及传递哪些上下文。

## 交付它

清单：

- **交接日志记录。** 每次交接写入一个追踪事件，包含来源智能体、目标智能体、上下文快照。
- **上下文传递规则。** 决定交接时传递什么：完整历史（昂贵）、最后N条消息，或一个摘要。
- **交接护栏。** 移交到具有不同工具权限的专家必须经过身份验证——否则提示注入可能强制进行不需要的交接。
- **循环检测。** 两个智能体来回交接是常见故障；使用简单的最后K步环检查来检测。
- **后备智能体。** 如果交接目标不存在，回退到安全默认值。

## 练习

1. 运行 `code/main.py`，分流到退款智能体。确认第二轮活跃智能体是退款。
2. 添加循环检测规则：如果同一对智能体连续交接了3次，强制退出。设计回退方案。
3. 阅读OpenAI Agents SDK关于交接过滤器的文档。实现一个“交接时摘要”版本：传出智能体在传入智能体接管前将上下文压缩为要点摘要。
4. 比较Swarm交接与GroupChatManager选择器。哪个模式会使提示注入更严重，为什么？
5. 阅读Swarm cookbook（https://developers.openai.com/cookbook/examples/orchestrating_agents）。找出Swarm做出的一项明确设计决策，该决策在OpenAI Agents SDK中被更改或保留。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|------------|----------|
| 例程 | “智能体提示” | 系统提示 + 工具列表。定义角色和可用的交接。 |
| 交接 | “转移到另一个智能体” | 活跃智能体可以调用的一个工具，返回一个新的Agent。运行时切换活跃智能体。 |
| 无状态 | “运行之间没有内存” | Swarm不持久化任何东西；内存是调用方的责任。 |
| 活跃智能体 | “谁在说话” | 当前持有对话的智能体。交接改变此对象。 |
| 上下文传递 | “交接时传递什么” | 传入智能体看到的历史记录策略：完整、最后N条或摘要。 |
| 交接循环 | “智能体乒乓” | 两个智能体不断互相交接的故障模式。 |
| OpenAI Agents SDK | “生产级Swarm” | 2025年3月后继版本；在交接原语之上增加了会话、护栏、追踪。 |
| 交接过滤器 | “传输关卡” | SDK功能，用于在交接边界检查并修改上下文。 |
