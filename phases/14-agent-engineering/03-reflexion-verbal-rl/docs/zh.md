# 反思：口头强化学习

> 基于梯度的强化学习需要数千次试验和 GPU 集群来修复一个失败模式。反思（Shinn 等人，NeurIPS 2023）用自然语言完成：每次失败的试验后，智能体写下一段反思，存入情景记忆中，并在下一次试验时基于该记忆进行条件化。这是 Letta 的睡眠时间计算、Claude Code 的 CLAUDE.md 学习以及 pro-workflow 的 learn-rule 背后的模式。

**类型：** 构建
**语言：** Python（标准库）
**前置知识：** 第 14 阶段 · 01（智能体循环），第 14 阶段 · 02（ReWOO）
**时间：** 约 60 分钟

## 学习目标

- 说出反思的三个组件（执行器、评估器、自我反思器）以及情景记忆的作用。
- 使用标准库实现一个包含二元评估器、反思缓冲区和全新重试的反思循环。
- 根据给定任务，在标量、启发式和自我评估的反馈来源之间进行选择。
- 解释为什么口头强化能捕捉到基于梯度的强化学习需要数千次试验才能修复的错误。

## 问题

智能体任务失败。在标准强化学习中，你需要再运行数千次试验，计算梯度，更新权重。昂贵、缓慢，而且绝大多数生产环境中的智能体不会为每次失败分配训练预算。

反思（Shinn 等人，arXiv:2303.11366）提出了一个不同的问题：如果智能体只是思考自己为什么失败，然后带着这个思考重新尝试，结果会怎样？无需权重更新，无需梯度。只需在试验之间存储自然语言。

结果是：在 ALFWorld 上，它击败了 ReAct 和其他未经微调的基线。在 HotpotQA 上，它改进了 ReAct。在代码生成（HumanEval/MBPP）上，它达到了当时的最高水平。所有这一切都不需要一次梯度更新。

## 概念

### 三个组件

```
Actor         : generates a trajectory (ReAct-style loop)
Evaluator     : scores the trajectory — binary, heuristic, or self-eval
Self-Reflector: writes a natural-language reflection on the failure
```

再加上一个数据结构：

```
Episodic memory: list of prior reflections, prepended to the next trial's prompt
```

一次试验运行执行器。评估器为其打分。如果分数低，自我反思器生成一条反思（“我选错了工具，因为我误以为问题问的是 X，而实际问的是 Y”）。反思进入情景记忆。下一次试验重新开始，但会看到这条反思。

### 三种评估器类型

1. **标量** — 外部二元信号。ALFWorld 成功或失败，HumanEval 测试通过或不通过。最简单，信号最强。
2. **启发式** — 预定义的失败特征。例如：“如果智能体连续两次产生相同动作，标记为卡住。”“如果轨迹超过 50 步，标记为低效。”
3. **自我评估** — 大语言模型对自己的轨迹打分。当没有真实标签时使用。信号较弱；最好与基于工具的验证配合使用（第 05 课 — CRITIC）。

2026 年的默认做法是混合使用：有标量时用标量，没有时用自我评估，启发式作为安全护栏。

### 为什么这种模式能泛化

反思与其说是一种新算法，不如说是一种命名模式。几乎所有生产环境中的“自愈”智能体都在运行某种变体：

- Letta 的睡眠时间计算（第 08 课）：一个独立的智能体反思过去的对话并写入记忆块。
- Claude Code 的 `CLAUDE.md` / “保存记忆”模式：将反思作为学习收获捕获，并前置到未来的会话中。
- pro-workflow 的 `/learn-rule` 命令：将修正捕获为显式规则。
- LangGraph 的反思节点：一个节点对输出进行评分，并在需要时路由到改进路径。

所有这些都源自同一个洞察：自然语言足以承载“我从失败中学到了什么”并在不同运行之间传递。

### 何时有效，何时无效

反思在以下情况下有效：

- 存在明确的失败信号（测试失败、工具错误、错误答案）。
- 任务类型是可复现的（同样类型的问题可以再次被提问）。
- 反思有改进轨迹的空间（有足够的行动预算）。

反思在以下情况下无帮助：

- 智能体已经第一次就成功。
- 失败是外部原因（网络断开、工具损坏）——反思“网络断开了”对未来运行无帮助。
- 反思变成了迷信——存储关于一次偶发性不稳定运行的故事。

2026 年陷阱：记忆腐烂。反思不断累积，有些已经过时或错误；重新运行随着情景缓冲区的增长而变慢。缓解措施：定期压缩（第 06 课），为反思设置 TTL，或者使用一个独立的睡眠时间清理智能体（Letta）。

## 构建

`code/main.py` 在一个玩具谜题上实现了反思：生成一个三元组列表，其和等于目标值。执行器生成候选列表；评估器检查总和；自我反思器写下一行描述哪里出了问题。反思进入情景记忆以供下一次试验使用。

组件：

- `Actor` — 一个脚本化的策略，在看到反思时会改进。
- `Evaluator.binary()` — 目标总和的通过/失败判断。
- `SelfReflector` — 生成一行对失败诊断的描述。
- `EpisodicMemory` — 具有 TTL 语义的有界列表。

运行它：

```
python3 code/main.py
```

追踪显示三次试验。试验 1 失败，存储反思；试验 2 看到反思并有所改进但仍失败；试验 3 成功。与基线运行（无反思）比较——基线会卡在试验 1 的答案上。

## 使用

LangGraph 将反思作为节点模式内置。Claude Code 的 `/memory` 命令和 pro-workflow 的 `/learn-rule` 将情景缓冲区外部化为一个 Markdown 文件。Letta 的睡眠时间计算在空闲时间运行自我反思器，从而使主智能体保持低延迟。OpenAI Agents SDK 没有直接提供反思；你需要通过自定义护栏（根据分数拒绝轨迹）和跨运行持久化的内存 `Session` 来构建它。

## 部署

`outputs/skill-reflexion-buffer.md` 创建并维护一个具有反思捕获、TTL 和去重功能的情景缓冲区。给定任务类型和一次失败，它会生成一条对下一次试验真正有帮助的反思（而不是一句泛泛的“再仔细些”）。

## 练习

1. 将二元评估器切换为返回距离度量（距离目标有多远）的标量评估器。它能更快收敛吗？
2. 为反思添加 10 次试验的 TTL。在此之后，旧的反思是有害还是有益？
3. 实现启发式评估器：如果相同动作重复出现，则标记为卡住。这如何与自我反思器交互？
4. 使用一个忽略反思的对抗性执行器运行反思。要迫使执行器注意到反思，最小的反思提示工程是什么？
5. 阅读反思论文中关于 ALFWorld 的第 4 节。概念性地重现 130% 的成功率提升：与普通 ReAct 相比，关键差异是什么？

## 关键术语

| 术语 | 人们通常所说的 | 实际含义 |
|------|----------------|------------------------|
| 反思 (Reflexion) | “自我修正” | Shinn 等人 2023 — 执行器、评估器、自我反思器加情景记忆 |
| 口头强化 (Verbal reinforcement) | “无梯度学习” | 将自然语言反思前置到下一次试验的提示中 |
| 情景记忆 (Episodic memory) | “每任务反思” | 针对同一任务类别的先前反思的有界缓冲区 |
| 标量评估器 (Scalar evaluator) | “二元成功信号” | 基于真实标签的通过/失败或数值评分 |
| 启发式评估器 (Heuristic evaluator) | “基于模式的检测器” | 预定义的失败特征（例如卡住循环、步骤过多） |
| 自我评估器 (Self-evaluator) | “大语言模型对自己的轨迹进行评判” | 无真实标签时的低信号回退方案——与基于工具的验证配合使用 |
| 记忆腐烂 (Memory rot) | “过时反思” | 情景缓冲区被过时条目填满；通过压缩/TTL 修复 |
| 睡眠时间反思 (Sleep-time reflection) | “异步自我反思” | 在非关键路径上运行自我反思器，使主智能体保持快速 |
