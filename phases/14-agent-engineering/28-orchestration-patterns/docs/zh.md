# 编排模式：监督者、群体、层次

> 到 2026 年，有四种编排模式在框架中反复出现：监督者-工作者、群体/点对点、层次、辩论。Anthropic 的指导是：“关键在于构建适合你需求的系统。”从简单开始；只有当单个智能体加上五种工作流模式不足时，才添加拓扑结构。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置条件：** 阶段 14 · 12（工作流模式），阶段 14 · 25（多智能体辩论）  
**用时：** 约 60 分钟

## 学习目标

- 说出四种反复出现的编排模式及其各自适用的场景。
- 描述 2026 年 LangChain 的建议：基于工具调用的监督 vs 监督者库。
- 解释 Anthropic 的“构建正确系统”原则及其如何决定拓扑结构的选择。
- 在标准库中针对一个脚本化的 LLM 实现所有四种模式。

## 问题所在

团队往往在真正需要之前就急于采用“多智能体”。四种模式在框架中反复出现；一旦你能说出它们的名字，就能选出正确的那个——或者干脆跳过拓扑结构。

## 概念

### 监督者-工作者

- 一个中央路由 LLM 将任务分发给专业智能体。
- 决策：返回自身、转交给专业智能体、终止。
- 专业智能体之间不直接通信；所有路由都通过监督者。

框架：LangGraph 的 `create_supervisor`、Anthropic 的 orchestrator-workers、CrewAI 的 Hierarchical Process。

**2026 年 LangChain 建议：** 通过直接工具调用来实现监督，而不是使用 `create_supervisor`。这样可以更精细地控制上下文工程——你可以精确决定每个专业智能体看到什么。

### 群体 / 点对点

- 智能体通过共享的工具接口直接进行转交。
- 没有中央路由器。
- 延迟低于监督者模式（跳数更少）。
- 更难以推理（没有单一控制点）。

框架：LangGraph 的群体拓扑、OpenAI Agents SDK 的转交（当所有智能体都可以相互转交时）。

### 层次

- 监督者管理子监督者，子监督者管理工作线程。
- 在 LangGraph 中作为嵌套子图实现；在 CrewAI 中作为嵌套 crew 实现。
- 可扩展到大量智能体群体，但代价是操作复杂性增加。

何时需要：当单个监督者的上下文预算无法容纳所有专业智能体的描述时。

### 辩论

- 并行提议者 + 迭代交叉批评（课程 25）。
- 更像是验证而非编排——但在框架中作为一种拓扑选择出现。

### CrewAI 的 Crew 与 Flow

CrewAI 形式化了两种部署模式：

- **Flow** 用于确定性的事件驱动自动化（建议作为生产环境的起点）。
- **Crew** 用于自主的基于角色的协作。

这与上述四种模式正交，但映射到拓扑：Flow 通常是监督者或层次；Crew 通常是监督者配合 LLM 路由器。

### Anthropic 的指导

“在 LLM 领域，成功不在于构建最复杂的系统。而在于构建适合你需求的系统。”

决策顺序：

1. 单个智能体 + 工作流模式（课程 12）——从这里开始。
2. 监督者-工作者——当你拥有 2-4 个专业智能体时。
3. 群体——当延迟比推理清晰度更重要时。
4. 层次——仅当监督者上下文预算不足时。
5. 辩论——当准确性比成本更重要时。

### 这种模式可能出错的地方

- **拓扑优先思维。** “我们需要多智能体”而没有明确多智能体解决什么问题。
- **群体中的来回转交。** A -> B -> A -> B。使用跳数计数器。
- **虚假层次。** 因为“企业级”而搞三层；实际上只有两个团队。应该合并。

## 动手构建

`code/main.py` 在标准库中针对一个脚本化的 LLM 实现了所有四种模式：

- `Supervisor`——中央路由器。
- `Swarm`——带有直接转交的点对点。
- `Hierarchical`——监督者的监督者。
- `Debate`——并行提议者 + 批评。

每种模式处理相同的三意图任务（退款 / 缺陷 / 销售）。轨迹形状不同。

运行：

```
python3 code/main.py
```

输出：每种模式的轨迹 + 操作次数。监督者模式最清晰；群体模式最短；层次模式最深；辩论模式最昂贵。

## 使用场景

- **LangGraph** 用于监督者和层次模式（嵌套子图）。
- **OpenAI Agents SDK** 用于作为工具的转交（监督者模式）。
- **CrewAI Flow** 用于生产环境中的确定性流程。
- **自定义实现** 用于辩论模式或需要精确控制时。

## 练习

1. 将一个监督者-工作模式转换为群体模式，移除路由器。什么会出问题？什么会改善？
2. 给群体模式添加一个跳数计数器：超过 3 次转交后拒绝。它能捕捉到 A->B->A 的来回转交吗？
3. 为一个有 12 个专业智能体的领域构建一个两层的层次系统。如果没有嵌套，上下文预算会在哪里失败？
4. 对四种模式进行性能分析，使用类似生产环境的工作负载。哪种模式在哪个指标上胜出（延迟、成本、准确性、可调试性）？
5. 阅读 Anthropic 的“Building Effective Agents”博文。将你的每个生产流程映射到四种模式之一。有哪个无法清晰映射吗？

## 关键术语

| 术语 | 人们常说 | 实际含义 |
|------|----------|----------|
| 监督者-工作者 | “路由器 + 专业智能体” | 中央 LLM 分发给专业智能体；它们之间不直接通信 |
| 群体 | “点对点” | 通过共享工具直接转交；无中央路由器 |
| 层次 | “监督者的监督者” | 用于大量智能体的嵌套子图 |
| 辩论 | “提议者 + 批评” | 并行提议者，交叉批评（课程 25） |
| 基于工具调用的监督 | “无需库的监督者” | 将监督者实现为直接工具调用以控制上下文 |
| Crew | “自主团队” | CrewAI 基于角色的协作模式 |
| Flow | “确定性工作流” | CrewAI 事件驱动的生产模式 |
