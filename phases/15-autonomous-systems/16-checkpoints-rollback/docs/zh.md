# 检查点与回滚

> 每个图状态转换都会被持久化。当工作节点崩溃时，其租约过期，另一个工作节点从最新的检查点接替。Cloudflare Durable Objects 可将状态保持数小时或数周。先提议后提交（第15课）为每个动作定义了回滚计划。操作后验证闭环。EU AI Act 第14条要求高风险系统必须实施有效的人类监督——在实践中，这意味着检查点必须可查询，回滚必须经过演练，审计跟踪必须能在部署后存活。典型的故障模式：如果没有幂等键和前置条件检查，在短暂故障后的重试可能导致已批准的动作被重复执行。操作后验证正是用来捕获这种问题的。

**类型：** 学习
**语言：** Python（标准库，检查点与回滚状态机）
**前置条件：** 第15阶段·12（持久化执行），第15阶段·15（先提议后提交）
**时间：** 约60分钟

## 问题

持久化执行（第12课）使崩溃的智能体可恢复。先提议后提交（第15课）使已批准的动作可审计。本课将两者结合：当已批准的动作部分执行、崩溃然后恢复时会发生什么？回滚在何时运行，针对什么状态？

现实系统采用不同的连接方式：

- **LangGraph** 将每次图状态转换检查点记录到 PostgreSQL。工作节点崩溃后，租约释放，另一个工作节点从最新检查点恢复。工作流在 `interrupt()` 处暂停，该操作本身也会被持久化。
- **Cloudflare Durable Objects** 将每个键的状态保持数小时或数周。将计算与已批准动作的存储放在一起。
- **Microsoft Agent Framework** 在工作流 API 中暴露 `Checkpoint` 原语；重播加幂等性覆盖了重试。

在每种情况下，真正有效的组合都是：幂等键（防止重复执行）+ 前置条件检查（状态仍与我们批准时一致）+ 操作后验证（副作用实际发生了）+ 验证失败时回滚。

## 概念

### 每个转换都持久化

图状态转换是指将工作流从一个命名状态迁移到另一个命名状态的任何步骤。简单的实现只在特定提交点持久化；生产实现则持久化每个转换。代价（少量额外写入）相对于可靠性收益（重播可落到任何位置，租约恢复精确）而言很小。

### 租约恢复

当工作节点崩溃时，工作流不会丢失；租约（一个短期的声明，表明该工作节点正在执行此运行）只是过期。另一个工作节点拾取最新的检查点并恢复。租约机制使得生产系统能够在滚动部署期间幸存而不丢失进行中的工作。

### 幂等性与前置条件

仅靠幂等性是不够的。考虑：工作流被批准“在余额大于 1000 时从 A 转账 100 到 B”。工作流已提交，中途崩溃，然后恢复。如果只检查幂等键，并且执行恢复，则转账执行一次（正确）。但考虑在崩溃和恢复之间，A 的余额通过另一个工作流降至 500。幂等检查仍然通过，但前置条件不通过。如果没有前置条件检查，我们就会导致透支。

每个重要动作都需要两者：

- **幂等键**：防止重复执行。
- **前置条件检查**：确认状态仍与批准时所依据的状态一致。

### 操作后验证

“工具返回 200”不是验证。真正的验证是重新读取目标状态并确认副作用确实发生了。模式：

- 数据库更新：`UPDATE ... RETURNING *` 然后断言返回的行与预期状态一致。
- 发送邮件：提交后在已发送文件夹中检查消息 ID。
- 文件写入：读回文件并计算哈希。
- API 调用：对目标资源进行后续 `GET`。

如果验证失败，工作流进入已知的坏状态。回滚启动。

### 回滚计划

先提议后提交（第15课）中的每个重要动作都带有一个回滚计划。类型：

- **带内回滚**：直接逆转副作用（`INSERT` 后的 `DELETE`，发送后的发送修正邮件）。
- **补偿事务**：一个中和原始动作的新动作（标准 SAGA 模式）。
- **带外回滚**：通知人类，暂停工作流，将坏状态留给调查。

无操作回滚（“我们无法撤销这个”）必须在提议中指明。没有回滚的动作需要更强的提交时人工介入（第15课挑战-响应）。

### EU AI Act 第14条的操作性解读

第14条要求高风险系统必须实施“有效的人类监督”。在操作层面，实施者将其解读为：

- 检查点可由审计员查询。
- 回滚需要演练（至少端到端测试一次）。
- 审计跟踪必须能在部署后存活（检查点后端不是临时性的）。
- 失败的验证必须发出警报，而不是静默记录。

如果一个工作流在提交中途崩溃、恢复、完成副作用而没有验证+回滚路径，则该工作流无法通过第14条测试。

### 典型故障模式：重复执行

该领域最常见的生产事故：

1. 动作被批准，幂等键为 k。
2. 提交开始，执行，返回 200。
3. 工作流在持久化“已提交”状态之前崩溃。
4. 工作流恢复；看到“已批准但未提交”；重新执行。
5. 副作用触发两次。

缓解措施：在执行之前持久化一个“进行中”的意图，使用幂等键执行，然后仅在操作后验证成功后才标记“已提交”。如果动作已触发但状态写入失败，你知道要验证并（如有必要）重新触发。如果状态写入成功但动作失败，你通过恢复路径验证并精确触发一次。

## 使用

`code/main.py` 实现了一个带有幂等性、前置条件、验证和回滚的检查点工作流。驱动程序模拟了四种场景：干净运行、崩溃后重试（幂等性捕获）、前置条件失败（工作流中止而不触发）、验证失败（回滚触发）。

## 输出

`outputs/skill-rollback-rehearsal.md` 为提议的工作流设计了一个回滚演练测试，并审计了检查点后端的审计跟踪持久性。

## 练习

1. 运行 `code/main.py`。验证四个场景。对于提交期间崩溃的情况，确认动作在重试中恰好执行一次。

2. 修改“先标记完成再执行”的模式，使状态写入在动作之后发生。重新运行崩溃场景。测量有多少重复动作被触发。

3. 为特定的生产动作（例如“发布到 Slack 频道”）设计一个回滚计划。分类为带内、补偿或带外。说明选择理由。

4. 选择一个你熟悉的工作流。识别每个状态转换。为每个标记持久性要求（持久化/不持久化）。统计目前未持久化的数量。

5. 演练回滚测试：设计一个端到端测试，运行真实工作流，使其崩溃，并确认回滚路径被触发。测试断言什么？
