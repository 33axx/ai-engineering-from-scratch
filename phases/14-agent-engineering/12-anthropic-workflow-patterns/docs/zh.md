# Anthropic 工作流模式：简单优于复杂

> Schluntz 和 Zhang（Anthropic，2024 年 12 月）区分了工作流（预定义的路径）和智能体（动态使用工具）。五种工作流模式覆盖了大多数场景。从直接 API 调用开始。仅在无法预测步骤时引入智能体。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置知识：** 阶段 14 · 01（智能体循环）  
**时间：** ~60 分钟  

## 学习目标

- 说出 Anthropic 的五个工作流模式：提示链、路由、并行化、编排器-工作者、评估器-优化器。
- 解释智能体与工作流的区别以及每种模式对应的工程成本。
- 识别何时选择工作流而非智能体（反之亦然）。
- 在标准库中使用模拟 LLM 实现全部五种模式。

## 问题所在

团队经常为那些本可以用单个函数调用解决的问题选择多智能体框架。代价是真实的：框架增加了层次，模糊了提示，隐藏了控制流，并引入了过早的复杂性。Schluntz 和 Zhang 在 2024 年 12 月的文章是业界最常引用的反例：从简单开始，只在复杂性值得投入时才添加。

## 概念

### 工作流 vs 智能体

- **工作流：** 通过预定义的代码路径编排的 LLM 和工具。工程师拥有图的控制权。
- **智能体：** LLM 动态地引导自己的工具并自主执行步骤。模型拥有图的控制权。

两者各有其适用场景。工作流成本更低、速度更快、更容易调试。智能体能够解决开放式问题，但使得故障模式更难推理。

### 增强型 LLM

所有五种模式的基础：一个 LLM 配备了三种能力——搜索（检索）、工具（动作）、记忆（持久化）。任何 API 调用都可以使用这些能力。

### 五种模式

1. **提示链：** 第一次调用的输出是第二次调用的输入。适用于任务具有清晰的线性分解结构时。步骤之间可以设置程序化的门控。

2. **路由：** 一个分类器 LLM 选择调用哪个下游 LLM 或工具。适用于不同类型输入需要不同处理（例如，一级支持 vs 退款 vs 缺陷 vs 销售）。

3. **并行化：** 并发运行 N 个 LLM 调用，汇总结果。两种形式：分区（不同分块）和投票（相同提示，N 次运行，多数/综合）。

4. **编排器-工作者：** 一个编排器 LLM 动态决定运行哪些工作者（也是 LLM），并综合它们的输出。类似于智能体循环，但编排器不会无限循环。

5. **评估器-优化器：** 一个 LLM 提出答案，另一个 LLM 评估它。迭代直到评估器通过。这是 Self-Refine（第 05 课）的泛化形式。

### 工作流优于智能体的场景

- **可预测的任务：** 如果可以枚举步骤，就应该这样做。
- **成本受限的任务：** 工作流具有有界的步骤数量；智能体可能无限扩展。
- **合规性受限的任务：** 审计人员希望读取图结构，而不是从轨迹中推断它。

### 智能体优于工作流的场景

- **开放式研究：** 当下一步取决于上一步返回的内容时。
- **不定长度的任务：** 分钟到小时的工作量，步骤数未知。
- **新领域：** 当还不知道正确的工作流时——先探索，后定型。

### 上下文工程的配套方法

“针对 AI 智能体的有效上下文工程”（Anthropic 2025）将这一配套学科形式化：200k 窗口是一个预算，而非一个容器。包括什么、何时压缩、何时允许上下文增长。在本课程的阶段 14 上下文压缩课程（阶段 14 早期课程 06，在重新编号之前）中详细讨论。

## 动手构建

`code/main.py` 使用 `ScriptedLLM` 实现了全部五种工作流模式：

- `prompt_chain(input, steps)` — 顺序执行
- `route(input, classifier, handlers)` — 分类 + 分发
- `parallel_vote(prompt, n, aggregator)` — N 次运行，汇总
- `orchestrator_workers(task, workers)` — 编排器选择工作者
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` — 迭代直到通过

运行：

```
python3 code/main.py
```

每种模式都会打印其执行轨迹。每种模式的代码量大约在 10-15 行之间；使用框架的成本则以千行单位计算。

## 应用实践

- 大多数任务使用直接 API 调用。
- 只有当模式确实需要持久状态（LangGraph）、actor 模型并发（AutoGen v0.4）或角色模板（CrewAI）时才使用框架。
- 当希望获得类似 Claude Code 的工具形态但又不想从头构建时，考虑使用 Claude Agent SDK。

## 交付输出

`outputs/skill-workflow-picker.md` 为给定的任务描述选择正确的模式，包括决策理由以及在工作流不足以满足需求时重构为智能体的路径。

## 练习

1. 实现带置信度阈值的路由。低于阈值 → 升级给人工处理。对于一级支持用例，阈值应该落在哪里？
2. 为 `parallel_vote` 添加超时。当一个调用挂起时会发生什么？如何汇总有缺失的投票？
3. 将 `evaluator_optimizer` 改造成一种“赌博机”：在多次迭代中保留前两个输出，以免后期好的结果被后期坏的结果覆盖。
4. 将提示链与路由结合：一个路由器选择三条链中的一条。测量与单个大提示方案相比的代币成本。
5. 选择一个你生产环境中的功能。绘制工作流图。统计步骤数。在这里使用智能体真的会更好吗？

## 关键术语

| 术语 | 人们通常说的 | 实际含义 |
|------|-------------|----------|
| 工作流 | "预定义流程" | 工程师拥有 LLM 和工具调用图的控制权 |
| 智能体 | "自主 AI" | 模型拥有图控制权；动态工具引导 |
| 增强型 LLM | "带工具的 LLM" | LLM + 搜索 + 工具 + 记忆；原子单元 |
| 提示链 | "顺序调用" | 第 N 次调用的输出是第 N+1 次调用的输入 |
| 路由 | "分类器分发" | 选择哪个链/模型来处理该输入 |
| 并行化 | "扇出" | N 个并发调用；通过分区或投票汇总 |
| 编排器-工作者 | "调度器智能体" | 编排器 LLM 动态选择专家 LLM |
| 评估器-优化器 | "提议者 + 评审者" | 迭代直到评估器通过；Self-Refine 的泛化 |
