# 共享内存与黑板模式

> 在2026年的多智能体系统中，两种方法共存：**消息池**（每个人都能看到所有人的消息，如AutoGen GroupChat或MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如Context-Aware MCP或Matrix框架）。两者都是多智能体系统中唯一有状态的部分——也就是说，它们也是有趣bug的滋生地。典型的失败模式是**记忆中毒**：一个智能体幻觉出一个“事实”，其他智能体将其视为已验证，准确率逐渐衰减，这种衰减比立即崩溃更难调试。本课程将用stdlib构建这两种结构，注入中毒攻击，并展示三种在实际生产中有效的缓解措施。

**类型：** 学习 + 构建  
**语言：** Python (stdlib, `threading`)  
**前置条件：** 阶段 16 · 04（原始模型），阶段 16 · 09（并行蜂群网络）  
**时间：** 约 75 分钟

## 问题

多智能体系统需要一个地方让智能体共享事实。一种字面上的选择是“在消息中传递一切”——但这等于用额外的复制重新发明共享状态。另一种是“给每个人一个全局日志”——但全局日志会无界增长且容易中毒。第三种是“为每个智能体投影一个视图”——可扩展但模式沉重。

当其中一个智能体产生幻觉并将幻觉写入共享状态时，每个读取该状态的下游智能体都将幻觉当作事实。等到人类察觉时，推理链已经深入五步，而根因却是第三条写入的消息。调试多智能体准确率衰减比调试崩溃更难。

这就是记忆中毒。它是MAST分类学（Cemri等人，arXiv:2503.13657）中记录第二多的失败家族，并且是结构性的：任何没有溯源和不可写验证者的共享内存设计最终都会出现这种问题。

## 概念

### 两种主要拓扑

**全消息池。** 每个智能体读取每一条消息。AutoGen GroupChat 和 MetaGPT 使用这种模式。简单、透明、可检查，但无法扩展到约10个智能体以上，因为每个智能体的上下文会被其他智能体的工作填满。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；底层只路由相关的消息。CA-MCP（arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）使用这种模式。可扩展性更好，但需要预先设计模式以使订阅有意义。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 各自何时胜出

- **全池** 在智能体数量少（<10）、异构且对话时间短时胜出。当每个人都能看到一切时，推理谁说了什么是微不足道的。
- **黑板** 在智能体数量多、角色同质但实例众多（蜂群）且对话时间长时胜出。路由节省了代币成本和上下文污染。

生产系统往往混合使用：顶层（规划层）使用小全池，下层（工作层）使用黑板。

### 记忆中毒，一个场景

三个智能体处理一个研究任务。智能体A是检索智能体。智能体B是摘要生成器。智能体C是分析师。

1. A获取一个页面并向共享状态写入一条消息：“研究报告了42%的准确率提升。”
2. 实际上获取的页面说的是“4.2%的提升”。A幻觉了小数点。
3. B读取共享状态，写道：“报告了巨大的42%准确率提升（来源：A）。”
4. C读取共享状态，写道：“建议采用——42%的提升具有变革性。”
5. 最终报告引用了一个从未存在过的42%数字。

没有智能体崩溃。没有测试失败。系统“正常工作”。幻觉从一个智能体的上下文通过共享状态传播到了每个下游智能体的推理中。

### 为什么这是结构性的

没有共享状态时，智能体A的幻觉停留在A的上下文中。下游智能体会重新获取或重新推导，可能发现错误。而使用朴素的共享状态，A的上下文变成了所有人的上下文，幻觉被洗白成事实。

问题不在于共享状态本身——而在于**没有溯源且没有独立验证者**的共享状态。三种缓解措施解决了这个问题：

1. **在每次写入时标注溯源。** 共享状态中的每条记录都记录谁写的、何时写的、在什么提示下写的，以及（如果适用）智能体引用的来源。下游智能体根据溯源以怀疑态度读取。
2. **版本化写入；采用仅追加方式。** 修正是一条替换旧条目的新条目，而不是原地更新。审计线索得以保留。
3. **至少保留一个不能写入共享状态的智能体。** 一个只读验证者智能体抽样检查条目，重新获取来源，并标记不一致之处。由于它不能写入池中，因此不会被池中毒。

### 黑板先例（Hayes-Roth, 1985）

黑板模式比LLM智能体早了四十年。Hayes-Roth（1985年，《一种用于控制的黑板架构》）描述了专业的知识源（Knowledge Sources），它们观察全局黑板，贡献部分解决方案，并触发其他知识源。2026年的黑板（CA-MCP, Matrix）是相同的模式，只是将LLM智能体作为知识源，将JSON blob作为部分解决方案。早期文献已经记录了写冲突、机会性控制和一致性的解决方案，现代系统正在重新发现这些方案。

### 投影 vs 全视图

纯黑板给每个订阅者相同的投影（按主题范围筛选）。更激进的设计是**每个智能体投影**：每个智能体获得一个针对其角色定制的视图。LangGraph的状态规约器（reducers）是2026年的典型实现——规约函数将全局状态折叠成角色特定的切片。

每个智能体投影的可扩展性更强，但需要模式。没有模式，你就要在每个智能体的提示中临时重建投影。

### 写冲突模式

多个智能体同时写入是一个并发问题，不仅仅是LLM问题。三种模式有效：

- **顺序写入器（单一生产者）。** 所有写入都经过一个协调智能体进行序列化。简单，但会成为瓶颈。
- **带版本化的乐观并发控制。** 每条记录都有一个版本；写入者在版本不匹配时失败并重试。经典的数据库技术。
- **主题分区。** 不同的智能体拥有不同的主题。没有跨主题冲突。需要设计好的分区边界。

大多数2026框架默认使用顺序写入器，因为LLM调用足够慢，冲突很少发生，瓶颈不会造成很大影响。

### 不可写验证者

最关键的缓解措施是只读验证者。实现规则：

- 验证者与团队共享状态（读取黑板或池）。
- 验证者没有共享状态的写入句柄——只有到单独验证通道的写入句柄。
- 验证者独立获取写入中引用的来源。标记不一致之处。
- 验证者自身的输出被路由给人类或单独的决策智能体，绝不反馈回池中。

如果没有这种分离，验证者的输出会成为池中的新条目，这意味着中毒的池会毒害验证者，进而毒害其验证结果。

## 构建它

`code/main.py` 使用stdlib Python实现了两种拓扑，加上一个玩具中毒攻击和三种缓解措施。

- `MessagePool` — 线程安全、仅追加的日志，支持完全读取。
- `Blackboard` — 按主题键的发布/订阅，支持每个智能体订阅。
- `ProvenanceEntry` — 每次写入记录 (写入者, 时间戳, 提示哈希, 来源URI)。
- `PoisoningScenario` — 运行一个三智能体研究任务，其中智能体A幻觉了小数点。输出最终报告。
- `Verifier` — 一个只读智能体，重新获取来源并标记不一致之处。在验证者存在的情况下运行相同的场景。

运行：

```
python3 code/main.py
```

预期输出：
- 运行1（无验证者）：幻觉的42%传播到最终报告。
- 运行2（有验证者）：验证者标记不一致之处，池被标记为“已标记”，最终报告包含撤回。

## 使用它

`outputs/skill-memory-auditor.md` 是一项技能，用于审计任何多智能体系统的共享内存设计，检查其溯源、版本化和验证者分离。在生产环境之前，在新的多智能体架构上运行它。

## 交付它

对于任何共享内存设计：

- 在每次写入时记录溯源：`(写入者, 时间戳, 提示哈希, 引用的工具调用, 来源URI)`。
- 让日志仅追加。修正是引用被取代条目的新条目。
- 部署至少一个具有独立来源访问权限的只读验证者智能体。
- 将验证者输出路由到单独的通道，而不是返回共享池。
- 记录作为替代写入的写入比率——上升的比率是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认运行1传播了幻觉，运行2捕捉到了它。
2. 添加第二个幻觉：智能体B编造了一个数据集大小。验证者应该无需针对两者手工调整就能同时捕捉到。
3. 将全池切换为具有主题分区（`prices`, `summaries`, `analyses`）的黑板。主题分区使哪些中毒场景更难实现，又对哪些场景无帮助？
4. 阅读 Hayes-Roth（1985年，《一种用于控制的黑板架构》）。指出论文中本课程未讨论的两个控制模式，这些模式对2026系统有益。
5. 阅读 CA-MCP（arXiv:2601.11595）。将其共享上下文存储映射到 `code/main.py` 中的 `MessagePool` 或 `Blackboard` 类。CA-MCP 在此基础上添加了哪些原语？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|----------------|------------------------|
| Message pool | “共享聊天历史” | 每个智能体读取的仅追加日志。完全透明，扩展性差。 |
| Blackboard | “共享工作空间” | 按主题键的发布/订阅。智能体订阅相关主题。扩展性更好。 |
| Provenance | “谁写了什么” | 每次写入的元数据：写入者、时间戳、提示、来源。 |
| Memory poisoning | “幻觉扩散” | 一个智能体的错误进入共享状态，下游智能体将其当作事实。 |
| Append-only | “无原地更新” | 修正是替代旧条目的新条目。保留审计线索。 |
| Unwritable verifier | “独立审计员” | 只读智能体，重新获取来源并标记不一致之处。 |
| Projection | “作用域视图” | 从全局状态计算出的每个智能体视图。LangGraph规约器是典型例子。 |
| Knowledge Source | “专家智能体” | Hayes-Roth 1985年对黑板参与者的术语。 |
