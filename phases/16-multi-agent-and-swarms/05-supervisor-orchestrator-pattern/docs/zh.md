# Supervisor / 编排器-工作者模式

> 一个主导智能体制定计划并委派任务；专业工作者在并行的上下文环境中执行任务并报告结果。这是Anthropic的研究系统（Claude Opus 4作为主导，Sonnet 4作为子智能体）背后的模式，在内部研究评测中比单智能体Opus 4高出+90.2%。Anthropic的工程博文报告称，BrowseComp上80%的方差仅由token用量解释——多智能体之所以胜出，很大程度上是因为每个子智能体都获得全新的上下文窗口。本课程从原语出发构建supervisor模式，并涵盖2026年生产部署中的工程经验。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`threading`）  
**前置条件：** 阶段16 · 04（原始模型）  
**时间：** 约75分钟

## 问题

研究是单智能体系统无法完成的典型任务。你问“2023年到2026年间多智能体系统发生了什么变化？”一个智能体依次读取五篇论文，用它们的文本填充了半个上下文窗口，然后必须对它们一起推理。当它读到第五篇时已经忘记了第一篇。它无法并行化。

Supervisor模式解决了这个问题：一个主导智能体制定搜索计划，将每个子问题委派给一个工作者，并进行综合。每个工作者都有自己的200k token窗口来处理一个狭窄的问题。主导智能体永远看不到原始论文——只看到工作者的总结。

Anthropic的生产研究系统报告称，在内部研究评测中比单个Opus 4高出+90.2%。同一篇博文指出，BrowseComp上80%的方差由*token用量*解释。每个子智能体获得全新上下文是主要机制。

## 概念

### 模式

```
                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context
```

主导智能体从不阅读原始材料。工作者在主导进行综合之前也看不到彼此的工作。每个箭头都是一次带有窄工件的交接。

### 为什么它会赢

三种机制：

1. **每个子智能体的全新上下文。** 一个探索“FIPA-ACL传统”的工作者不会携带主导计划时花费的40k tokens。它针对一个问题获得200k窗口。
2. **通过提示实现专业化。** 主导的提示是“分解并综合”，而不是“研究”。每个工作者的提示很窄：“找出X中发生了什么变化”。专注的提示产生专注的输出。
3. **并行性。** 工作者并发运行。墙上时间大致是`max(worker_times) + plan + synthesis`，而不是`sum(worker_times)`。

### 工程经验（Anthropic 2025）

Anthropic的博文列出了几条生产经验，至今（2026年）仍然相关：

- **根据查询复杂度调整工作量。** 简单查询：一个智能体，3-10次工具调用。复杂查询：10个以上智能体。主导必须自行评估这一点，而不是由调用者评估。
- **先宽后窄。** 首先分解为宽泛的子问题，然后如果答案需要深入，再为每个子问题生成更多工作者。
- **彩虹部署。** 智能体是长时间运行且有状态的。传统的蓝绿部署不起作用。Anthropic使用彩虹部署：新版本逐步推出，同时旧版本逐渐排空。
- **token用量占主导。** 多智能体约为单智能体的15倍token。仅当任务价值证明成本合理时才运行。

### LangGraph的转变

LangGraph最初发布了`langgraph-supervisor`库，带有一个高层`create_supervisor`助手。2025年，LangChain将建议转向通过直接工具调用来实现supervisor模式，因为工具调用能更好地控制*supervisor看到什么*（上下文工程）。该库仍然可用；但文档现在推荐工具调用的形式。

### 失败模式

- **主导幻觉出计划。** 如果主导生成的子问题并未分解真实问题，工作者会在错误的目标上进行精确研究。
- **工作者过度探索。** 没有明确的范围边界，工作者会偏离分配的子问题，污染综合步骤。
- **综合冲突。** 两个工作者返回矛盾的事实。主导必须要么重新提问（增加一轮），要么明确记录分歧。默默选择其中一方是最糟糕的失败：用户永远不知道发生了分歧。

### 何时不适合使用supervisor

- **顺序任务。** 如果步骤2确实需要步骤1的输出，并行性毫无意义。使用流水线（CrewAI Sequential，LangGraph线性图）。
- **简单查询。** 单智能体处理得更快且更便宜。在派生工作者之前，使用主导的“调整工作量”检查。
- **严格确定性。** Supervisor使用LLM选择的委派。当可审计/重放比适应性更重要时，静态图更好。

## 构建它

`code/main.py` 使用 `threading` 实现了包含三个并行工作者的supervisor。主导将查询分解为子问题，工作者在每个子问题上并发运行，主导进行综合。没有真正的LLM——工作者被脚本化为模拟获取和总结。

关键结构：

- `Lead.plan(query)` 将查询拆分为3个子问题。
- `Worker.run(sub_q)` 返回一个伪造的摘要（在生产中可以是任何使用工具的智能体）。
- `Lead.run(query)` 在线程中启动工作者，等待它们完成，然后综合。

运行：

```
python3 code/main.py
```

输出显示计划、带有开始/结束时间戳的并行工作者追踪，以及最终的综合结果。你可以看到墙上时间的优势：三个0.3秒的工作者在约0.35秒内完成，而不是0.9秒。

## 使用它

`outputs/skill-supervisor-designer.md` 接受用户查询，生成supervisor模式设计：主导系统提示、工作者角色、子问题分解规则以及综合模板。在构建新的研究类智能体系统之前使用此工具。

## 部署它

部署supervisor模式前的检查清单：

- **模型配对。** 主导使用推理级模型（Opus类，`o3`类）。工作者使用更快、更便宜的模型（Sonnet，`o4-mini`）。
- **工作者超时。** 任何运行时间超过中位时间2倍的工作者将被终止；主导要么以更窄的范围重新生成，要么跳过它继续。
- **每个工作者的token上限。** 硬限制（例如预期综合输入的10倍）防止失控的工作者超出预算。
- **可观测性。** 追踪主导的计划、每个工作者的工具调用以及综合结果。这是任何事后调试的基础。
- **彩虹部署。** 有状态的长时间运行智能体需要逐步版本过渡，而不是热切换。

## 练习

1. 运行 `code/main.py`，然后修改主导使其生成5个工作者而不是3个。观察墙上时间的效果。在这个演示中，工作者数量达到多少时生成开销超过了并行节省？
2. 实现工作者超时：终止任何运行超过0.5秒的工作者，并让主导综合剩余结果。你需要哪些可观测性来知道一个工作者被截断了？
3. 在主导的综合步骤中添加冲突检测步骤：如果两个工作者返回矛盾答案，主导记录分歧而不是选择其中一个。在不调用LLM的情况下，如何检测矛盾？
4. 阅读Anthropic的研究系统工程博文。列出三个本玩具演示需要采纳才能在生产中运行的做法。
5. 比较LangGraph的 `create_supervisor`（旧版）与新的工具调用推荐。哪个能更好地控制supervisor看到什么？为什么Anthropic在综合中明确只传递子答案而不是原始工作者上下文？

## 关键术语

| 术语 | 人们常说 | 实际含义 |
|------|----------|----------|
| Supervisor | “主导智能体” | 一个编排智能体，负责计划、委派和综合。它自己不执行具体工作。 |
| Worker | “子智能体” | 由supervisor调用的专门智能体，具有狭窄的范围和自己的上下文窗口。 |
| Orchestrator-worker | “supervisor模式” | 同一事物，不同名称。2026年的文献两者都用。 |
| Fresh context | “干净窗口” | 工作者的上下文从其系统提示和分配的问题开始，而不是主导的历史记录。 |
| Rainbow deployment | “逐步推出” | 长时间运行的有状态智能体需要带版本控制的排空替换，而不是蓝绿部署。 |
| Token dominance | “上下文是变量” | 根据Anthropic，80%的研究评测方差来自总token使用量，而非模型选择。 |
| Scale effort | “根据复杂度匹配智能体数量” | 主导评估查询难度，相应地生成1个或10个以上工作者。 |
| Synthesis conflict | “工作者意见不一致” | 两个工作者返回矛盾的事实；主导必须暴露分歧，而不是默默选择其中之一。 |
