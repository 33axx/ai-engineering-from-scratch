# LLM 路由层 —— LiteLLM、OpenRouter、Portkey

> 厂商锁定代价高昂。不同的工具调用工作负载适合不同的模型。路由网关提供统一的 API 接口，支持重试、故障转移、成本跟踪和安全防护。2026 年主流的三种架构：LiteLLM（开源自托管）、OpenRouter（托管 SaaS）、Portkey（生产级，2026 年 3 月开源）。本课程将说明决策标准并实现一个基于标准库的路由网关。

**类型：** 学习
**语言：** Python（标准库，路由 + 故障转移 + 成本跟踪）
**前置知识：** 第 13 阶段 · 02（函数调用），第 13 阶段 · 17（网关）
**耗时：** 约 45 分钟

## 学习目标

- 区分自托管、托管和生产级路由选项。
- 实现一个故障转移链，在定义的优先级顺序内在提供商失败时重试。
- 跨提供商跟踪每次请求的成本和令牌使用情况。
- 根据给定的生产约束条件，在 LiteLLM、OpenRouter 和 Portkey 之间做出选择。

## 问题场景

提供商路由重要的场景：

1. **成本。** Claude Sonnet 的价格是 Haiku 的 3 倍。对于分诊任务，Haiku 足够了；对于综合任务，Sonnet 值得投入。应逐请求路由。

2. **故障转移。** OpenAI 出现故障数小时，所有请求都失败。你需要自动回退到 Anthropic 而无需重新部署。

3. **延迟。** 实时聊天界面需要快速的首 token 时间。批量摘要器则不需要。应根据延迟 SLA 路由。

4. **合规。** 欧盟用户必须留在欧盟区域。应根据区域路由。

5. **实验。** 在同一工作负载上 A/B 测试两个模型。应根据测试分组路由。

手动在每个集成中编写所有这些逻辑会重复乏味。路由网关提供一个兼容 OpenAI 的 API 并处理其余部分。

## 概念

### 兼容 OpenAI 的代理形状

所有系统都采用 OpenAI 的形状。路由网关暴露 `/v1/chat/completions`，接受 OpenAI 架构，并在内部代理到 Anthropic / Gemini / Cohere / Ollama / 任何服务。客户端无需关心。

### 模型别名

你的代码中使用 `our_smart_model` 而非 `claude-3-5-sonnet-20251022`。网关将别名映射到真实模型。当 Anthropic 发布 Claude 4 时，只需在服务端更改别名，代码无需任何改动。

### 故障转移链

```
primary: openai/gpt-4o
on 5xx: anthropic/claude-3-5-sonnet
on 5xx: google/gemini-1.5-pro
on 5xx: refuse
```

网关在配置文件中定义此链。重试次数受预算限制，以防止故障转移级联导致成本暴增。

### 语义缓存

相同或近乎相同的提示会命中缓存而非提供商。在重复的智能体循环中，可节省 30% 到 60% 的成本。键基于嵌入，近乎相同的提示共享一个缓存槽位。

### 安全防护

网关层面：

- **PII 脱敏。** 在发送提示前进行基于正则或机器学习 的检查。
- **策略违规。** 拒绝包含禁止内容的提示。
- **输出过滤器。** 清理补全内容以防止泄漏。

Portkey 和 Kong 都内置了健壮的安全防护。LiteLLM 将其设为可选。

### 按密钥速率限制

一个 API 密钥对应一个团队。按密钥的预算可防止单个团队消耗共享配额。大多数网关都支持此功能。

### 自托管与托管的选择权衡

| 因素 | LiteLLM（自托管） | OpenRouter（托管） | Portkey（生产级） |
|--------|----------------------|----------------------|----------------------|
| 代码 | 开源，Python | 托管 SaaS | 开源（2026 年 3 月）+ 托管 |
| 设置 | 部署一个代理 | 注册 | 两者皆可 |
| 提供商 | 100+ | 300+ | 100+ |
| 计费 | 使用自己的密钥 | OpenRouter 积分 | 使用自己的密钥 |
| 可观测性 | OpenTelemetry | 仪表盘 | 完整 OTel + PII 脱敏 |
| 最佳适用场景 | 需要完全控制的团队 | 快速原型开发 | 生产环境需合规 |

当你有 SRE 团队且需要数据主权时，LiteLLM 胜出。当你想要单一订阅且无需基础设施时，OpenRouter 胜出。当你需要开箱即用的安全防护和合规时，Portkey 胜出。

### 成本跟踪

每个请求携带 `provider`、`model`、`input_tokens`、`output_tokens`。乘以每个模型每令牌的价格（来自网关维护的定价表）。按用户/团队/项目进行聚合。

### MCP 加路由

网关可以同时路由 LLM 调用和 MCP 采样请求。当采样请求的 modelPreferences 指定特定模型时，网关将其翻译到正确的后端。这是第 13 阶段 · 17（MCP 网关）与本课程路由网关有时合并为同一个服务的地方。

### 路由策略

- **静态优先级。** 列表中的第一个；出错时回退。
- **负载均衡。** 轮询或加权。
- **成本感知。** 选择满足延迟/质量的最便宜模型。
- **延迟感知。** 选择过去 N 分钟内最快的模型。
- **任务感知。** 提示分类器将代码相关提示路由到偏向智能的别名，摘要相关提示路由到偏向速度的别名。

## 使用它

`code/main.py` 在大约 150 行代码中实现了一个路由网关：接受 OpenAI 形状的请求，转换为各提供商的桩代码，运行优先级故障转移链，跟踪每次请求的成本，并对输入进行 PII 脱敏。运行三个场景：正常请求、主提供商故障触发回退、PII 泄漏被脱敏捕获。

要关注的要点：

- `ROUTES` 字典：别名 -> 按优先级排序的具体提供商列表。
- 故障转移循环在 5xx 时重试。
- 成本跟踪器将令牌使用量乘以每模型费率。
- PII 脱敏器在转发前清除类似社会安全号码的模式。

## 练习

1. 运行 `code/main.py`。触发故障场景，确认回退落在第二个提供商上，并且成本正确归因。

2. 添加语义缓存：提示的 SHA256 作为查找键；缓存命中时立即返回。在重复调用上衡量成本节省。

3. 添加一个提示分类器，将 "code ..." 提示路由到偏向智能的别名，将 "summarize ..." 提示路由到偏向速度的别名。

4. 设计团队预算：每个团队有每月支出上限，一旦达到上限，网关拒绝请求。选择执行粒度（按请求或窗口化）。

5. 并排阅读 LiteLLM、OpenRouter 和 Portkey 的文档。指出每个服务独有的一个功能，其他两个没有。
