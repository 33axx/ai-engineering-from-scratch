# 多区域 LLM 服务与 KV 缓存局部性

> 轮询负载均衡对缓存推理是有害的。未命中其前缀缓存的请求需要承担完整的预填充成本——长提示词的 P50 约为 800 毫秒，而缓存命中时约为 80 毫秒。到 2026 年，生产环境中的标准方案是缓存感知路由器（vLLM Router in Rust、llm-d router），它消费 KV 缓存事件并根据前缀哈希匹配进行路由。最近的研究（GORGO）将跨区域网络延迟显式纳入路由目标。商业化的“跨区域推理”产品（Bedrock 跨区域推理、GKE 多集群网关）将推理视为黑盒——它们处理的是可用性，而非 TTFT。摩根大通与梅奥诊所于 2024 年 11 月在 us-east-1 上进行故障切换，耗时约 22 分钟。灾备现实：32% 的 LLM 灾备失败原因是团队备份了权重但忘记了 tokenizer 文件或量化配置。

**类型：** 学习  
**语言：** Python（stdlib，简单的前缀缓存感知路由器模拟器）  
**先决条件：** Phase 17 · 04（vLLM Serving）、Phase 17 · 06（SGLang RadixAttention）  
**时间：** ~60 分钟

## 学习目标

- 解释为什么轮询负载均衡会破坏缓存推理，并量化 TTFT 惩罚。
- 绘制缓存感知路由器示意图：输入（KV 缓存事件）、算法（前缀哈希匹配）、决胜规则（GPU 利用率）。
- 说出 LLM 灾备失败的 32% 驱动因素（缺少 tokenizer 文件 / 量化配置），并列出三文件灾备检查清单。
- 区分商业跨区域推理产品（Bedrock CRI、GKE 多集群网关）与 KV 感知路由。

## 问题

你的服务运行在 us-east-1、us-west-2 和 eu-west-1 区域。你使用 ALB 并配置轮询策略。生产中前缀缓存命中率降至 8%，TTFT P50 增加了三倍。你的 vLLM 日志显示每个请求都承担了完整的预填充成本。

对于无状态服务，轮询是最优的。而 LLM 推理本质上是状态性的——KV 缓存编码了模型所见的一切。盲目路由就是路由到错误的缓存。

此外，你的团队制定了灾备计划。你将模型权重备份到跨区域的 S3 上。当某个区域内发生故障，你尝试故障切换，但副本拒绝启动。原来 tokenizer.json、量化配置和 RoPE 缩放配置存放在另一个未同步的存储桶中。

多区域 LLM 服务是一个缓存问题、路由问题和灾备卫生问题——而非负载均衡问题。

## 概念

### 缓存感知路由

请求到达时带有提示词。路由器对前缀（例如前 512 个 token）进行哈希；它向每个副本询问“你是否缓存了这个前缀？”。副本通过发布/订阅通道在分配和逐出块时发布 KV 缓存事件。路由器选择有匹配的副本，若无人匹配则回退到基于 GPU 利用率的决胜规则。

**vLLM Router**（Rust，2026 生产栈）：订阅 `kv.cache.block_added` 事件，维护前缀哈希 → 副本索引的映射，以 O(1) 查找进行路由。无匹配时回退到最小队列深度。

**llm-d router**：相同模式，Kubernetes 原生。通过 ControlPlane API 发布事件。

**SGLang RadixAttention**（Phase 17 · 06）是副本内部的对等概念。跨副本路由严格在上层进行。

### 数据

2K token 提示词，Llama 3.3 70B FP8，H100 上的 TTFT P50：
- 缓存命中（同一副本，前缀驻留）：~80 ms。
- 缓存未命中（冷预填充）：~800 ms。

10 倍差距。如果你的路由器在不同副本上达到 60-80% 的前缀缓存命中率，那么你就能以 N 副本容量近似达到单一副本的性能。如果只有 10%，则近似于简单扩展。

### 跨区域增加了新约束——网络延迟

区域间 RTT：
- us-east-1 ↔ us-west-2：~65 ms。
- us-east-1 ↔ eu-west-1：~75 ms。
- us-east-1 ↔ ap-southeast-1：~220 ms。

如果路由将请求从 us-east-1 导向 ap-southeast-1 的热前缀，节省的预填充时间（800 → 80 ms）会被 440 ms 的往返延迟淹没。GORGO（2026 研究）将此明确纳入考虑——联合最小化 `prefill_time + network_latency`，而不仅仅是预填充时间。通常的答案是保持区域级路由，除非在处理非常大的前缀（数 MB）时预填充占主导。

### 商业“跨区域推理”在此无帮助

AWS Bedrock 跨区域推理在容量压力下自动将请求路由到其他区域。它优化的是可用性，而非 TTFT，且将推理视为黑盒。GKE 多集群网关也是如此——服务级故障切换，不感知 KV 缓存。

即使使用这些产品，你仍然需要一个应用层的缓存感知路由器。它们处理的是“us-east-1 着火了”的情况，而缓存感知路由处理的是 TTFT 问题。

### 灾备卫生——32% 的文件缺失问题

2026 年被广泛引用的统计：32% 的 LLM 灾备失败是因为团队备份了权重但忘记了：

- `tokenizer.json` 或 `tokenizer.model`
- 量化配置（`quantize_config.json`、AWQ scales、GPTQ zero-points）
- 模型特定配置（RoPE 缩放、注意力掩码、聊天模板）
- 引擎配置（`vllm_config.yaml`、采样默认值、LoRA 适配器清单）

修复方法是三类文件的最小灾备清单：

1. HF 模型仓库下的所有文件（权重 + 配置 + tokenizer）。
2. 引擎特定的服务配置。
3. 部署清单（K8s YAML、Dockerfile、依赖锁定）。

此外：每季度执行灾备演练。摩根大通 2024 年 11 月对 us-east-1 的演练达到了 22 分钟恢复时间，这仅仅是因为剧本经过多次排练。

### 数据驻留是正交约束

欧盟客户的 PHI 不能离开欧盟。如果你的缓存感知路由器将来自巴黎的请求发送到 us-east-1 以获取前缀匹配，那么无论 TTFT 增益如何，你都违反了 GDPR。在优化缓存之前，先按数据驻留边界对路由器进行分区。

### 你应该记住的数据

- 缓存命中与未命中的 TTFT 差距：~10 倍（2K 提示词上 80 ms vs 800 ms）。
- 跨区域 RTT（美欧）：~75 ms。
- 灾备失败：32% 遗漏 tokenizer/量化配置。
- 摩根大通 us-east-1 故障切换（2024 年 11 月）：22 分钟（30 分钟 SLA）。

## 关键术语

| 术语 | 大家说的 | 实际含义 |
|------|---------|----------|
| 缓存感知路由 | "智能LB" | 基于前缀哈希匹配路由到持有 KV 缓存的副本 |
| KV 缓存事件 | "缓存发布订阅" | 副本发布块添加/逐出事件；路由器建立索引 |
| 前缀哈希 | "缓存键" | 前 N 个 token 的哈希，用于路由器查找 |
| GORGO | "跨区域路由研究" | arXiv 2602.11688；将网络延迟作为显式项 |
| 跨区域推理 | "Bedrock CRI" | AWS 产品；可用性故障切换，不感知 TTFT |
| 灾备清单 | "备份列表" | 恢复所需的所有文件——不仅仅是权重 |
| 数据驻留 | "GDPR 边界" | 法律约束，决定哪一区域可以处理用户数据 |
| RTT | "往返时间" | 网络延迟；美欧 75 ms，美亚太 220 ms |
| LLM 感知 LB | "缓存命中LB" | 缓存感知路由器作为一个产品类别 |
